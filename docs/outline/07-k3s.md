# Infrastructure — K3s cluster

Learning environment. Complexity is intentional here. Failure has no impact on must-run services.

## Topology

6 VMs total — one control plane VM and one worker VM per physical node, co-located. K3s embedded etcd provides HA control plane — losing one node does not take down the cluster.

| VM | Node | IP | Role | vCPU | RAM |
|----|------|-----|------|------|-----|
| k3s-cp-1 | skadi | `10.0.20.150` | Control plane + etcd | 2 | 2 GB |
| k3s-cp-2 | sigyn | `10.0.20.151` | Control plane + etcd | 2 | 2 GB |
| k3s-cp-3 | sylvi | `10.0.20.152` | Control plane + etcd | 2 | 2 GB |
| k3s-wk-1 | skadi | `10.0.20.153` | Worker — heavy workloads | 2 | 8 GB |
| k3s-wk-2 | sigyn | `10.0.20.154` | Worker | 2 | 4 GB |
| k3s-wk-3 | sylvi | `10.0.20.155` | Worker | 2 | 3 GB |

skadi's worker gets the most RAM — the Celeron has 32 GB and hosts memory-heavy workloads like Immich and Jellyfin.

All VMs use fixed memory allocation (no ballooning) for predictable resource usage.

| Authentik | Identity provider — OIDC/SAML for all apps |

## GitOps workflow

```
Push to GitHub repo
  → Flux detects change (1-minute poll interval)
    → Flux reconciles cluster state
      → Resources created/updated automatically

Renovate scans image tags and Helm chart versions
  → Opens PR with version bump
    → Review and merge
      → Flux deploys automatically
```

No manual `kubectl apply` for production workloads. Ever.

## Storage

All persistent volumes are NFS-backed via democratic-csi pointing at Synology `/volume1/k3s-data`. No local-path storage for anything that matters. No iSCSI.

## Database backends

Databases run in LXCs outside K3s — not in Kubernetes. Running clustered databases in K8s adds operational complexity without benefit at this scale.

- **MariaDB Galera** (×3 LXCs, one per node) — phpIPAM
- **PostgreSQL** (×3 LXCs, one per node) — Authentik, Vault, AWX, Outline, Immich, n8n, Teamspeak
