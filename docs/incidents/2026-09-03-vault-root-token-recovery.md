# 2026-09-03 — Vault root token leaked in a transcript, rotation tooling had two bugs, old token went invalid mid-rotation, recovered via `generate-root`

## Summary

During Immich deploy work, `vault token lookup -format=json` was run to diagnose a stale AppRole and its output — including the literal root token value — was displayed in a Claude session transcript. Building a proper rotation tool (`rotate-vault-root-token`, new function in both shim dialects) surfaced two real bugs before it worked: `vault token lookup` has no `-field` flag (used to safely extract just the accessor — wrong, `-format=json` capture + `jq` is the actual safe pattern), and a hash-verification step had a trailing-newline mismatch between `op read`'s output and the locally-held value (false-positive failure, correctly aborted before touching anything). Both fixed and verified.

The first *real* rotation attempt (after both bugs were fixed) then hit a third, more serious issue: `op item edit` reported success but silently did not write the new token to the 1Password item — proven by an independent read-back returning the *old* token's accessor. The script's design was wrong here too: it should have followed `rotate-approle`'s already-established print-and-paste pattern (1Password CLI editing is documented elsewhere in this repo as unreliable for certain item fields) instead of reinventing an automated write. Redesigned to match.

Between fixing that and re-attempting the rotation, **the old root token itself went invalid** (`403 permission denied / invalid token`) even though the owner confirmed only the orphaned *new* token from the failed first attempt was revoked — the old one should have been completely unaffected by that. Root cause was not conclusively identified (see "What's still open"). With no working root token and Vault otherwise healthy (confirmed via the still-functional `ansible-local` AppRole), recovery used Vault's actual designed-for-this mechanism: `vault operator generate-root` against 3 of 5 Shamir recovery-key shares. Recovered cleanly; new token saved via the 1Password **app GUI** (not CLI) and independently read-back-verified.

## Trigger

Owner: *"can you create a script that rotates my root vault token and updates 1password?"* — following up on an earlier in-session flag that the root token had appeared in a tool-output transcript (`vault token lookup -format=json`) and should be rotated.

## Sequence

1. Wrote `rotate-vault-root-token` (bash/zsh `.config/scripts/homelab.sh` + fish `.config/fish/conf.d/homelab.fish`) — mint orphan token, write to 1P, hash-verify, live-check, prompt, revoke old. Syntax-checked in all three shells; guard/precondition paths tested. Not run end-to-end (correctly — the design requires an interactive terminal for the confirm-before-revoke prompt, which a non-interactive Bash tool call can't satisfy).
2. Owner ran it. Failed immediately: `vault token lookup -field=accessor` → `flag provided but not defined: -field`. `vault token lookup -h` confirmed: only `-format` is supported, not `-field` — that flag only exists on the `read`/`write`/`kv get` command family, which wraps a different internal response type. Fixed both shim files (capture `-format=json` into a local var, `jq -r '.data.accessor'`, discard the var) and the shell-tooling.md gotcha that had recommended the nonexistent flag.
3. Owner re-ran. Got further — minted new token, wrote to 1P, then failed at hash-verify: `1P write verification FAILED (hash mismatch)`. Diagnosed: `op read` appends a trailing newline to stdout; the verify side piped that raw into `shasum` while the source side was hashed via `printf '%s'` (no newline) — comparing "token" against "token\n". Fixed by capturing `op read`'s output into a variable first (command substitution strips trailing newlines in both bash/zsh and fish) before hashing. **The safety gate worked correctly** — it aborted before revoking the old token, on what turned out to be a false-positive.
4. Owner re-ran a third time. This time genuinely useful information: the diagnostic one-liner (`VAULT_TOKEN=$(op read ...) vault token lookup -format=json | jq -r .data.accessor`) returned the **old** token's accessor, not the new one — proving `op item edit "$__op_vault_root" "password=$new_token"` had reported success (exit 0) while not actually persisting the value. Matches an already-documented class of gotcha in this repo (`known-issues/shell-tooling.md`: "Password item missing a `ps` value errors... the validator rejects ANY edit"), just a worse instance — a silent no-op instead of a hard error. Redesigned the function to match `rotate-approle`'s proven pattern instead: print the value, human pastes into the 1Password GUI, script hash-verifies the read-back. Removed the automated `op item edit` call entirely. Also caught and removed a leftover duplicate confirm-prompt in the fish version (an artifact of the original two-prompt design collapsing to one).
5. Owner revoked the orphaned token from the failed first attempt (`vault token revoke -accessor ntYcahzwbDg4VMuQQs6dVc6M`, confirmed the *correct* accessor, not the old one).
6. Owner re-ran the redesigned function. It failed at the very first step — looking up the *current* (old) token — with `403 permission denied / invalid token`. The old token, which had been independently confirmed working via a live lookup earlier in this same session (step 4's diagnostic), was now dead. Nothing in the owner's actions between then and now should have touched it (the only action was revoking the *different*, already-isolated orphan accessor). Root cause not established with certainty — see "What's still open."
7. Confirmed Vault itself was healthy and unaffected (`vault-homelab-env --refresh` succeeded cleanly via the completely separate `ansible-local` AppRole) — this was a root-token-specific problem, not a Vault outage.
8. Recovered via `vault operator generate-root`: `-init` for a nonce+OTP (no auth required — this is Vault's designed unauthenticated bootstrap-recovery path), 3 of 5 recovery-key shares submitted interactively (secure prompt, never touched shell history/process args/a transcript — Claude relayed only the commands to run, never received or handled key material), decoded the resulting token with the OTP, saved via the 1Password **app** (not `op item edit`, not `op` CLI at all this time), and independently read-back-verified via the same `op read | vault token lookup` diagnostic used throughout — new accessor confirmed live and distinct from both prior accessors.

## Findings (encoded as gotchas)

1. **`vault token lookup -format=json` prints the literal token at `.data.id`** — never display that output where it might land in a transcript/log. → `known-issues/shell-tooling.md`.
2. **`vault token lookup` has no `-field` flag** (only `-format`) — the safe extraction pattern is capture-full-JSON-into-a-variable → `jq` → discard the variable, never `-field`. → `known-issues/shell-tooling.md`.
3. **Hash-verifying a value read via `op read` needs the read captured into a variable before hashing** — piping directly into `shasum` includes `op read`'s trailing newline, which the source side (typically built via `printf '%s'`, no newline) won't have. Same *class* of bug as the already-documented `vault kv patch <field>=-` stdin issue, different direction (read side, not write side).
4. **`op item edit` can report success while silently not writing the value — confirmed live, not just theoretical.** Matches the existing "SSH-Key items / malformed Password items reject CLI edits" gotcha class, but worse: a no-op instead of a hard error, so nothing signals the failure short of an independent read-back. `rotate-approle`'s print-and-human-pastes pattern exists for exactly this reason; `rotate-vault-root-token` now follows it instead of automating the write. → `known-issues/vault.md`.
5. **`vault operator generate-root` is the correct recovery path when no valid root token exists and Vault is otherwise healthy** — no existing root token required, just a threshold of Shamir recovery-key shares (this cluster: 3 of 5, `Total Recovery Shares: 5 / Threshold: 3` per `vault status`). Full ceremony: `-init` (unauthenticated, returns Nonce + OTP) → `-nonce=<nonce>` submitted 3× interactively (secure prompt, no key material on the command line or in scrollback) → `-decode=<encoded-token> -otp=<otp>` → save + verify. Worth having as a documented runbook rather than re-deriving under pressure next time.
6. **A non-interactive Claude session's `op` CLI session does not share state with the operator's own terminal `op signin`, even on the same machine, and retrying `op whoami` a few times did not resolve it this time** (contrast the `ansible-frigg` incident earlier the same day, where a second call *did* work) — don't assume the "just retry" fix is reliable; if it doesn't land after 2-3 tries, hand the command to the operator to run directly rather than continuing to poll.

## What's still open

- **Root cause of the old root token going invalid was not established.** The owner confirmed they revoked only the correct, already-orphaned accessor from the failed first attempt (`ntYcahzwbDg4VMuQQs6dVc6M`), which should have been completely isolated (minted with `-orphan`, no parent-child relationship to the old token) from the old token (`N4sx52OEig5YfpiMoi9Bf5Ja`) — yet the old token stopped working between an independently-confirmed-working read (mid-incident, step 4 above) and the next attempt (step 6). Candidate explanations, none confirmed: a 1Password multi-device sync race re-writing the field to a stale/different value after the mid-incident check; some Vault-side session/lease behavior not accounted for; operator action not fully captured in this transcript. **Recommend:** if this recurs, capture `vault list -format=json auth/token/accessors` (needs some other valid elevated token) and 1Password's item edit history for the root-token item *before* attempting any fix, to actually pin the cause down.
- **No alerting exists for "the root token stopped working."** This was caught only because a rotation happened to be in progress. Same class of gap as the `ansible-frigg` AppRole silent-expiry incident earlier the same day — that incident's own "what's still open" item (SecretID-expiry alerting) should probably be scoped to cover root-token health too, not just AppRoles.
- **`generate-root` was walked through live but isn't yet a documented runbook** (`docs/procedures/`) — worth writing up properly given how rarely it's needed and how easy it would be to fumble under pressure without a checklist.
