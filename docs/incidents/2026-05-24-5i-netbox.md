### 2026-05-24 — Phase 5i: NetBox IPAM/DCIM deploy

**Goal:** Stand up NetBox in asgard K3s as the homelab's IPAM/DCIM source of truth. External PG via the 5g.2 HAProxy VIP, bundled Valkey, Authentik OIDC, internal-only HTTPRoute. Populate initial inventory (sites, cluster, VLANs, prefixes, devices, VMs, IPs) via web UI. Decide the TF↔NetBox integration direction for going-forward writes.

**Process:** Three parallel research agents spawned for chart deployment specifics, NetBox→Ansible inventory integration, and TF↔NetBox direction (~3 minutes wall-clock for ~4500 words of findings). Sub-steps 5i.a (PG DB) → 5i.b (Authentik OIDC) → 5i.c (HelmRelease + 6 follow-up fixes) → 5i.d (HTTPRoute + CoreDNS rewrite with 1 follow-up fix) → 5i.e (web-UI data import per the procedure doc) → 5i.f (this post-flight). Wall-clock ~5 hours including ~2 hours of fix iteration on 5i.c chart quirks + 1 hour of CoreDNS rewrite discovery + the data import session.

**Findings, in rough order of discovery:**

1. **`tasks_from:` in the play-level `roles:` keyword is silently ignored.** Found while validating 5i.a's netbox DB creation — `psql` as user `netbox` returned "password authentication failed" despite the Vault password being correct. Diagnosis chain: confirmed Vault had the password → confirmed Ansible plays show as ok → confirmed no `\du netbox` row in PG → noticed that the postgres-host playbook's "sandwich" pattern of `roles: [postgres tasks_from: prepare, patroni, postgres tasks_from: bootstrap]` was actually running `main.yml` twice (with `tasks_from:` silently ignored), and main.yml gated the bootstrap-include on `when: not postgres_patroni_managed` — so in patroni-managed mode the user/DB creation tasks were dead code. **Two fix approaches considered**: (a) swap `roles:` block for `import_role` in `tasks:` (which honors `tasks_from`), minimal 1-file diff; (b) split into `postgres` + `postgres-common` roles where each does one thing, the playbook lists them sequentially. Picked (b) for clarity — `postgres-common` is reusable for future standalone PG deployments where the patroni layer is skipped. Commit `69d72d3`.

2. **netbox-chart's bundled Valkey defaults to replication mode + needs `volumePermissions` for iSCSI.** Valkey crashed at startup with `Can't open or create append-only dir appendonlydir: Permission denied` — same Synology CSI fsGroup-not-honored class as Vault + Authentik Redis. Two fixes in one commit: `valkey.architecture: standalone` (don't need replication for single-tenant cache) + `valkey.volumePermissions.enabled: true` (adds root-running chown initContainer). Cleanup needed too — replica StatefulSet's PVC left orphaned with retain policy. Commit `90c6abe`.

3. **netbox-chart shares ONE RWO media PVC between server + worker.** Synology CSI is iSCSI-only — no RWX. RWO + two deployment consumers means both pods must land on the same node (otherwise the second blocks unmounting). PVC stuck Pending; even if it provisioned, anti-affinity + same-node-requirement is a scheduling deadlock waiting to happen. **Workaround**: `persistence.enabled: false` (emptyDir for media). Accepted while no device photos exist; documented inline as the three future options (accept same-node, singleton server PVC, NFS export on Munin). Commit `6cf090b`.

4. **netbox-chart `existingSecret` references project ALL expected keys without `optional: true`.** Two iterations of "couldn't find key X in Secret Y": first `email_password` on `netbox-app` (chart docs say only `secret_key` is needed; pod's projected secret references email_password / ldap_bind_password / napalm_password unconditionally — must be provided as empty strings); then `username` on `netbox-superuser` (chart wants username/email/password/api_token, ignores the `superuser.username`/`.email` values block). Both fixes added empty-string-or-literal values to the ExternalSecret template. Commits `182a06f` + `40a5be3`.

5. **`resourcesPreset: small` (768Mi) OOMs during NetBox migrations.** The 5i.c research guide said `small` was right for ~50 devices; that was steady-state numbers. Django bootstrap + initial migrations + granian worker startup spike well above the limit. Bumped both server + worker to `medium` (1536Mi); peak observed ~830Mi, so margin is healthy. Lesson: size for migration peak, not steady state. Commit `5eb1f0a`.

6. **In-cluster pod-to-MetalLB-VIP traffic is broken; CoreDNS rewrite is the cluster-wide answer.** NetBox's OIDC backchannel (discovery + token exchange + userinfo) to `authentik.midgard.xiiisins.com:443` timed out from inside the pod — AGH returns 10.0.20.10 (Traefik MetalLB VIP) which doesn't work for pod-originated traffic (well-known L2-mode tromboning issue). Tried a per-pod `hostAlias` to 10.0.20.10 first — same target IP, same timeout. Realized this generalizes the pre-existing "Cloudflared targets ClusterIP DNS, NEVER MetalLB IPs" rule. **Cluster-wide fix**: K3s `coredns-custom` ConfigMap with `rewrite name exact <fqdn> traefik.traefik.svc.cluster.local`. CoreDNS resolves the rewritten name to Traefik's ClusterIP at query time (volatility-safe — DNS resolves at query time, same as Cloudflared's `https://traefik.traefik.svc.cluster.local:443` pattern). Pod connects to Traefik with the original SNI + Host header → Traefik's wildcard cert matches → TLS validates cleanly → HTTPRoute resolves the right backend. External clients unaffected (browsers resolve via AGH, hit the VIP, that path works fine). Commit `44c8f63`.

7. **K3s `coredns-custom` ConfigMap: `*.override` vs `*.server` keys matter.** First attempt at the rewrite used the data key `rewrites.server` — CoreDNS REFUSED queries with "recursion not available". Diagnosis via reading the actual Corefile in the `coredns` ConfigMap: K3s imports `data` keys ending in `*.override` INSIDE the default `.:53` server block (for plugin directives like `rewrite`), and `*.server` keys at TOP LEVEL (for full new server blocks like `myzone.:53 { ... }`). Our bare `rewrite name exact ...` line is a plugin directive; outside any server block it's a syntax error and CoreDNS silently rejects the file. Renamed key `rewrites.server` → `rewrites.override`; CoreDNS auto-reloaded; queries resolved correctly. Commit `cd80202`.

8. **netbox-chart `extraConfig.secret:` mounts files at `/run/config/extra/<index>/<key>` but the chart's exec-loader doesn't propagate variables to Django settings reliably for index>0.** Browser flow worked through to Authentik but returned "Client ID Error" — NetBox was sending an empty `client_id`. Verified `kubectl exec ... manage.py shell` showed `SOCIAL_AUTH_OIDC_KEY = '<UNSET>'` despite the secret being mounted at `/run/config/extra/1/99-oidc.py` with correct content. The `values:` block (always index 0) propagated correctly (`SOCIAL_AUTH_OIDC_OIDC_ENDPOINT` was set); the secret-derived file at index 1 mounted but its variables never reached settings. **Fix**: stopped using `extraConfig.secret:` — used chart's `extraVolumes` + `extraVolumeMounts` with `subPath` to mount the secret file directly into `/etc/netbox/config/99-oidc.py` where NetBox's own configuration loader picks it up. `subPath` is critical (without it, the volume mount replaces the entire dir, clobbering the rest of the config files). Commit `715ab13`.

9. **NetBox OIDC group→permission sync is NOT automatic.** First OIDC login succeeded — user `ghost` was auto-created — but the user could authenticate and then immediately couldn't do anything. `autoCreateUser: true` provisions the record but with zero NetBox-side permissions; the Authentik `netbox-admins` group membership means nothing to NetBox's RBAC by default. **Quick fix**: log in as the local-superuser (`admin` + Vault password) via the regular login page, navigate to Admin → Users → ghost, check Active + Staff + Superuser, save, log out + log back in via OIDC. Permanent fix is a custom `SOCIAL_AUTH_PIPELINE` override that maps Authentik group claims → NetBox permission assignments — deferred until manual elevation per user becomes recurring toil (>3 users).

10. **`tight coupling` is the right TF↔NetBox direction for the homelab.** Three-way research between TF→NetBox writes (Option A), NetBox→TF reads (Option B), and webhook-driven runs (Option C). Picked A because (a) Git already is the IaC spec — inverting to NetBox-UI-as-spec would be a regression; (b) Option B makes NetBox a hard runtime dependency of `terraform apply` AND exposes the IP-allocation race in `netbox_available_ip_address` (upstream issue #59); (c) Option C needs remote TF state + a runner, neither of which we have. Provider pick: `e-breuninger/netbox` v5.3.0 (only actively-maintained NetBox provider in 2026, consensus for official-provider promotion in the NetBox community discussion). Implementation Phase 5i.3 — NOT deferred indefinitely, immediate next phase.

**Successes worth noting:**

- **CoreDNS rewrite generalizes a real pattern**, not just a NetBox fix. Any future K8s workload hitting an internal K8s-fronted FQDN now has the right plumbing for free. Cluster-wide single point of maintenance.
- **Cloudflared was the right reference point** for the in-cluster-traffic question. Its existing `service: https://traefik.traefik.svc.cluster.local:443` + `httpHostHeader` + `noTLSVerify` pattern shows the same problem solved at the app level. Our CoreDNS rewrite is the cluster-level equivalent for workloads that lack Cloudflared's app-level config flexibility (e.g. python-social-auth in NetBox).
- **Research agents paid off.** The three parallel research findings (chart specifics, Ansible inventory, TF direction) compressed what would have been hours of discovery into actionable scope decisions before any code was written. Saved at least one bad-architecture deploy.
- **Web-UI data import was tractable.** ~50 records (site / cluster / types / roles / VLANs / prefixes / 5 devices / 17 VMs+LXCs / 3 VIPs) took the user about an hour to enter via UI. Documented as a procedure so any future rebuild can replay it. Hand-entered descriptions cross-link each entry to its IaC source — manual bridge until 5i.3 lands.
- **`postgres-common` role split is cleaner than the original sandwich pattern**, regardless of the `tasks_from:` bug. The split makes the responsibility boundaries explicit (preparation vs object-provisioning) and is reusable for any non-Patroni-managed PG deploy.

**Resolution:** NetBox live at `https://netbox.niflheim.xiiisins.com`, fully populated with current homelab inventory, OIDC working end-to-end. Eleven netbox-chart gotchas in CLAUDE.md NetBox section. CoreDNS rewrite + `tasks_from`-in-`roles` warning generalized into cross-cutting CLAUDE.md sections (DNS / Networking / Ansible-roles). Four new decision rows in `docs/operations/decisions.md`. New `docs/services/netbox.md` documents the architecture. TF→NetBox integration scoped for Phase 5i.3 as the immediate next phase.

**Root-cause patterns:**

- *"It's documented" doesn't mean "it does what the docs say".* netbox-chart's `existingSecret` docs imply minimal keys; the chart projects many more. `extraConfig.secret:` docs say it mounts secret files for NetBox config; the chart's loader doesn't propagate them to Django settings. Read the chart source or test the assumption before relying on the docs.
- *"In-cluster traffic to MetalLB-VIP" is a recurring class.* We had the Cloudflared instance of it; NetBox surfaced another. Future K8s workloads will hit the same pattern when they need to reach a K8s-fronted internal FQDN. The CoreDNS rewrite is the structural answer; new workloads get it for free now.
- *Silent-failure patterns surface late.* `tasks_from:` in `roles:` block silently runs the wrong code path. K3s coredns-custom `.server` vs `.override` silently rejects the bad-syntax file. NetBox's chart loader silently fails to propagate secret-derived files to settings. Each took ~30 min to diagnose because the symptom was "thing X isn't doing what I told it to" rather than "thing X errored loudly". Cataloguing these in CLAUDE.md is the operational defense.
- *Tight coupling beats loose coupling when the operator's discipline is the only enforcement mechanism.* The TF→NetBox direction choice (tight, in same module) was the right call for a single-operator homelab specifically because loose coupling would degrade silently when the operator forgets the second-step apply. Discipline is a thinner safety net than tooling-enforced consistency.
- *Research agents are worth the latency cost.* Three parallel ~3-min agents returned ~4500 words of structured findings. The alternative was ~3 hours of trial-and-error during the deploy. The deploy itself still had 11 surprise gotchas, but they were chart-quirks that no amount of research would have caught — the research correctly informed the higher-level decisions (provider pick, integration direction, deployment pattern).
