# 2026-10-02 — Phase 10d1: Gná (n8n agent host) deploy: findings

*Not an outage: a retrospective on the first apply of a new host. Plan: [`10d-diagnosis-chatops.md`](../operations/10d-diagnosis-chatops.md); procedure: [`procedures/aiops-diagnosis.md`](../procedures/aiops-diagnosis.md); code: PR #32 (+ #33).*

## What happened

The 10d1 code (LXC 1121, NetBox, DNS, Vault secrets, `n8n-agent` role, Caddy ingest listener, stub workflow) was reviewed and merged as #32. The applies ran from the main checkout: `asgard-lxcs`, `vault` and `adguard` went through; `netbox` failed once; after the fix (#33) everything applied. The playbook then ran bootstrap -> full -> re-run (no-op) -> reboot -> re-run (no-op). Final state: `ok=92 changed=52` on the first full play, `changed=0` on both re-runs, n8n and Caddy not restarted by the re-runs, the workflow re-activating by itself after a reboot.

## Findings

1. **A new NetBox group needs its `ansible:<group>` tag declared in `tags.tf`; I added the role mapping and the VM but not the tag.** `terraform plan` showed `4 to add`, the apply died on the VM: `could not locate referenced tag "ansible:n8n-agent" in netbox, no results`. `terraform validate` and CI cannot see this (it is a lookup against live NetBox). Fixed in #33; checklist now in [`known-issues/netbox.md`](../known-issues/netbox.md). *Lens that was missing:* the pre-flight read the NetBox pattern but not the tag catalog the VM resource resolves names against. **Follow-up:** a cheap CI check that every value of `local.ansible_group_for_role` has a key in `local.tags`.
2. **The macOS control node reads a materialized NetBox snapshot, which predates any new host.** After the NetBox apply `ansible-playbook` said `Could not match supplied host pattern, ignoring: gna` and `no hosts to target`, although `hosts.yml` listed the host: `env.sh` exports `ANSIBLE_INVENTORY` pointing at `ansible/inventory/.netbox-cache.yml` (written 05:49, before Gná existed), which *replaces* the `ansible.cfg` inventory list. Fix: `.config/scripts/refresh-netbox-inventory-cache.sh` (31 hosts after). Now documented in [`known-issues/frigg-control-node.md`](../known-issues/frigg-control-node.md). Diagnose with `ansible-inventory --graph`, never `--list` (it merges the decrypted `vault.yml`).
3. **`cmd 2>&1 > file` leaves stderr on a non-blocking handle and Ansible refuses to start** (`Ansible requires blocking IO on stdin/stdout/stderr`). Redirect as `cmd > file 2>&1`.
4. **The first-deploy unknowns I could not prove off-host all held.** `SystemCallFilter=@system-service` with Node 22 on Debian 13: fine (`systemd-analyze security` exposure 1.5, OK); the LXC `nesting` feature with the unit sandbox: fine; Caddy `:8081` from Hugin: the designed matrix (webhook route reaches n8n -> 403 for lack of a token; `/healthz`, `/rest/login`, `/webhook-test/*` -> Caddy 404; from a non-allowlisted source every path -> 403).
5. **The `/healthz`-before-workflow-registration race is real on the host too.** The smoke test and the "wait for n8n" task both retried a few times on the first start and after the reboot; my own immediate post-reboot `curl` got connection refused. Probe the route, not `/healthz` (already in [`known-issues/n8n-aiops.md`](../known-issues/n8n-aiops.md)).
6. **Worked as designed:** env-managed owner (no UI step), the checksum-gated import (a re-run restarts nothing), staged credentials removed, `0600`/`0400` modes, root SSH locked out, services persisting across a reboot. The local end-to-end test against a mock Discord before the deploy caught the Caddy auto-HTTPS and `/healthz` issues so they never reached the host.
