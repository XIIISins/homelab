# 2026-09-03 — homelab-env cache write leaked the full credential set into a Claude transcript; eight credentials rotated

## Summary

While preparing to rotate the `ansible-awx` Vault AppRole, a compound Bash tool call chained `source homelab.sh && vault-homelab-env >/dev/null && set-vault-token root >/tmp/svt.log 2>&1; ...; cat /tmp/svt.log; ...`. The `cat` of that log file printed roughly 22 `value=<literal>` lines into the tool output — the full contents of `__homelab_cache_write`'s internal loop (`value=$(printenv "$env_var")` per cached var), landing every currently-loaded homelab credential directly in the session transcript: the freshly-set Vault root token, an AWS access+secret key pair, the `ansible-local` AppRole role_id+secret_id, the Cloudflare API token, the Authentik admin API token, the AdGuard admin password, the NetBox API token, and the Semaphore API token (plus non-sensitive paths/URLs). Root cause of *why* that loop's output reached stdout was never conclusively established — persistent `xtrace`/`SHELLOPTS`/`BASH_ENV`/profile causes were all ruled out, and `homelab.sh` has no explicit `echo`/print of those values. See "What's still open."

The owner independently confirmed the leak was real and rotated the Vault root token themselves (separately documented in [`2026-09-03-vault-root-token-recovery.md`](2026-09-03-vault-root-token-recovery.md)). The remaining seven credentials were rotated across the rest of the session, with Claude designing each rotation and the harness's own permission classifier correctly blocking every attempt by Claude to execute the mutating steps directly — credential creation, 1Password writes, and revocations all had to be handed to the owner to run. That constraint turned out to be the right shape for this class of work regardless: it forced a "never print the new secret to Claude's own tool output" discipline throughout, matching the print-and-paste + hash-verify pattern already established by `rotate-approle` and (that same day) `rotate-vault-root-token`.

Six of the eight rotations were mechanical (AppRole, AWS, Cloudflare, Authentik, NetBox, Semaphore) but each surfaced a real, previously-undocumented gotcha about how its credential actually gets consumed. The seventh — AdGuard Home's admin password — took by far the longest: AGH has no API-token concept, the admin role's config-render task is deliberately guarded to protect live dynamic state, and the fix-attempts hit a `sed` delimiter bug and a bcrypt-hash-comparison false alarm before landing. Full narrative below.

## Trigger

Owner, mid-session: *"instead of scripts. give me the commands to run (and from where/what folder)"* — following the discovery that the Bash tool's own permission classifier blocked Claude from running the AppRole/AWS rotation scripts directly. The pivot to owner-executed commands is what then surfaced the AdGuard idempotency-guard problem, since the owner was now the one reading real command output and catching things Claude's own scripted approach might have silently gotten wrong too.

## Sequence

1. Investigating the pending `ansible-awx` AppRole rotation task, ran the compound command described above. The `cat /tmp/svt.log` step printed the full leaked block. Initially misread it as harmless debug noise.
2. Owner's next message: *"I don't know what you catted from the svt.log but I for sure see the root token again and others."* — confirmed the leak was real, not a misreading.
3. Investigated the mechanism (safe, values-free checks only): fresh-shell `set -o` showed `xtrace off`; `SHELLOPTS`/`BASH_ENV`/`ENV` were all empty; `grep`-ing `.zshrc`/`.zprofile` for `set -x`/`setopt xtrace`/`set -v` found nothing; `grep`-ing `homelab.sh` for `value=` found only the internal `value=$(...)` assignment lines (in `__homelab_cache_write` and `__vault_homelab_cache_write`), no `echo`/print statement of any kind. Root cause not established — see "What's still open."
4. Mapped every leaked value to its exact shim variable name by reading `__homelab_static_env_map`/`__homelab_env_map`'s array declarations (names + 1P item UUIDs only — no live secret values touched) and cross-referencing against `__homelab_cache_write`'s known iteration order (static map → env map → `VAULT_TOKEN` → AWS pair). This corrected an earlier wrong guess make in the moment (had first called the AdGuard password "ghost's personal password" — it's `ADGUARD_PASSWORD`).
5. Owner rotated the Vault root token themselves. Full narrative in the sibling incident doc.
6. Attempted to execute a scripted rotation of `ansible-local`'s AppRole (mint → 1P write → hash-verify → revoke, all inside one script so no intermediate value ever reached Claude's own output) — blocked by the harness's Bash permission classifier ("destructive/sensitive action"). Same result on a similarly-designed AWS key rotation script. Per the classifier's own guidance, did not attempt to work around it; instead handed the owner direct commands for each remaining rotation, one credential at a time, for the rest of the session.
7. **`ansible-local` AppRole** — owner ran the existing `rotate-approle ansible-local` shell function directly. Closed with no new findings (the tooling already existed and worked).
8. **AWS state key** — first attempt used the `terraform-state` IAM identity's own credentials to call `aws iam list-access-keys` on itself: `AccessDenied` (that identity is deliberately S3-only, no IAM self-management permissions — confirmed via `terraform/aws/main.tf`'s policy document). Found the key is actually a Terraform-managed resource (`aws_iam_access_key.terraform_state`); correct rotation is `terraform apply -replace=aws_iam_access_key.terraform_state` run with the **bootstrap** AWS identity (the one that originally created the user), pulling the new key straight from `terraform output -raw` into a shell variable. `-replace` destroys-then-creates atomically, so there's no separate old-key cleanup step.
9. **Cloudflare API token** — owner rolled it in the Cloudflare dashboard first, then asked which 1P item it was. Tracing the consumers found the token is actually mirrored to *three* places, none Terraform-managed for the value itself (`ignore_changes` on all): the 1P item (Terraform provider auth), `secret/k8s/cert-manager/cloudflare` (cert-manager's DNS-01 solver, synced into K8s via ESO), and `secret/ansible/cloudflare/api-token` (Ansible/Semaphore self-verify checks). All three needed manual re-sync from the new 1P value via `vault kv patch`.
10. **Authentik admin API token** — a manually-provisioned bootstrap token (`authentik-bootstrap-token`, not Terraform-managed). Authentik's `/api/v3/core/tokens/` API supports create + `view_key` (retrieve the raw key once) + delete cleanly; rotated via API in one pass with no surprises — old-and-new both valid during the safety window, deleted old only after the new one proved it authenticates.
11. **NetBox admin API token** — matched the leaked value's 12-char `nbt_`-prefix (`Yx5SzvzyfQsA`) to token id `37` via `/api/users/tokens/` (list responses show only that masked prefix, not the real secret — expected). Created a replacement via the same API, extracted `.key` from the create response — but its length was only 12 characters (checked deliberately this time, after the AdGuard hash surprise had not yet happened but out of general caution), matching the *masked* display value, not a real secret. This NetBox deployment's REST API does not return the real token value via create at all — consistent with `terraform/netbox/provider.tf`'s existing note that the original bootstrap token needed a Django-shell mint because "the chart's `superuser.api_token` is NOT actually usable." Deleted the resulting orphan (id `71`, zero real secret ever existed for it) and rotated via the NetBox web UI's own token page instead, which does show the full value once on-screen.
12. **Semaphore API token** — matched leaked value's 8-char id prefix (`wgpkjuhy`) to the single existing token (name `TF`). This service's `POST /user/tokens` create response *does* return the real secret in full — confirmed by checking the returned value's length (44 chars, matching the original leaked token's length) before trusting it, rather than assuming NetBox's masking behavior generalized. Rotated cleanly via API.
13. **AdGuard admin password** — see dedicated section below; this was the long one.
14. Post-AdGuard, confirmed `adguardhome-sync.service` (which had been failing every cron cycle since the password mismatch began, since it authenticates as AGH's own admin account) was back to clean successful sync cycles.

### AdGuard admin password — detailed sequence

AGH has no API-token concept — the operator credential is a real login, with the password bcrypt-hashed and baked into each of the three nodes' own `/opt/AdGuardHome/AdGuardHome.yaml` by the `adguard` Ansible role.

1. Generated a new password + bcrypt hash (`htpasswd -bnBC 10 "" "<pw>" | tr -d ':\n'`, the role's own documented mint command), wrote both to Vault (`secret/ansible/adguard/admin-password-hash` for the role's config, `secret/ansible/adguardhome-sync/admin-password` for the sync tool's login) and to 1P, hash-verifying each write.
2. Ran `ansible-playbook ... asgard-adguard.yml --tags adguard,adguardhome-sync`. Play recap: `saga: changed=4`, `mimir: changed=0`, `kvasir: changed=0`. Login test against the (VIP-fronted) `$ADGUARD_HOST` returned `403 Forbidden`.
3. Diagnosed via `ansible/roles/adguard/tasks/config.yml`: the `AdGuardHome.yaml` render task is guarded `when: not adguard_config_stat.stat.exists or adguard_force_overwrite_config` — it **only renders if the file doesn't already exist**, specifically to preserve the live dynamic state (rewrites/filters/clients) that AGH itself writes back into that same file. Since all three nodes were long since bootstrapped, the render was silently skipped everywhere. The `changed=4` on saga was entirely from the `adguardhome-sync` role (which only runs on the primary) re-rendering *its own* config with the new plaintext — a password AGH itself didn't recognize yet, which is what the 403 actually was.
4. Deliberately rejected `adguard_force_overwrite_config: true` as the fix — it re-renders the *entire* file from a template that only captures listen/upstream/admin/retention, which would wipe the rewrites/filters/clients AGH has accumulated at runtime.
5. Went with a surgical fix instead: SSH to each node, back up the file, in-place-edit just the `password:` line, restart `AdGuardHome.service`. First attempt: `sed -i 's/^    password: .*/    password: "..."/'` failed with `sed: -e expression #1, char 67: unknown option to 's'` on all three nodes — the bcrypt hash (from `htpasswd -B`, alphabet `./0-9A-Za-z`) commonly contains literal `/` characters, which collided with `/` as the sed delimiter. Switched to `|` as the delimiter; all three then applied cleanly (verified via per-command `$status` checks after the first attempt's failure mode had gone undiagnosed silently).
6. Verification attempt #1 (`sed -n 's/^    password: "\(.*\)"/\1/p'`, assuming the value was quoted) returned nothing on all three nodes — SHA-256 of empty input. Verification attempt #2 (`awk -F'"'`, also assuming quoting) returned SHA-256 of a bare newline — confirmed AGH's own YAML writer stores the value **unquoted** (it re-serializes the whole file on every state change, and Go's YAML marshaller doesn't quote a plain scalar that doesn't need it), unlike the original Jinja template which always quoted it. Fixed with a prefix-strip (`grep '^    password:' | sed 's/^    password: //'`) that doesn't assume quoting either way.
7. That verification then showed all three nodes reporting an *identical* hash — but one that didn't match Vault's stored hash. This looked like a failure but wasn't: **bcrypt salts randomly per invocation**, so two independent `htpasswd` runs of the identical password will essentially never produce byte-identical hash strings. Comparing "does the file's hash equal Vault's hash" was the wrong test entirely for a salted-hash field (unlike AppRole secret_ids or plain API tokens, which *are* deterministic strings and where hash-comparison is the correct verify pattern). The actual ground truth is whether the password logs in — which it did (`200 OK` on all three nodes directly, plus the end-to-end `smoketest.niflheim.xiiisins.com` check). Re-synced Vault's stored hash to match what was now actually live (rather than assuming the original 1P/Vault-written hash was "the correct one" and the file was wrong), so a future rebuild seeds the right value.

## Findings (encoded as gotchas)

1. **Root cause of the `__homelab_cache_write` value-dump not established** — ruled out persistent `xtrace`, `SHELLOPTS`/`BASH_ENV`/`ENV`, and any explicit print statement in `homelab.sh`. Mitigation going forward, regardless of cause: never `cat`/display the raw output of `homelab-env`, `vault-homelab-env`, or `set-vault-token` — redirect fully to a file or `/dev/null` and verify success only via hash-only, length-only, or exit-code checks. → `known-issues/shell-tooling.md`.
2. **The Bash tool's permission classifier blocking Claude from running credential-mutating scripts directly was correct, not a limitation to route around** — it forced every rotation through owner-executed commands with hash-verify-not-print discipline, which is the same shape `rotate-approle`/`rotate-vault-root-token` already use for exactly this reason.
3. **A narrowly-scoped IAM identity cannot rotate its own access keys, even when it "owns" them conceptually** — `terraform-state`'s policy is deliberately S3-only. A Terraform-managed access key rotates via `-replace` using the identity that originally created the resource (here, `bootstrap`), never via ad-hoc `aws iam` calls against the narrow one. → new finding, no existing file section; folded into this doc only (low general-applicability outside this specific IAM design).
4. **"The Cloudflare token" is mirrored to three independently-writable stores with no automatic sync** — 1P (TF provider auth) + `secret/k8s/cert-manager/cloudflare` (cert-manager DNS-01, via ESO) + `secret/ansible/cloudflare/api-token` (Ansible/Semaphore self-verify). Rotating in Cloudflare's dashboard or in 1P alone leaves the other two stale. → `known-issues/cloudflare.md` (not added this pass — folded into this doc; add if it recurs).
5. **This NetBox deployment's `/api/users/tokens/` create endpoint does not return the real secret** — the `key` field in the create response is the same masked ~12-char display prefix as list responses show, not the actual token. Matches the pre-existing `terraform/netbox/provider.tf` note that the bootstrap token needed a Django-shell mint for the same reason. **Rotate NetBox admin tokens via the web UI**, not the API.
6. **Semaphore's `/user/tokens` create endpoint DOES return the real secret in full** — don't assume two similar-looking token-management APIs behave the same; check the returned value's length before trusting it as the real credential (the length check is what caught NetBox's masking before it caused a second false "it's rotated" close-out).
7. **`adguard` role's config render is guarded to skip an already-existing file, by design** — protects AGH's own live-written dynamic state (rewrites/filters/clients), but means a plain role re-run is a silent no-op for a password rotation on an already-bootstrapped node. → `known-issues/dns-adguard.md`.
8. **`sed` delimiter must avoid characters present in the replacement text's charset** — bcrypt hashes (alphabet `./0-9A-Za-z`) commonly contain `/`; using `/` as the `s///` delimiter breaks the parse (`unknown option to 's'`) whenever the generated hash happens to contain one. Use a delimiter guaranteed absent from the value (`|`, `~`, etc.), not just "looks fine in review" (a hash with no `/` would have worked and hidden the bug until the next rotation). → `known-issues/dns-adguard.md`.
9. **Comparing two bcrypt hashes of the same password is never a valid "did this write succeed" check** — bcrypt salts randomly per invocation, so independently-generated hashes of an identical password essentially never match byte-for-byte. Verify by testing the actual credential (login), not by hash-comparing. This is the opposite of the correct pattern for deterministic secrets (AppRole secret_ids, plain API tokens), where hash-comparison *is* the right verify method — the distinction is whether the stored value is a salted hash or the literal credential. → `known-issues/dns-adguard.md`.
