# Known gotchas — Frigg / control-node watchtower

*Migrated from `CLAUDE.md`. Recovery commands + rules. Incident retros in [`../incidents/`](../incidents/).*

## Frigg / control-node watchtower (Phase 6 Stage 2)

- **Running any playbook FROM the macOS MacBook crashes its forked task workers — `[ERROR]: A worker was found in a dead state` (SIGSEGV).** The real root cause (fully diagnosed 2026-07-04, real-`ansible-playbook` only — earlier theories below were wrong): **macOS CoreFoundation is not fork-safe.** Once the *main* ansible process has done *any* HTTP, macOS has initialized fork-unsafe CF state (proxy auto-detection via `_scproxy`→`SCDynamicStoreCopyProxies`, `Network.framework` path evaluation, and `os_log`→`CFPreferences` — confirmed in the crash backtraces from `~/Library/Logs/DiagnosticReports/Python-*.ips`). The forked task worker inherits that poisoned state and segfaults the instant *it* touches the network. **The trigger on our Mac is the NetBox dynamic inventory** (`netbox.netbox.nb_inventory`), which makes threaded HTTPS calls to NetBox in the *main* process at startup (wired into `ansible.cfg` `inventory=` in Phase 5h.3). The `community.hashi_vault` lookup is just the fork *victim*, not the cause — with a **static** inventory it succeeds 10/10 (the lookup runs in the child, and a child-first HTTP call with a clean parent is fine). **Empirically ruled out, real ansible, 10 runs each (all 10/10 crash):** Python version (3.13.14 ≡ 3.14.6), ansible-core version (a fresh venv of the *same* 2.20.6 **without** the NetBox collection is clean — proving it's the inventory doing HTTP, not the core), `netbox.netbox` plugin version (its fetch has been threaded HTTP since 1.0.0 — all versions crash), TLS-vs-plaintext & IP-vs-FQDN `VAULT_ADDR`, `OBJC_DISABLE_INITIALIZE_FORK_SAFETY=YES` (only suppresses the *objc-init* SIGABRT, not this CFPreferences SIGSEGV), and `no_proxy='*'`. The only variable that flips it: the inventory (`static hosts.yml` → 0/10 crash, 10/10 success; live NetBox → 10/10 crash).
  - **Why `no_proxy='*'`/`OBJC_DISABLE…` are the *documented* fix elsewhere but not here:** those upstream reports (community.hashi_vault #380, amazon.aws #1339, ansible/ansible #76631) are **lookup-only** setups with a *static* inventory, where the crash is the *child lookup's own* proxy detection and `no_proxy` stops it. Our crash comes from the *parent's* dynamic-inventory HTTP, which no child-side env var can undo. Don't chase env vars for this case.
  - **Fix (live in the shim, macOS-only): warm a static NetBox inventory cache before playbooks run.** `.config/scripts/refresh-netbox-inventory-cache.sh` materializes the NetBox inventory to `ansible/inventory/.netbox-cache.yml` **in a short-lived separate process** (it does the HTTP + exits — never forks playbook workers, so it can't crash) and the shim (`homelab-env` / `vault-homelab-env`, both dialects) exports `ANSIBLE_INVENTORY` at it. Playbook runs then do **zero HTTP in the forking process** → no crash. Refreshed on every shim (re)fetch; force with `refresh-netbox-inventory`. **Leak-safe:** the materialize copies only `netbox.yml`+`hosts.yml` into a tempdir with no adjacent `group_vars/`, so `--list` can't merge the ansible-vault `vault.yml` into the cache (verified: only 22 NetBox-metadata hostvar keys, zero secrets). `group_vars/` (incl. `vault.yml`) re-merge in-memory at playbook time because the cache lives in `inventory/`. The cache is git-ignored. Validated 2026-07-04: NetBox-host target + `community.hashi_vault` lookup in a forked worker + `group_vars`/`vault.yml` → **0/10 crash, 10/10 success**. **Linux controllers (Frigg/Semaphore) are immune** (glibc fork + no CoreFoundation) and keep using the live NetBox dynamic inventory — the shim's `refresh` is a no-op off macOS.
  - **Fix pattern still used by the `control-node` role's OWN provisioning** (shim env not loaded yet): fetch the secret ON the target via the vault CLI + the box's own AppRole (a `shell` task: source `/etc/frigg/vault-approle.env` → `vault write -field=token auth/approle/login …` → `vault kv get`), NOT a controller-side `lookup('community.hashi_vault…')`. `control-node`'s `repo.yml` + `claude.yml` do this. Roles using the controller lookup (`tailscale`, `vlagent`, `zabbix-agent`, **`postgres-common`**) now run fine from the **MacBook** (warm-cache fix above) **or** a **Linux** controller. (Frigg became usable for *remote* hosts on 2026-06-01 when the shim started materializing the ansible SSH key — see below.)
- **Frigg's env shim is `/usr/local/bin/homelab-env` (bash), NOT the MacBook's fish `vault-homelab-env`.** Same public name `homelab-env`, Vault-backed (the `ansible-frigg` AppRole) instead of 1P. Secret-zero is `/etc/frigg/vault-approle.env` (root:root 0600, RoleID + SecretID). `/etc/profile.d/homelab-env.sh` auto-sources it **only for interactive login shells** (`[ -n "$PS1" ]` guard) — a non-interactive `sudo -u ghost bash -c …` / `bash -s` does NOT get the env. To use it non-interactively: `. /usr/local/bin/homelab-env && homelab-env` explicitly. **Never pipe the function** (`homelab-env | tail`) — the pipe runs it in a subshell so its `export`s never reach the caller (the generic "pipe-induced subshell hides env exports" gotcha; this cost a wrong *"Frigg is broken / has no shim"* diagnosis on 2026-06-01 — the shim was fine, the probe was checking the Mac-fish names `vault-homelab-env` + `~/.config/ansible/vault-approle.env`, which don't exist on Frigg, AND piping the function so its exports vanished). When probing Frigg, look for `/usr/local/bin/homelab-env` + `/etc/frigg/vault-approle.env`, not the fish paths; Frigg has no `fish` installed.
- **The `homelab-env` shim materializes the ansible SSH private key so `ansible-playbook` ON Frigg can SSH to the fleet (added 2026-06-01).** Previously the shim exported `VAULT_TOKEN` / `ANSIBLE_VAULT_PASSWORD_FILE` / `ANSIBLE_HASHI_VAULT_*` / `KUBECONFIG` but **not** an SSH key → `ansible@<host>: Permission denied (publickey)`, so Frigg couldn't run any *remote* role. It now also writes `secret/ansible/frigg/ssh-private-key` → `~ghost/.ssh/ansible_homelab` (0600) + exports `ANSIBLE_PRIVATE_KEY_FILE` (which `ansible.cfg` deliberately leaves unset so it comes from the env, same as the MacBook). The key is **operator-placed**, NOT a TF resource: it's the existing shared `ansible_niflheim` key whose public half is already in every host's `ansible` `authorized_keys` — a fresh `tls_private_key` wouldn't be authorized anywhere. Stored once with `vault kv put secret/ansible/frigg/ssh-private-key value=@~/.ssh/ansible_niflheim` (documented in `terraform/vault/frigg.tf`; covered by the `homelab-frigg` `secret/data/*` read policy, no policy change). The shim uses `printf '%s\n'` to re-add the trailing newline that command-substitution strips — OpenSSH rejects a key file with no final newline (`invalid format`). **Redeploy the shim after a template change from the MacBook** with `ansible-playbook playbooks/asgard-control.yml --limit frigg --tags control-node:vault-env` — `vault-env.yml` is template/file/copy only (no `community.hashi_vault` lookup), so it runs from the Mac WITHOUT the Python-3.14 fork crash (unlike a full converge). A future Frigg-*specific* keypair distributed via the `baseline` role would supersede the shared key, but is deferred (chicken/egg: distributing it needs a fleet-wide `baseline` run, which needs a working controller).
- **Operational — running a remote-host role from Frigg** (the controller path for any `community.hashi_vault`-lookup role the MacBook can't run): `ssh ansible@frigg.niflheim.xiiisins.com` → `sudo -iu ghost` → `. /usr/local/bin/homelab-env && homelab-env` (loads the env incl. `ANSIBLE_PRIVATE_KEY_FILE`; **no pipe**) → `cd ~/homelab/ansible && git pull --ff-only` → `ansible-playbook …`. Validated 2026-06-01 running `postgres-common --limit vor --tags postgres-common` to create the n8n DB. The **one-playbook-at-a-time** fleet rule still applies — don't run a Frigg playbook concurrently with a MacBook one.
- **A Proxmox VM created with `agent { enabled = false }` has NO QEMU guest-agent virtio-serial channel, so `qemu-guest-agent.service` can't start** (`A dependency job for qemu-guest-agent.service failed`). bpg blocks at *create* waiting for the agent on images lacking it (Debian genericcloud), which is why Frigg was created agent=false. **Fix:** after create, `qm set <vmid> --agent enabled=1` + a power-cycle (`qm reboot` = fresh QEMU) materializes the channel; then `qemu-guest-agent` starts. Reconcile the TF config to `agent { enabled = true }` afterward (in-place, no reboot) so config matches reality + Proxmox gets graceful HA shutdown.
- **`claude remote-control` requires a FULL-SCOPE interactive `claude auth login`, NOT a `setup-token` / `CLAUDE_CODE_OAUTH_TOKEN`** (those are inference-only → RC rejects them: "Remote Control requires a full-scope login"). An inference token in the service env *overrides* the login and breaks RC — keep it out of the unit. Two further one-time interactive gates a headless systemd service can't answer: **workspace trust** (`projects."<dir>".hasTrustDialogAccepted` in `~/.claude.json`) and **the RC enable consent** (`remoteDialogSeen`, top-level in `~/.claude.json`). The `control-node` role seeds both (idempotent JSON patch, run as the operator user, once `~/.claude.json` exists from the login) so a rebuild only needs the interactive `claude auth login`. Unit runs `claude remote-control --spawn worktree`, gated to start only once `~ghost/.claude/.credentials.json` exists.
- **The `tailscale` role with the default `accept-dns=true` HIJACKS a control node's `/etc/resolv.conf` → DNS-loss-on-reboot footgun.** Frigg's resolv.conf is baseline-owned (AdGuard VIP `10.0.10.200`, `baseline_manage_resolv_conf` default true), but `tailscale up` (accept-dns defaults true) overwrote it with MagicDNS (`100.100.100.100`/`fd7a:115c:a1e0::53`). It worked initially, then **after an HA reboot the tailnet split-DNS path to AdGuard returned `server misbehaving`** → `vault.niflheim.xiiisins.com` unresolvable → `homelab-env` AppRole login failed → the **entire IaC toolchain was down**. A LAN control node must keep DNS on the direct AdGuard path, independent of tailscaled. **Fix:** `tailscale_accept_dns: false` (set in `group_vars/control.yml`; the role passes `--accept-dns={{ tailscale_accept_dns | default(true) | lower }}` — default true so the tailnet LXCs, which deliberately live on MagicDNS with `baseline_manage_resolv_conf=false`, are unchanged). **Live-fix without a Vault dependency** (chicken-egg: re-running `tailscale up` needs the authkey from the now-unresolvable Vault): `sudo tailscale set --accept-dns=false` flips the pref on the connected node — but it does NOT restore resolv.conf, so also rewrite `/etc/resolv.conf` to the baseline content (AdGuard VIP + UCG fallback + `search niflheim.xiiisins.com`). The pref persists in `tailscaled.state`; reboot-test (`tailscale debug prefs` → `CorpDNS:false`, resolv.conf intact). Surfaced 2026-05-31 finishing Stage 2 — the HA crash-test reboot is what exposed it.
- **`qm stop <vmid>` on an HA-managed resource is a GRACEFUL HA stop (desired-state → `stopped`), NOT a crash — HA will NOT auto-restart it.** The CLI prints "Requesting HA stop for VM N"; `ha-manager status` then shows `(node, stopped)` steady and the VM stays down until you `ha-manager set vm:<id> --state started`. To actually test HA crash-recovery (without killing a node), **`kill -9 $(cat /var/run/qemu-server/<vmid>.pid)`** on the hosting node — the qemu process dies while desired-state stays `started`, so the LRM detects the discrepancy and auto-restarts within ~6s (validated on vm:2900 2026-05-31). Live migration of an HA VM is `ha-manager migrate vm:<id> <node>` (NOT `qm migrate`); with the disk on shared NFS it's a RAM-only live-migrate = zero downtime.
- **Frigg commits with a DISTINCT, repo-LOCAL git identity (`Frigg <frigg@niflheim.xiiisins.com>`) so its commits don't masquerade as the operator's MacBook** (which commits as `XIIISins <xiii@xiiisins.com>`). Set by the `control-node` role's `repo.yml` (`community.general.git_config`, `scope: local`, `repo: ~ghost/homelab`) as a post-clone step — **local scope, not global**, so it only stamps Frigg's homelab checkout and can't bleed onto any other repo `ghost` touches. The `.git/config` it writes lives in the checkout's **common** git dir, so `--spawn worktree` worktrees inherit it automatically (no per-worktree config needed). The `frigg@` email is intentionally **not** registered to the GitHub account — commits land as a plain unlinked "Frigg" author rather than an avatar'd impersonation of the operator. Because `.git/config` isn't tracked, a fresh clone re-inherits the committed `XIIISins` identity until the role's git_config task runs; to set it live without a full converge: `git -C ~ghost/homelab config --local user.name Frigg && git -C ~ghost/homelab config --local user.email frigg@niflheim.xiiisins.com` (or `ansible-playbook playbooks/asgard-control.yml --limit frigg --tags control-node:repo`). Identity strings are `control_node_git_user_{name,email}` in the role defaults.
- **NetBox dynamic inventory on Frigg needs `python3-pytz` + `python3-pynetbox` (apt).** Without them `netbox.netbox.nb_inventory` fails to parse (`pytz must be installed`) and Frigg silently falls back to needing `-i inventory/hosts.yml` (the static DR inventory — which is fine for a `--limit <host>` run, and where `frigg` lives under group `control`). Now installed by the `control-node` toolchain (same apt pattern as `python3-hvac`; Debian 13 is PEP668 so apt, not pip). Same class as the Semaphore pod-start `pip install pytz`. A brand-new Zabbix host class (Frigg → `Asgard/Control`) also needs its host group created first — `ansible-playbook playbooks/zabbix-host-groups.yml --limit frigg` aggregates+creates it before `zabbix-agent` registration succeeds.
- **`terraform apply` from Frigg against any Vault-touching module fails with `permission denied` on `/v1/auth/token/create` until the `homelab-frigg` policy grants it (added 2026-06-20).** The Terraform Vault provider's *default* mode mints a short-lived **child token** per run (lease isolation + end-of-run revoke); that call needs `create` on `auth/token/create`. The original `homelab-frigg` policy deliberately had **no `auth/*` path at all**, so the provider died at child-token creation before touching a single resource — blocking the entire IaC cycle from the watchtower (surfaced 2026-06-20 finishing the Vault listener-TLS migration: every module except `terraform/vault`/`terraform/aws` is supposed to run from Frigg, but none could). **Misdiagnosis to avoid:** this is NOT a near-root boundary being correctly enforced — `auth/token/create` mints **child** tokens only, which inherit a *subset* of `homelab-frigg` (cannot add policies Frigg lacks, cannot reach `sys/*`) and die when Frigg's ≤1h parent token (`token_max_ttl = 3600`) expires. Orphan/periodic/long-TTL tokens need `sudo` (`auth/token/create-orphan`, the `period` field) and stay ungranted. The real boundary — `sys/*` (auth methods/policies/mounts) + `terraform/vault`/`terraform/aws` staying MacBook+root — is untouched. **Two clean fixes existed; chose the policy grant over `skip_child_token = true` on the provider** because the grant leaves the MacBook+root path *identical* (both control nodes now run the provider in its documented default mode — no per-module `provider.tf` edits, no behavioural divergence), whereas an unconditional `skip_child_token` would have changed root runs to use the root token directly (losing the ephemeral-child wrap). **Fix:** `path "auth/token/create" { capabilities = ["create", "update"] }` in the `homelab-frigg` policy (`terraform/vault/frigg.tf`). **Apply from MacBook+root** — `terraform/vault` is Vault self-config and stays a MacBook operation by design; Frigg cannot re-wire its own auth model (that's the whole point). After the apply, Frigg's next `terraform apply` against `terraform/semaphore` (and every other Vault module) just works, no re-login needed.
- **Drift-check reports a perpetual `changed=1` on frigg's `control-node : Add github.com to operator known_hosts` whenever only ed25519 is pinned — benign OpenSSH host-key auto-learning, NOT a compromise (fixed 2026-06-21 by pinning all of GitHub's keys).** The `copy:`-pinned `~ghost/.ssh/known_hosts` (`roles/control-node/tasks/repo.yml`, content = `control_node_github_known_hosts`) owns the whole file. OpenSSH's `UpdateHostKeys` (default `yes` since 8.5) learns the server's *other* host keys after a successful git op and appends them — **hashed** (`HashKnownHosts yes`, the Debian default → `|1|…` lines), so they don't match the unhashed pin → the `copy` task re-flags `changed` on every drift-check (6h cron). The appended keys are GitHub's real RSA + ECDSA host keys, not a MITM. **Fix = pin ALL of GitHub's published keys (ed25519 + ecdsa + rsa), not just ed25519**, so `UpdateHostKeys` (which matches by key *material*, not text form, so hashing is irrelevant) finds every advertised key already present and appends nothing → steady-state `changed=0`. `UpdateHostKeys no` would also stop it but only *masks* the mechanism and forgoes the rotation tripwire; pinning the full set is the correct posture. **Refresh recipe** (authoritative, over TLS): `curl -s https://api.github.com/meta | jq -r '.ssh_keys[] | "github.com " + .'` → cross-check fingerprints with `… | ssh-keygen -lf -` against GitHub's published *"SSH key fingerprints"* doc (ED25519 `SHA256:+DiY3wvvV6TuJJhbpZisF/zLDA0zPMSvHdkr4UvCOqU`, ECDSA `SHA256:p2QAMXNIC1TJYWeIOttrVc98/R1BUFWu3/LiyKgUfQM`, RSA `SHA256:uNiVztksCsDhcc0u9e8BujQXVUpKZIDTMczCvj3tD2s`) → paste into `control_node_github_known_hosts` (`roles/control-node/defaults/main.yml`). **A FUTURE `changed=1` here = GitHub actually rotated a host key** (they rotated the RSA key in 2023 after exposure) — verify the new key against the meta API + fingerprints doc *before* re-pinning, don't blindly accept it. Surfaced 2026-06-20 via the drift-check cron; fixed 2026-06-21.
- **Drift-check reported a *different* perpetual `changed=1` on the same known_hosts task — a foreign host (frigg's OWN key) landing in the operator file — because the whole-file `copy:` managed `~ghost/.ssh/known_hosts` as "github-only", but that file is ALSO the known_hosts for every SSH the `ghost` user makes from Frigg (fixed 2026-07-04 by pinning GitHub to a DEDICATED `known_hosts.github`).** Distinct from the gotcha above (that was `UpdateHostKeys` appending GitHub's *own* keys; this is a *non-GitHub* host). Root cause: running `ansible-playbook --limit frigg` FROM Frigg as ghost (the documented remote-role path) makes the controller's ssh process (running as ghost) connect to `10.0.11.30` — frigg's own `ansible_host` — and `accept-new`-learn frigg's host key (`SHA256:7jB/kOA2GHCO/LBrRyt0pJrViHLhFTToeAtQ6B5ZfHw` = `root@frigg`), **hashed** (`HashKnownHosts yes` → `|1|…`). The github-only whole-file `copy:` then perpetually flagged that legit entry for deletion on every 6h drift-check. Benign (frigg's own key, no MITM) but permanent noise — and any *other* host ghost legitimately SSHes to from Frigg does the same. **Fix = decouple the strict GitHub pin from ghost's general-purpose known_hosts:** the pin now writes to `~ghost/.ssh/known_hosts.github` (task renamed `Pin github.com host keys (dedicated known_hosts.github)`), and the `Host github.com` ssh-config stanza gets `UserKnownHostsFile ~ghost/.ssh/known_hosts.github` so git consults ONLY the pinned file (rotation tripwire from the gotcha above stays intact — a real GitHub rotation still surfaces as drift on the dedicated file). `~ghost/.ssh/known_hosts` is now **unmanaged** → self-SSH + fleet-host entries land there freely and no longer trigger drift. Both in `roles/control-node/tasks/repo.yml`. **Diagnostic if a known_hosts `changed=1` recurs:** unmask the hashed hostname with `ssh-keygen -F <candidate-host> -f <file>` (hashed entries only reveal on a hostname match) + fingerprint the key (`ssh-keygen -lf <file>`) — a `github.com`-fingerprint match on the *dedicated* file = real GitHub rotation; anything else on the *general* file is a benign learned host and should NOT be in a managed file. Surfaced + fixed 2026-07-04 via the drift-check investigation.
- **Drift-check reported a perpetual `changed=1` on `control-node : Render operator Claude settings.json` — the running `claude remote-control` service writes BACK to `~ghost/.claude/settings.json`, which a whole-file `template:` fully owned (fixed 2026-07-06 by moving the allow-list to Claude Code's enterprise managed-settings policy).** Same *class* as the two known_hosts gotchas above: Ansible fully managing a file that a **runtime process also mutates**. `~ghost/.claude/settings.json` is the one Claude Code settings file the CLI writes back to at runtime — it persisted `agentPushNotifEnabled` + `inputNeededNotifEnabled` (notif toggles flipped during a mobile remote-control session) and **reordered keys** (moved the `_comment` from top to bottom), none of which the template rendered → `changed=1` every 6h forever (benign noise). **Fix = deploy the allow-list as Claude Code's ENTERPRISE managed policy at `/etc/claude-code/managed-settings.json` (root:root 0644) and STOP managing the user file.** Managed settings are **highest-precedence and Claude Code never writes them**, and `permissions.allow`/`deny` **merge across layers** (users can extend but not weaken a managed list) → the conservative floor is intact while `~ghost/.claude/settings.json` is left free for the CLI's own runtime prefs. Role: `roles/control-node/tasks/claude.yml` renders `templates/claude-managed-settings.json.j2` (was `claude-settings.json.j2` → user file); path var `control_node_claude_managed_settings_path` in `defaults/main.yml`. Settings precedence (high→low): managed policy > CLI flags > `.claude/settings.local.json` > `.claude/settings.json` (project) > `~/.claude/settings.json` (user, the only one `claude` writes back). **Same fix pattern applies to any future Ansible-vs-runtime file fight** — don't `template:` a file a daemon rewrites; find the read-only policy/drop-in layer instead. Surfaced + fixed 2026-07-06 via the Semaphore drift-check.
