# Media automation (Sonarr, SABnzbd, Recyclarr) gotchas

Read before touching `k8s/asgard/apps/media/`. Service page: [`../services/media-automation.md`](../services/media-automation.md). The NFS permission model is in [`jellyfin.md`](jellyfin.md).

- **SABnzbd was OOM-killed at a 1 GiB limit with 20 connections (found 2026-10-08).** The article cache plus direct unpack and par2/unrar exceeded it; the pod crash-looped and left in-flight jobs with corrupted job folders (SABnzbd logged `__ADMIN__/SABnzbd_article_* missing`) that stayed `Paused` at 90 to 95 % and could not be resumed. Rule: `cache_limit = 256M`, memory limit 2 Gi. Recovery: remove the stuck jobs from SABnzbd and Sonarr with `removeFromClient=true`, no blocklist, and re-search the episodes.
- **The seeded `sabnzbd.ini` is only rendered when the file is missing,** so a changed default in the manifest does nothing on a running install. The init container therefore re-asserts `cache_limit`, `bandwidth_max`, `download_dir`, `direct_unpack` and `download_free` with `sed` on every start; add a key to its `setkey` list if the manifest must own it. macOS `sed -i` differs from busybox, so test that script in the cluster, not on the laptop.
- **Recyclarr 8 changed its environment and needs a writable config dir (found 2026-10-08).** `RECYCLARR_APP_DATA` is an error; use `RECYCLARR_CONFIG_DIR` (and optional `RECYCLARR_DATA_DIR`). A read-only config dir (a ConfigMap mount) fails with `Read-only ...` while activating the migration step, so the CronJob mounts an emptyDir at `/config` and the ConfigMap's `recyclarr.yml` on top via `subPath`. The profile block comes from `recyclarr/config-templates` (`sonarr/templates/anime-remux-1080p.yml`); `config create` is not needed.
- **Flux applies a merged fix minutes later: test a CronJob change only after `flux reconcile kustomization apps --with-source`** and a check that the CronJob spec has the new args, or a manual Job (`kubectl create job --from=cronjob/recyclarr ...`) runs the old spec and fails identically.
- **ameNZB's Newznab search is loose: about 620 results for every query, including other shows (found 2026-10-08).** Wrong-show releases (`The Amazing World of Gumball`, `The Copenhagen Test`, `GNOSIA`) appear for anime episodes. The profile's minimum custom-format score of 100 rejects almost all of them, but one `The.Copenhagen.Test.S01E07` was grabbed once. Watch the queue after a mass search; remove with `blocklist=true`. A search that returns 600 releases per episode is also slow (a 24-episode `MissingEpisodeSearch` took several minutes), so interactive `/release` calls need a long client timeout.
- **A single-episode release without an episode number is grabbed as a season pack (found 2026-10-08).** `[Bunny-Apocalypse] ... [BDRip 1080P ...]` was grabbed for all 12 S1 episodes, contained one episode (imported as S1E12) and left 11 phantom `completed / importPending` queue entries ("No files found are eligible for import"). Fix: delete the phantom entries with `blocklist=true&skipRedownload=true`, then run `EpisodeSearch` on the missing episodes by id.
- **Removing a queue item does not always start a re-search.** `DELETE /queue/{id}?removeFromClient=true&blocklist=false&skipRedownload=false` removed three stuck jobs but no search followed; run `POST /command {"name":"EpisodeSearch","episodeIds":[...]}` yourself. SubsPlease releases use absolute numbering (`- 07 (1080p)`), so filtering search results by `seasonNumber`/`episodeNumbers` hides them.
- **Sonarr tells Jellyfin about its own paths.** Sonarr sees `/data/Anime/...`, Jellyfin sees `/media/Anime/...`; without the Jellyfin connection's `mapFrom=/data`, `mapTo=/media` the update-library call is a no-op and Jellyfin shows 0 episodes until a manual scan. (Real-time monitoring is off on purpose.)
- **Pods may not resolve `*.niflheim.xiiisins.com` names that point at LXCs (found 2026-10-08).** `jellyfin-direct.niflheim.xiiisins.com` resolved when the Jellyfin connection was created and later failed in the same pod (`Name does not resolve`). Use the container IP (`10.0.11.223`) in Sonarr's connection; the cluster-internal names (`sabnzbd.media.svc.cluster.local`) are fine. Root cause not chased (CoreDNS forwarding of the `niflheim` zone; see the coredns-custom gotcha in [`dns-adguard.md`](dns-adguard.md)).
- **Sonarr keeps indexers, download client and notifications in its database.** None of that is restored by Recyclarr or by the seeded API key; a lost `sonarr-config` volume means re-adding them (keys from Vault).
- **FrugalUsenet connection limits:** the primary allows up to 50 connections (10 to 20 recommended), the `bonus` server 50 separately and 1.5 TB per month on their side; use SSL port 563.
- **The `linuxserver` images start as root and drop to `PUID`/`PGID`**, so the pods do not set `runAsNonRoot`; the NFS rule maps every uid to the DSM `admin` anyway. `kubectl exec` therefore shows uid 0.
- **CI's image check cannot resolve `lscr.io`** (HTTP 401): pull the same images from `ghcr.io/linuxserver/...`. It also rate-limits (HTTP 429) when queried repeatedly; re-run it later.
- **SABnzbd never repaired or unpacked anything, so 18 of 24 imported episodes contain zero-filled holes (found 2026-10-10).** The seed script wrote the default and `anime` categories without a `pp`, which SABnzbd treats as "download only": every job ran `Repair:False, Unpack:False` and the history has no verify or repair stage, although the NZBs carry 8-16 par2 files each. Missing articles become zero-filled holes in the assembled file; SABnzbd still reports the job `Completed` with every byte downloaded, Sonarr imports it, and Jellyfin direct-plays it until the first hole. Signature: runs of exactly 716,800 bytes (700 KiB, one article) of `0x00`; ffmpeg reports `0x00 at pos N invalid as first byte of an EBML number`; playback stalls at the first hole (first hole at 74 s for S01E02, so "stops after about a minute"). **Check a file:** its CRC32 against the `[XXXXXXXX]` in the release name (Sonarr's `sceneName`; SubsPlease releases carry it), and a scan for `\x00` runs of 4 KiB or more (24 files take ~20 minutes over NFS). **Fix:** `pp = 3` (repair + unpack + delete) in both categories, seeded on first render and enforced on every start by `setcatpp` in the init container (the ini is otherwise only rendered once). Fixing the setting does not repair files already imported, and whether par2 can repair a given release depends on how many recovery blocks it carries (a file with 340 missing articles may not be repairable). Open work: [`open-questions.md`](../operations/open-questions.md).
- **Outcome of the SABnzbd repair fix, 2026-10-10 (#258).** With `pp = 3` the same SubsPlease NZB for S01E02 that had imported with 12 holes was re-downloaded: SABnzbd's quick-check failed, `par2` repaired it in 53 s, and the imported file's CRC32 equals the published `360B6C0D` with zero holes. All 18 damaged episodes were then replaced one at a time; the final scan of all 24 files shows no holes and, for the 13 with a CRC in the release name, an exact match. **A release that cannot be repaired now fails instead of importing garbage** ("Repair failed, not enough repair blocks (N short)", or "Aborted, cannot be completed"), which happened for 12 of the first-choice posts (7 to 575 blocks short). Season 1 SubsPlease posts failed for S01E07 (202 short) and S01E09 (7 short); both ended as clean 720p SubsPlease copies, and S02E09 as a 732 MB x265 WEBRip. Season 2 has 10-20 independent posts per episode (VARYG, ToonsHub, AnoZu, others), so a failed first choice was replaced by a later post within 1-3 attempts. The damaged originals were moved to `/data/_quarantine/` (outside Jellyfin's library) while the replacements were verified, then deleted (22 GB, 18 files, 2026-10-10).
- **Sonarr's automatic re-download of a failed download can import the wrong thing (found 2026-10-10).** `autoRedownloadFailed` grabbed `[Chihiro] ... Season 2 - 07 [1080p HEVC]` for S01E07 and `... Season 2 - 09` for S01E09: releases of a different season matched by absolute numbering. Both failed repair this time; one that repaired cleanly would have been imported as the wrong episode. It also silently downgrades to 720p when the 1080p post is unrepairable. When replacing files in bulk, turn `autoRedownloadFailed` and `autoRedownloadFailedFromInteractiveSearch` off (`PUT /api/v3/config/downloadclient/<id>`), grab chosen releases explicitly, and turn them back on afterwards.
- **Replacing a file needs the old one out of the way first.** Sonarr rejects every release with "Existing file on disk has a equal or higher Custom Format score" while a file exists, and the recycle bin is unset (deletes are permanent). The working order: move the damaged file to `/data/_quarantine/`, `DELETE /api/v3/episodefile/<id>`, then list `release?episodeId=` and grab. Release URLs from that API embed the indexer API key: never print them.
- **SABnzbd held ~33 MB/s of a 1 Gbit line because the DS223J's NFS write path was the bottleneck, not a SABnzbd setting (found 2026-10-11).** `bandwidth_max = 50M` (50 MB/s, ~400 Mbit/s) was never reached: 30 connections were active, the pod used ~130m of its 1 CPU limit and was barely throttled, iowait was ~20%, and a 1 GiB `dd` to `/data` during the download wrote 47.8 MB/s (570 MB/s to the local `/config` disk). Articles, direct unpack and the moves all hit the one NAS over NFS. Fix: `incomplete/` on the node-local `local-path-scratch` PVC `sabnzbd-incomplete`, `direct_unpack = 0` so SABnzbd unpacks only when a job is complete, and `download_free = 10G`. **Two limits remain:** `bandwidth_max = 50M` now becomes the binding cap (raise it deliberately), and the unpack of a finished job still writes its result to NFS. Jobs queued before the change keep their old `download_path` on the share and finish there; only new jobs use `/incomplete`.
- **If `/scratch` is not mounted on the worker, local-path creates the volume directory on the root disk.** The role mounts with `nofail`, so a failed mount does not stop boot; the PVC then provisions into an empty `/scratch` directory on the 30 GB root filesystem. `download_free = 10G` pauses SABnzbd before the root disk fills, but check `findmnt /scratch` on the worker if downloads pause with free space apparently available.
- **SABnzbd is OOM-killed by NFS writeback, not by its own memory (found 2026-10-11).** The kernel's cgroup report at each kill showed `anon` ~170 MB but `file` ~1.9 GB of which `file_writeback` was **1.28 GB**: pages being written to the NFS share cannot be reclaimed until the DS223J (~48 MB/s) has taken them, so a finished 1.3-1.5 GB episode that is copied or unpacked to `/data` faster than that fills the limit, and the kernel kills the whole container (`memory.oom.group=1`). Earlier the same day it killed only SABnzbd's Python process (s6 respawned it inside the container, so the restart count did not move), which left job folders with `__ADMIN__/SABnzbd_nzf_* missing` and made the downloader crash with `Failure in tempfile.mkstemp` at 16:53: that was the "stuck" queue, not NFS flakiness. The rightsizing note about OOMs with a tiny peak is the same effect. **Diagnose:** `dmesg -T | grep -A30 'invoked oom-killer'` on the worker (look at `anon`, `file`, `file_writeback`), and watch `memory.stat` of the container while a job finishes. **Mitigation:** memory limit 4 Gi (a larger writeback backlog fits). **Not solved:** a file bigger than the limit minus the other memory still kills it; the systemic fix is to cap how much dirty and writeback data a node accumulates (`vm.dirty_bytes` and `vm.dirty_background_bytes` on the workers via the baseline role), which affects every NFS writer and needs its own reboot test.
- **"No video files were found in the selected folder" on a `completed / importBlocked` queue item means the NZB held no video (found 2026-10-12).** The Headpatter `Loner Life in Another World` S01E01 NZB (ameNZB, 195 days old) downloaded 820 MB in 32 s and SABnzbd marked it `Completed`, but the job folder held a single 897 MB `...vol01+02.par2` and nothing else (the log line `Detected filename from yenc or uu: ....mkv -> ....vol01+02.par2` is the tell). With no par2 index file there was nothing to verify or repair, so SABnzbd reported success; Sonarr then blocked the import ("matched to series by ID") and manual import found no video. It is the same dead-post family as the rest of that series' grabs: the other Headpatter and Freehold posts for E02-E12 failed with "not enough repair blocks (95 to 844 short)" or "Aborted, cannot be completed" within minutes. Not a mount or path problem: Sonarr and SABnzbd both see `/data/Downloads/complete/anime`, and the scratch `incomplete/` volume is not involved. **Diagnose:** `ls` the job folder from the sonarr pod and check SABnzbd's history stage log (`Download ... N articles were missing`, `Age: Nd`). **Fix:** `DELETE /api/v3/queue/<id>?removeFromClient=true&blocklist=true&skipRedownload=true` (also removes the folder), then pick a release from a different group, preferably a newer post. Posts older than ~6 months from this indexer are the likely casualties.
