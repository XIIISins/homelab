# Known gotchas — HAProxy / keepalived

*Migrated from `CLAUDE.md`. Recovery commands + rules. Incident retros in [`../incidents/`](../incidents/).*

## HAProxy / keepalived

- **VRID collision on shared L2 segment.** Two keepalived clusters on the same L2 (e.g. AGH VIP `10.0.10.200` + PG VIP `10.0.10.210`, both on VLAN 10 HL-ASG-VIP) MUST use different `virtual_router_id`. Same VRID → both receive each other's adverts, auth-fail (different `auth_pass`), log `received an invalid passwd from <peer>` continuously. Allocations as of 2026-05-24: AGH=51, PG=61. **Spacing convention: increment by 10** (next VRRP=71, ...). Allocate during design before deploying a new VIP; mid-flight fix is render + Ansible re-apply + brief re-election.
- **`systemctl kill` doesn't actually kill patroni — and patroni systemd unit ships `KillMode=process`.** Unit defaults to `KillSignal=SIGINT` + `Restart=on-failure`; SIGKILL via `systemctl kill -s SIGKILL` only catches the patroni main PID. PG runs as a child process tree that survives, and `Restart=on-failure` respawns patroni within `RestartSec`. To force an ungraceful crash for failover testing: `systemctl mask patroni && pkill -9 -f patroni; pkill -9 -f postgres` — then `systemctl unmask patroni && systemctl start patroni` to recover.
- **Patroni callbacks must ALWAYS exit 0.** The supervisor loop invokes `on_start` / `on_stop` / `on_restart` / `on_reload` / `on_role_change` callbacks synchronously; a non-zero exit can (depending on callback type + Patroni version) be interpreted as "callback execution failed" and hold up role transitions or trigger restart logic. For `on_role_change` the impact is bounded; for the others it's load-bearing. Rule: **any callback that touches external systems (notifications, log shippers, side-channel state) must catch + swallow failures and exit 0**, logging to a local file for forensics instead. Pattern in `roles/patroni/templates/hermod-callback.sh.j2`: every code path ends `exit 0`, including `curl-failed` branches; HTTP status + error context land in `/var/log/patroni-hermod.log` (PG-owned, mode 0640). Surfaced 5h.2.j.
- **Patroni 3.x+ renamed the `on_role_change` leader role from `master` to `primary`** (to align with PG 14+'s native terminology). Both names still appear in the wild: cold-start sometimes emits `master`, steady-state promotion on Patroni 4.x emits `primary`. A callback case statement matching only `master` silently drops the promotion-half notification on 4.x (`replica` and `standby_leader` are unchanged across versions, so demotion still delivers — masking the bug as "half the failover is missing"). **Fix pattern**: alternation in the case branch — `primary|master)` — covers both vocabularies. Verify against the actual cluster's Patroni version (`patroni --version`) when writing or reviewing role callbacks; assume future role-name shifts are possible and prefer alternation over single-name matches. Surfaced 2026-05-26 during 5h.2.j live-failover validation against Patroni 4.1.3.
- **VIP-on-secondary-NIC needs source-based policy routing.** Generalised in the keepalived role via `keepalived_source_policy_routing: [{name, table_id, from, gateway, interface}, ...]` — same class as the K3s workers' VLAN 20 fix (see "Networking / multi-homed workers"), N-entry-capable. Required whenever the VIP's L2 segment differs from the host's default route — without it, replies sourced from the VIP IP exit the default-route interface and stateful firewalls (UCG-Ultra) drop them.
- **Dual-NIC LXC for VRRP + service traffic.** HAProxy/etcd LXCs (Hlin/Eir/Snotra) carry eth0 on VLAN 11 (etcd peer + Patroni REST API + default gateway) + eth1 on VLAN 10 (VIP + VRRP). VRRP requires all peers L2-adjacent on the VIP's segment, so every node needs a real address on the VIP VLAN for advertisement source + diagnostics. Pattern reusable for any future VIP where the L2 segment differs from the service IP.
- **HAProxy `option httpchk` against Patroni REST API for leader detection.** `option httpchk GET /master HTTP/1.0` + `http-check expect status 200` — only the current Patroni leader returns 200 on `/master`; replicas return 503 → HAProxy marks them DOWN. With `balance first` + one-UP-at-a-time, routing is fully deterministic. `on-marked-down shutdown-sessions` (in `default-server`) forces clients to reconnect on demotion — without it, long-lived sessions stick to the deposed primary until they error out, defeating failover transparency.
- **keepalived all-BACKUP election (no static MASTER).** All instances set `state: BACKUP`; election by `priority` only. Avoids dual-MASTER when interfaces come up out of order on simultaneous boot (a static MASTER would announce itself authoritatively before noticing the other peer also announcing).
- **HAProxy + keepalived generic roles — data-driven via list-of-dicts.** `haproxy_listens` and `keepalived_vrrp_instances` are caller-supplied per group; the roles themselves are backend-agnostic and reusable. Adding a new VIP/backend is a group_vars edit, not a role fork. Roles live at `ansible/roles/{haproxy,keepalived}/`; PG-specific config at `ansible/inventory/group_vars/haproxy_etcd_hosts.yml`.
- **DB (`mode tcp`) listeners need a long idle `timeout` — the role's 50s default reaps pooled PG connections.** The `haproxy` role's `defaults` block sets `timeout client/server 50s` (correct for HTTP/stats); a PG listener that inherits it silently closes any connection idle >50s. Symptom: pooled/persistent clients (psycopg pools, and Authentik's `django_channels_postgres` LISTEN connection most visibly) log `OperationalError('… SSL SYSCALL error: EOF detected')` / "Postgres connection is not healthy" on next reuse — benign (auto-reconnect, readiness green) but ~5.5k reconnects/day + log noise, and broader than any one app. **Diagnostic:** HAProxy log termination flag **`cD`** (client-timeout-during-data) with `Tt≈50000ms` is the idle reap; **zero backend DOWN/UP events** distinguishes it from `on-marked-down shutdown-sessions`/failover. Count via `awk '/ cD /&&/pg_write\//' /var/log/haproxy.log`; the timer is field `$8` (`Tw/Tc/Tt`) once you strip the rsyslog prefix. **Fix:** `timeout client 30m` + `timeout server 30m` + `option tcpka` scoped to the listener (the listener's `extra:`/`options:` keys, NOT the role default → stats stays 50s), matching the upstream Patroni HAProxy reference. Surfaced 2026-05-31 Wave S7.
- **A `haproxy.cfg` change reaches disk but is NOT live until HAProxy reloads — and the reload can silently be skipped, then never re-fire.** The role's config template notifies `reload haproxy` (graceful `systemctl reload`: master stays up, sessions drain on the old worker → no VIP flap, no dropped conns; existing idle conns keep the OLD timeout until they recycle onto the new worker). But a deploy run can write the validated config while the running process keeps the old one — and because the file is then unchanged, **re-running the playbook reports `ok` and never re-notifies**, so it stays stale indefinitely. **Diagnostic:** compare `stat -c %y /etc/haproxy/haproxy.cfg` against the worker start time (`ps -eo lstart,cmd | grep '[h]aproxy '`) — if the worker predates the config mtime, the change isn't live; cross-check that connections *accepted after* the reload aren't still hitting the old behaviour. **Recovery:** reload out-of-band — `ansible <group> -b -m ansible.builtin.systemd -a "name=haproxy state=reloaded"` (do all trio members so a failover doesn't land on a stale node — non-VIP-holders carry no sessions, so it's free). **Root cause — the `--tags` suspicion is DISPROVEN** (tested 2026-05-31 Wave S3): a *notified* handler fires under `--tags <role>` regardless of the handler's own tags (a tagged task notifying an untagged handler runs the handler — confirmed with a minimal localhost play). So tag-filtering is NOT it; the most likely strand is a **handler notified but never flushed** — Ansible flushes handlers at *play end* by default, so a later task failing (or an interrupt/SIGINT) between the config-render and play-end strands the notified `reload`, and the now-on-disk config means a clean re-run sees no change → never re-notifies. **Do NOT "fix" with `force_handlers: true` on `asgard-haproxy-etcd.yml`** — that play has no `serial:`, so forcing handlers on a failed play could fire `restart etcd` on all three DCS nodes at once (quorum loss). The robust fix is a **notify-independent self-heal**: a role task that compares the running process start time to the config mtime (the diagnostic above) and reloads if stale — idempotent, per-node, graceful. Tracked as a follow-up in open-questions. Surfaced 2026-05-31 Wave S7; investigated Wave S3.
