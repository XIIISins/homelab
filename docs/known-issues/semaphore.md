# Known gotchas — Semaphore (Ansible scheduler)

*Migrated from `CLAUDE.md`. Recovery commands + rules. Incident retros in [`../incidents/`](../incidents/).*

## Semaphore (Ansible scheduler, 5h.3)

- **DB backend is Postgres, NOT sqlite.** Initial drafts considered sqlite-on-PVC; pivoted to PG on the Patroni VIP `10.0.10.210:5432/semaphore` at deploy time for consistency with every other K3s consumer (Authentik / NetBox / Outline / Zabbix / Teamspeak) and to side-step the "pod restart into broken PVC" failure mode. The chart-side env var for SSL is `SEMAPHORE_DB_OPTIONS` as a JSON string (`'{"sslmode":"require"}'`) — the docs-documented `SEMAPHORE_DB_SSL_MODE` is silently dropped. Config-file shape uses `dialect: postgres` + a nested `postgres: { host, user, pass, name, options }` block, mounted from an ESO-rendered Secret.
- **Semaphore runs IMAGE-BUNDLED collections, NOT the `ansible/requirements.yml` pins — closed via a custom GHCR image (2026-06-10).** The stock `semaphoreui/semaphore:<ver>-ansible<ver>` image ships its own Galaxy collection set, and Semaphore **never runs `ansible-galaxy collection install`** — so the pins in `ansible/requirements.yml` (honored on the MacBook/Frigg, which galaxy-install them) **never reached the Semaphore runtime**. Every play silently ran on the bundle, which is OLDER across the board: community.zabbix **2.3.1 vs pinned 4.2.0**, community.postgresql **3.4.0 vs 4.2.0**, community.crypto **2.18.0 vs 3.2.1**, netbox.netbox 3.17.0 vs 3.22.0. The repo's vendored `ansible/collections/` is **gitignored** (`.gitignore:32`), so the Semaphore git checkout never carried them either. The 2.x↔4.x community.zabbix auth-model break is what surfaced it — the `zabbix-agent` `register-host` task uses the 4.x httpapi pattern (`ansible_connection: httpapi` + `ansible_zabbix_auth_key`), which **passed from Frigg (4.x) but FAILED from Semaphore (2.3.1)** with a `no_log`-censored error. **Diagnostic:** `kubectl exec -n semaphore semaphore-0 -- ansible-galaxy collection list | grep -iE '<collection>'` shows what's installed, but that does NOT tell you what a *task* resolves — `ansible-galaxy list` and a raw `python import` both bypass Ansible's collection finder. To see the version a task actually loads, query the finder: `python3 -c "from ansible import constants as C; from ansible.utils.collection_loader._collection_finder import _AnsibleCollectionFinder as F; F(paths=C.config.get_config_value('COLLECTIONS_PATHS'))._install(); import ansible_collections.community.zabbix.plugins.modules.zabbix_host as m; print(m.__file__)"`. **Fix — install into the ansible venv's site-packages, NOT `/usr/share` + an env var (that FAILED — see below):** custom image (`docker/semaphore/Dockerfile` → `ghcr.io/xiiisins/semaphore-homelab`, built by `.github/workflows/build-semaphore-image.yml`) installs the pinned collections with `--force` straight into `<ansible-venv>/site-packages/ansible_collections`, overwriting the stock bundle, + bakes the runtime pip deps (`hvac`/`psycopg2-binary`/`pytz`, formerly the pod-start `pip install`). **Why site-packages and not a configured path:** Semaphore runs tasks with the repo's `collections_path = collections` (an empty vendored dir) ansible.cfg AND builds the task subprocess env itself — it does **not** carry container env vars, so a pod-spec `ANSIBLE_COLLECTIONS_PATH` never reaches the task (verified: `kubectl exec` inherits it and resolves 4.2.0, but the actual task still ran 2.3.1 → r1 still failed). The ONLY channel that reaches the task is Ansible's import-based finder scanning `ansible_collections` on `sys.path` — i.e. the venv site-packages. That's also exactly how MacBook/Frigg resolve 4.2.0 (their ansible venv site-packages holds it). So matching the venv site-packages makes Semaphore identical to every other controller — no ansible.cfg edit, no env var. **Bump discipline:** when `ansible/requirements.yml` (or the base image) moves, bump `BASE_IMAGE` (Dockerfile) + `IMAGE_TAG` rN (workflow) + the StatefulSet image tag in one commit; the workflow only triggers on changes to the Dockerfile / requirements / workflow. **Generalisations:** (1) any controller that doesn't galaxy-install the pins runs on whatever its image bundles — the pin is only real where it's actually installed; (2) Semaphore task env ≠ pod env — config that must reach a task goes via the checkout's ansible.cfg, the Semaphore Environment object, or (for collections) the venv site-packages, never a pod-spec env var. (The earlier "pod-start `pip install` is the canonical pattern" note was wrong on collections: pip installs Python deps, NOT Galaxy collections.)
- **`enableServiceLinks: false` is mandatory on the Semaphore pod spec.** Semaphore reads env vars whose names collide with K8s' auto-injected service-link variables (e.g. `SEMAPHORE_PORT`). Without `enableServiceLinks: false`, K8s' `<SVC>_PORT=tcp://...` injection wins and Semaphore starts listening on garbage. The collision is silent — Semaphore parses the value as a port string and binds wherever it lands. Generalisable to any app whose env-var schema uses common prefixes; rule of thumb: any app with a `<NAME>_PORT` or `<NAME>_HOST` env var in its docs needs `enableServiceLinks: false` if it's deployed in a namespace that also has a Service named `<name>`.
- **`config.json` `vaults:` block nests credentials at `password.vault_key_id`.** Flat `vault_key_id` at the top level is silently ignored. Surfaced during Vault integration setup; one of three undocumented-schema findings discovered by chasing pod errors.
- **Vault env var is `ANSIBLE_HASHI_VAULT_ADDR`, NOT `ANSIBLE_HASHI_VAULT_URL`.** The community.hashi_vault collection reads `_ADDR`; `_URL` is a common misremember from VAULT_ADDR but isn't a real variable the collection looks for. No error — lookups just fail with `Vault not configured` or fall through to the default `http://127.0.0.1:8200`.
- **Vault password file goes via `ANSIBLE_VAULT_PASSWORD_FILE` env, not `ansible.cfg`.** Semaphore mounts the vault-pass into a per-job tmpdir; the path varies per template. Static `vault_password_file = /path/to/file` in `ansible.cfg` doesn't resolve. Set the env var at the project/template level, not in checked-in config.
- **Inventory cache MUST be emptyDir on the Synology DS223J trio, not iSCSI PVC.** The 11th iSCSI LUN claim hangs Pending against the LUN cap (CLAUDE.md "Synology DS223J iSCSI LUN cap"). Inventory cache is cache-class state: rebuild = one NetBox API round-trip on next pod start (~30s). Same mitigation as Outline Redis. Generalisable to any cache-class consumer when the trio is at LUN cap.
- **Inventory file must be isolated from `group_vars/`** to skip Ansible Vault decrypt at parse-time. `nb_inventory` walks `group_vars/` on every parse; if `group_vars/all/vault.yml` is present, the plugin tries to decrypt it for every invocation. Move `inventory/netbox.yml` to a parallel dir (`inventory/` separate from where `group_vars/` lives) so the plugin doesn't see the encrypted vars files. Surfaced 2026-05-27 — `04803eb fix(semaphore): isolate inventory file from group_vars to skip vault decrypt`.
- **NetBox-injected `tags` collides with Ansible play/task `tags` namespace.** Rename via `keyed_groups` to `netbox_tags`. Don't try to `nuke` the source `tags='[]'` to force the rename — kills `keyed_groups` entirely (no source data to key on). Let both co-exist with rename happening downstream. Surfaced 2026-05-27 — `3571d70` (rename) + `055599e` (revert the over-aggressive nuke).
- **NetBox dynamic-inventory silent-success on cold cache + transient 500** — see also CLAUDE.md "NetBox" section for the canonical three-layer defence. Within Semaphore specifically: the `refresh-netbox-inventory` template wipes + rebuilds the cache; if a consumer template fires between the wipe and the rebuild AND NetBox returns a transient 500, the plugin parses 0 hosts and ansible exits 0 → Semaphore reports `success` against a no-op run. Defence: (1) refresh-script retries on NetBox 500s; (2) cache TTL 24h > refresh cadence 4h so consumers hit warm cache in steady state; (3) `site.yml` preflight-asserts `groups['all'] | length >= 20` and fails loud if the inventory came back empty. Surfaced 2026-05-27 via task-27.
- **Inline `hosts.yml` host-vars are INVISIBLE to the NetBox dynamic inventory — per-host vars that both inventories need must live in `inventory/host_vars/<host>.yml`.** Semaphore runs `ansible-playbook -i inventory/netbox.yml`; the static `hosts.yml` is a *separate inventory source*, so any var defined inline under a host there (e.g. `bifrost: { tailscale_tag: subnet-router }`) does NOT reach a NetBox-inventory run. **`group_vars/` and `host_vars/` DO reach both** — Ansible loads them adjacent to the inventory *directory* regardless of which inventory source is active (this is why `group_vars/tailscale.yml` already worked under Semaphore). Symptom: a role works at original deploy (run from the static inventory) but fails from Semaphore with an undefined-var / empty-template error (`tailscale up --advertise-tags=tag:{{ tailscale_tag }}` → `tag:` → all 3 tailscale LXCs failed 2026-06-10). **Diagnostic:** `ansible-inventory -i inventory/netbox.yml --host <h> | grep <var>` (run in the Semaphore pod with the AppRole env) shows what the *NetBox* path actually resolves; compare to the static inventory. **Fix:** move the inline host-vars to `inventory/host_vars/<host>.yml` (config like tailscale tags/routes belongs in Git/host_vars, not NetBox custom fields — IPAM-vs-config split). **General rule:** never put per-host config inline in `hosts.yml`; `hosts.yml` host entries should carry only `ansible_host` (the static DR connection info). Surfaced 2026-06-10.
- **Drift-check template wraps `ansible-playbook` with `--check` preflight assertion.** Belt-and-suspenders against accidental `--check`-less re-run of the same template (would mutate the fleet on a 6h cron). The wrapper script asserts both: (a) `--check` is on the argv, (b) `ansible_check_mode == true` at play-start (catches the "what if the operator subclassed the template and dropped --check by accident" case). Surfaced 2026-05-27 — `05762d3 fix(drift-check): self-enforce --check via preflight assert`.
- **A `set_fact` (or any check-mode-EXECUTING task) that dereferences a check-mode-SKIPPED `command`/`shell` task's `register` fails the play under `--check`.** `command`/`shell` modules don't run in `--check` (they `skipping:`), so their registered var has no `.stdout`; but `set_fact` DOES execute in check mode, so `{{ reg.stdout | from_json }}` hits `from_json` on `""` → `Expecting value: line 1 column 1` → fatal (often `no_log`-censored, so it reads as an opaque failure). Bit drift-check on frigg via `control-node`'s "Parse GitHub deploy key fields" (consuming the skipped "Fetch … from Vault" shell). **Fix:** put `check_mode: false` on the *producer* shell IF it's read-only (the repo convention — same as the k3s/zabbix detect-state probes), so it runs in `--check` and the consumer gets real data; otherwise gate the consumer with `when: reg.stdout is defined` / `not ansible_check_mode`. Read-only-fetch → `check_mode: false` is preferred: it also gives genuine drift detection on whatever the fetched data provisions. Surfaced 2026-06-10.
- **Hermod-summary callback plugin** parses the `PLAY RECAP` output and ships a compact markdown body to Hermod via the Semaphore webhook config. Without the callback, the Hermod alert payload is the full ansible stdout — multi-MB on a 25-host fleet, exceeds Apprise's body limit, gets truncated to garbage. Custom callback emits per-host `changed/failed` counts + first 3 failure summaries; full output remains in VL for forensics.
