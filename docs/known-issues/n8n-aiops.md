

- **`IPAddressDeny=` on a unit applies to its WHOLE cgroup, `ExecStartPre=+` helpers included (2026-10-02, Toolbelt API).** The first version ran the Vault token loader as `ExecStartPre=+` inside the API unit that has `IPAddressDeny=any`; the loader timed out reaching Vault (`URLError: timed out`, unit `Failed to start`). `+` lifts the sandbox directives (`ProtectSystem=` etc.) but not the cgroup BPF filter. Fix: the loader is its own oneshot unit (`aiops-toolbelt-token.service`, no IP filter, `RuntimeDirectoryPreserve=yes`) and the API unit runs `ExecStartPre=+systemctl restart aiops-toolbelt-token.service`, which also refreshes the token on every start. A timeout (not `connection refused`) from a helper inside an `IPAddressDeny=` unit means this. The local loader test cannot show it; only the unit on the host does.
- **Toolbelt API reachability check:** from Gná an anonymous `/stats` returns 403 and `/healthz` 200; from any other host (Hugin tested) the connection times out, because the unit's `IPAddressAllow=` drops it before the app's own allow-list sees it.
- **The Toolbelt unit's `IPAddressAllow=` now includes the homelab egress range (10.0.0.0/8) for the `reach.tcp` probe, so the cgroup filter no longer drops other LAN hosts' inbound packets (2026-10-02).** The app-level allow-list (`--allow`, Gna only) still refuses them with 403, and that is tested, but a Hugin probe now gets 403 instead of a timeout. If the cgroup layer must be strict again, move `reach.tcp` to a separate helper unit and shrink `aiops_toolbelt_egress_allow` to the specific read-only backends.
