# Jellyfin (LXC 1123) gotchas

Read before touching the Jellyfin role, its LXC or its media mount. Service page: [`../services/jellyfin.md`](../services/jellyfin.md). Plan: [`plans/active/5h-jellyfin.md`](../plans/active/5h-jellyfin.md).

- **A passed-through device keeps its host group id, and low gids collide with the container's own groups (found 2026-10-06).** The render node arrives in the LXC as `crw-rw---- root <gid>`. Debian 13's LXC template has `kvm`=993 and `render`=992, so a `device_passthrough { gid = 993 }` made the node group `kvm`, not `render`. Rule: give the device its own gid (2001, group `igpu`, `jellyfin_gpu_gid`) in Terraform and create the matching group in the role; the role's preflight asserts the node is a char device with that gid (`stat.gid`, not `gr_gid`). A gid change in Terraform restarts the container.
- **`apt` needs a fresh index right after adding the Jellyfin repo (found 2026-10-06).** "No package matching jellyfin-server" on the first run. The role refreshes the index when the repo task changed or `apt-cache policy jellyfin-server` has no candidate. It also installs `curl` first, which the minimal template lacks.
- **Do not set a mode on the NFS mount point (found 2026-10-06).** `file: path=/media mode=...` on a re-run hits the already-mounted read-only share ("Read-only file system"). The role creates the directory without a mode, mounts, then asserts `ro` from the live mount options.
- **DSM NFS evaluates numeric uids and the POSIX mode bits, not the share ACL (found 2026-10-06).** Symptoms: `/media` shows mode 0 owned by root, or the top level lists but every folder is `700` owned by DSM uid 1026 and `jellyfin` (uid 104) is denied, although `admin` has read/write in the DSM share permissions. Rules: Squash "Map all users to admin" with Privilege Read only is the rule that works; custom DSM groups cannot be given a fixed gid such as 2000, so a shared-gid scheme does not work; the Linux NFS client has no `uid=` option (CIFS does). Fix used (no root on the Synology needed): temporarily mount `rw`, `chown -R jellyfin /media` and `chmod` the folders the pods write to (`Downloads`, `Anime`) to 777, set the mount back to `ro` (re-run `--tags jellyfin:media`; the role asserts `ro`), then switch the DSM rule for `10.0.11.223` from Read/Write to Read only. Propagating permissions in DSM resets the share root's mode, so recheck `sudo -u jellyfin ls /media` afterwards. The share was the old `media-backup` tree, renamed `media` once the backups moved off; it is now one share for the media automation too ([`../services/media-automation.md`](../services/media-automation.md)). NFS is case-sensitive: the folders are `Downloads` and `Anime`.
- **Never leave `/media` mounted `rw`.** With the squash rule above and `admin` read/write on the share, a `rw` mount would let Jellyfin write to the NAS. `/etc/fstab` is managed by the role; an out-of-band edit to `rw` is reverted by the next `--tags jellyfin:media`.
- **jellyfin-ffmpeg and stdin.** Running ffmpeg in a loop over an SSH heredoc makes it read the script from stdin and pause ("Transcoding is paused"). Use `-nostdin` and run a script file with `</dev/null`.
- **`TranscodingTempPath` is not in the 10.11 encoding API section.** The role's settings step asserts every wanted key exists in the live document and fails on a missing one; the default transcode directory (`/var/cache/jellyfin/transcodes`) is already on the cache mount.
- **gitleaks flags public checksums in variables named `*key*sha256`** (`generic-api-key` rule). The apt signing-key checksum is `jellyfin_apt_signer_sha256`. Never bypass the pre-push hook for this.
- **Hand-run Ansible from macOS crashes forked workers; run it from Frigg** (see [`frigg-control-node.md`](frigg-control-node.md)).
- **A restored container has an empty, root-owned cache volume, and Jellyfin aborts on it (found 2026-10-10, J5 restore test).** `/var/cache/jellyfin` is a separate mount point excluded from PBS (`backup = false`), so `pct restore` creates a fresh volume owned by `root`. Symptom: `jellyfin.service` dies with SIGABRT in `StartApp` and restarts until the start limit. Fix in the role: a `tmpfiles.d` rule (`/etc/tmpfiles.d/jellyfin-cache.conf`) re-owns the cache and transcode directories on every boot, before the service starts. Verified by restoring a fresh backup: the service starts on its own and reports the live server id.
- **`jellyfin.service` will not start without `/media` (`Requires=media.mount`, by design).** A scratch restore with its network removed (what `pbs-restore-test.yml` does) therefore leaves Jellyfin `inactive` with "Dependency failed". That is the safeguard against scanning an empty library away, not a restore defect. To prove the restored service itself starts, mount an empty `tmpfs` on `/media` inside the scratch CT only, then `systemctl reset-failed media.mount && systemctl start jellyfin`.
- **`pct migrate 1123 <node> --restart` takes about 9 minutes each way** because the whole 40 GB cache volume is copied (thin LVM is copied at full size). Plan the outage; shrinking the cache volume is the lever if it ever matters.
- **A restore with the network removed shows a plugin-repository stack trace in the journal** (the update check cannot reach the internet). Harmless.
- **Debian 13 has no OpenCL runtime, so HDR tone mapping failed until Intel's upstream packages were installed (found 2026-10-10, J5 matrix).** Symptom: every HDR10 / Dolby Vision transcode dies immediately; the ffmpeg log says `Failed to get number of OpenCL platforms: -1001` and `Failed to set value 'opencl=ocl@va' for option 'init_hw_device'`. SDR transcodes are unaffected. Cause: `EnableTonemapping` (OpenCL) and `EnableVppTonemapping` were both on, and Jellyfin prefers OpenCL when both are on; `intel-opencl-icd` exists in Debian bookworm and unstable but **not in trixie**. Fix: `tasks/opencl.yml` installs Intel's `.deb`s from the [compute-runtime](https://github.com/intel/compute-runtime/releases) and [IGC](https://github.com/intel/intel-graphics-compiler/releases) releases (compute-runtime 26.22.38646.4, IGC 2.36.3, gmmlib 22.10.0): sha256-verified, dependency order, `apt-mark hold`, and the GPU self-check asserts `clinfo` sees the iGPU. Intel documents and validates these only on Ubuntu (the 26.22 release on 24.04; the newest releases on 26.04), so the set was **tested on Debian 13 here**: clean install, `clinfo` as `jellyfin` sees "Intel(R) UHD Graphics", OpenCL 3.0 NEO, and tone-mapped transcodes run at 2.6-3.3x real time. Rules: bump compute-runtime, IGC and gmmlib **together** (the compute-runtime release notes name the IGC and gmmlib versions), and pick a release built on a distro whose glibc is not newer than trixie's 2.41 (the package says `libc6 >= 2.38`; the 26.35 releases on Ubuntu 26.04 were not tried). **Alternative with no extra packages:** set `EnableTonemapping: false` and keep `EnableVppTonemapping: true`; Jellyfin then tone-maps HDR10 (and Dolby Vision P8.1 via its HDR10 layer) on the iGPU's VPP engine at the same speed (within 5%). OpenCL additionally covers the cases VPP does not claim (Dolby Vision P5, HLG), which were not testable here.
