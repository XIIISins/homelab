# Known gotchas — Vault

*Migrated from `CLAUDE.md`. Recovery commands + rules. Incident retros in [`../incidents/`](../incidents/).*

## Vault

- **Vault listener is TLS (cert-manager internal CA), flipped 2026-06-20.** Single TLS listener on the `homelab-internal-ca` cert (Secret `vault-tls`; SANs cover the Services + `*.vault-internal` + `10.0.20.11` + `127.0.0.1`) — no plaintext API endpoint survives. trust-manager distributes the CA as `vault-ca-bundle` ConfigMaps (every ns); Traefik verifies the backend via Gateway-API `BackendTLSPolicy`, ESO via `caProvider` (`vault-tls` `ca.crt`), Semaphore via `ANSIBLE_HASHI_VAULT_CA_CERT`. FQDN consumers (operator CLI/TF, Frigg) keep the public LE cert at Traefik — no internal-CA trust needed. `vault-ui` LB on `10.0.20.11` now serves **HTTPS** (internal CA — break-glass needs `VAULT_CACERT`/`-tls-skip-verify`), still LAN-only via `loadBalancerSourceRanges`. The Raft *cluster* port 8201 uses Vault's own auto-generated cluster cert (unaffected by the listener flip). **Cert renewal needs a manual STS rolling-restart** (Vault doesn't auto-reload listener certs); leaf is 1y/30d-grace. Runbook: [`../procedures/vault-tls-migration.md`](../procedures/vault-tls-migration.md).
- **`vault-ui` is dual-pathed (Phase 6 Stage 1): a pinned MetalLB LB at `10.0.20.11` + a Traefik HTTPRoute at `vault.niflheim.xiiisins.com`.** Both reach the same `vault-ui` Service (selects all 3 server pods; Vault standby request-forwarding routes to the active node, so either entry behaves identically). The FQDN is the OIDC/primary path (Authentik login via `terraform/vault/oidc.tf` + `terraform/authentik/vault.tf`); the `.11` LB is **kept deliberately** as a Traefik-independent direct path (break-glass when the Gateway/Traefik is itself being debugged). **`VAULT_ADDR` was cut over `.11` → the FQDN on 2026-05-31** — it's sourced from the 1P item `[Asgard] - Ansible - Vault - AppRole (ansible-local)` (`url` field, read by the `homelab-env` shim into `VAULT_ADDR`, which `community.hashi_vault` also falls back to — so Terraform + Vault CLI + Ansible AppRole all follow that one field). To move it again: edit the 1P `url` field + `homelab-env --refresh` (HTTPS needs no `VAULT_SKIP_VERIFY` — the `*.niflheim` wildcard is a public LE cert). `.11` is pinned via `ui.loadBalancerIP` (NOT dynamic — stable across Service recreate, closes the static/dynamic collision gotcha). The earlier "flip to ClusterIP to reclaim `.11`" plan was **abandoned** — `.11` is kept. Don't remove the `.11` LB without re-confirming nothing points at it.
- **Vault Raft follower auto-join can fail** on fresh init. If vault-1/2 missed the join window, they log "stored unseal keys are supported, but none were found." Fix: `kubectl exec -n vault vault-<N> -- vault operator raft join -leader-ca-cert=@/vault/userconfig/vault-tls/ca.crt https://vault-0.vault-internal:8200` (TLS listener since 2026-06-20). Auto-unseal via KMS after.
- **Vault init can leave stuck partial state.** Recovery: `kubectl delete statefulset vault -n vault --cascade=orphan`, `kubectl delete pvc -n vault data-vault-{0,1,2}`, `kubectl delete pod -n vault vault-{0,1,2} --force --grace-period=0`, then `flux reconcile helmrelease vault -n vault --force`. Clean up old iSCSI LUNs on DSM after.
- **Vault root token is in 1Password item `7g4grolyien2yqkm7me2jficmy`.** Retrieve: `op item get 7g4grolyien2yqkm7me2jficmy --reveal --fields password`. Use with container pin: `kubectl exec -n vault vault-0 -c vault -- env VAULT_TOKEN=(op item get 7g4grolyien2yqkm7me2jficmy --reveal --fields password) vault operator raft list-peers`. **Rotate it** with `rotate-vault-root-token` (both shim dialects, added 2026-09-03) — mints a fresh **orphan** token (non-orphan would get cascade-revoked when the old one is killed in the last step), verifies it live against Vault, writes + hash-verifies the 1P update, then prompts before revoking the old one. Needs an interactive terminal (the confirm prompt reads stdin) — run it from a real shell, not scripted.
- **`VAULT_TOKEN` in `~/.cache/homelab/env.sh` is per-session and can expire mid-deploy.** Symptom during a long apply chain: `terraform plan/apply` errors with `* permission denied / * invalid token` against any `vault_*` resource. Re-mint: `fish -c 'homelab-env; set-vault-token root; homelab-env --refresh'` (the shim's `set-vault-token root` mode reads the root token from 1P and writes it into the cache files; `--refresh` is needed to actually persist; `homelab-env` first because `set-vault-token` depends on `VAULT_ADDR` from the cache). Verify with `vault token lookup`. **Long-deploy rule**: any chain that spans more than ~2h should re-verify VAULT_TOKEN before each TF module's apply — token-expiry mid-flight is a quiet failure that costs a full plan-and-retry cycle. Tracked as a follow-up in open-questions (`homelab-preflight` shim idea).
- **Two AppRoles, two storage conventions, two rotation helpers — don't conflate.** `ansible-local` (MacBook control node) stores RoleID + SecretID in 1P item `Ansible - Vault - k3s` and rotates via `rotate-approle ansible-local`. `ansible-awx` (Semaphore — inherited the role when Semaphore replaced the planned AWX deployment) stores its credentials at Vault KV `secret/k8s/semaphore/vault-approle` and rotates via `rotate-semaphore-approle` (separate helper). Running `rotate-approle ansible-awx` errors out at "unknown role" because the helper is 1P-canonical and ansible-awx has no 1P entry. Worse failure mode: assuming Semaphore uses ansible-local and manually writing ansible-local's new SecretID into Semaphore's Vault KV slot → role_id (ansible-awx's `c43a483d-…` from Vault KV) + secret_id (ansible-local's freshly minted UUID) is a mismatched pair → Semaphore drift-checks fail with `permission denied` on `/v1/auth/approle/login`. Diagnostic: `vault read -field=role_id auth/approle/role/ansible-{local,awx}/role-id` shows both authoritative RoleIDs; compare against the leaked / consumer-stored value to identify which AppRole each consumer actually uses. Surfaced 2026-05-27 leak-driven rotation. Recovery: mint a fresh ansible-awx SecretID, write to Vault KV with hash-verify, `terraform apply` in `terraform/semaphore/`, drift-check validate, revoke orphan.
- **The `approle` auth mount's `max_lease_ttl` caps every role's `secret_id_ttl` — Vault's 768h (32d) default silently clamps a 90d role.** A SecretID minted under the default mount expires 32d out despite `secret_id_ttl = 7776000` (90d) on the role — a surprise monthly re-mint treadmill. **Diagnostic:** `vault read sys/auth/approle/tune` shows the mount ceiling (`max_lease_ttl`); compare to the role's `secret_id_ttl`. **Fix:** `tune { max_lease_ttl = "2160h" }` on `vault_auth_backend.approle` in `terraform/vault/` (plan is in-place, 0 destroy). Verify a fresh mint gets the full window: `vault write auth/approle/role/<r>/secret-id-accessor/lookup secret_id_accessor=<new>` → `.expiration_time` should be ~90d out. Surfaced 2026-05-31 Wave S7. **Corollary — the fix is NOT retroactive: a SecretID minted *before* the mount tune keeps its clamped 32d lease.** So a credential minted in the days before 2026-05-31 expires ~32d after *its mint date*, weeks after the fix landed, while `vault read auth/approle/role/<r>` and the mount tune both look perfect — login just starts returning `400 invalid role or secret ID` and `vault list auth/approle/role/<r>/secret-id` shows `{}` (zero live accessors). Bit `ansible-awx` (Semaphore's infra-health-check prober) on 2026-06-28: minted 2026-05-27, clamped to 32d → expired exactly 32d later, blinding the prober. **Fix = just re-mint** (mount is correct now, so the new one gets the full 90d); for `ansible-awx` that's the bootstrap path inside `rotate-semaphore-approle` (the helper aborts on zero existing accessors): `vault write -f auth/approle/role/ansible-awx/secret-id` → `vault kv patch -mount=secret k8s/semaphore/vault-approle secret_id="$sid"` (hash-verify) → `terraform apply` in `terraform/semaphore/` to propagate to the Semaphore env.
- **`rotate-approle` is human-in-the-loop by design (it PRINTS the new SecretID), and the paste step is a footgun — NEVER touch the `username` field.** The helper mints, prints `password` + `secret_id_accessor` + `expires_at` (so it's operator-run, never scripted into a transcript), and the human pastes those three into the 1P item. `username` holds the **RoleID**, which is STABLE across SecretID rotations and must not be changed. A 2026-05-31 rotation pasted the new *accessor* into `username` (and left `secret_id_accessor` at the now-revoked old value) → `set-vault-token approle` sent an accessor as the role_id → Vault `400 invalid role or secret ID`. **Diagnostic** (never echo the secret — use sha256 + accessor membership): triangulate authoritative Vault (`vault read -field=role_id auth/approle/role/<r>/role-id` + `vault list .../secret-id`) against the 1P fields — the 1P `username` must equal Vault's role_id, and the 1P `secret_id_accessor` must be in Vault's live accessor list. **Recovery:** `op item edit <uuid> "username=$RID" "secret_id_accessor=<live-accessor>"` (values via shell var, not literal) → `homelab-env --refresh`. Correcting `secret_id_accessor` is load-bearing, not cosmetic: a later `rotate-approle --fix` treats the 1P accessor as canonical and **destroys every other SecretID** — a stale value there would nuke the live one. Surfaced 2026-05-31 Wave S7.
- **Machine-accessed 1P items are referenced by UUID, not title — `vault-root-token` was the last offender.** The shim helper behind `set-vault-token root` read the literal title `"Asgard - Vault - Root Token"`, which the Wave-S1 1P reorg renamed → `op read` failed (`isn't an item`) and `set-vault-token root` broke (masked while a cached root token stayed valid). Now `__op_vault_root = 7g4grolyien2yqkm7me2jficmy` in both shims (`.config/fish/conf.d/homelab.fish` + `.config/scripts/homelab.sh`). Reaffirms the convention — every `op://` reference in the shim/TF uses a UUID so 1P renames never break automation. Surfaced 2026-05-31 Wave S7.
- **Replacing a Vault Raft node's storage (e.g. a StorageClass migration) is a per-node remove→wipe→join→WAIT-for-voter dance.** The chart's raft config has **no `retry_join`** stanza, so a node whose `/vault/data` is wiped comes up **uninitialized + sealed** and will NOT auto-rejoin — it must be manually `vault operator raft join -leader-ca-cert=@/vault/userconfig/vault-tls/ca.crt https://<leader>.vault-internal:8200`'d (TLS listener since 2026-06-20), after which KMS auto-unseals it and it resyncs (validated 2026-05-30: uninitialized→joined→unsealed→standby in ~10s). Clean per-node sequence, leader last: `raft remove-peer vault-N` (from a healthy node; drops to 2 voters, quorum still 2) → `kubectl delete pvc data-vault-N --wait=false` + `delete pod vault-N` (STS provisions the fresh empty PVC on the new SC) → `raft join` → KMS unseal. **The load-bearing gate: after join, a freshly-joined node is a NON-VOTER until autopilot promotes it (~`server_stabilization_time` window), during which `raft autopilot state` shows `Failure Tolerance: 0`.** Moving to the next node before promotion (Voter:true + tolerance back to 1) means the next wipe drops you below quorum. Always poll `list-peers` (target node `Voter: true`) **and** `autopilot state` (`Failure Tolerance: 1`) between nodes. Step the leader down (`vault operator step-down`) before wiping it so leadership lands on an already-migrated node. Surfaced 2026-05-30 Class-L (iSCSI→local-path); full runbook in [`docs/procedures/synology-storage-redesign.md`](../procedures/synology-storage-redesign.md) "Class L".
- **`vault operator raft snapshot save` is the right Vault backup, NOT a recursive `kv get` dump.** The snapshot is the entire Vault (all KV + policies + auth methods + mounts) captured consistently and **sealed-encrypted** (4 tar members: `meta.json` + `state.bin` BoltDB + `SHA256SUMS` + `SHA256SUMS.sealed`); restore via `vault operator raft snapshot restore`. A `kv get` dump is plaintext-on-disk and only covers KV. Take one before any storage-touching maintenance: `kubectl exec -n vault vault-0 -c vault -- env VAULT_TOKEN=$ROOT vault operator raft snapshot save /tmp/snap` → `kubectl cp` off-cluster → `rm` the in-pod copy. Kept at `~/homelab-backups/vault/`.
- **`seed-vault-approle` does NOT mint a fresh SecretID from Vault — it copies whatever `$ANSIBLE_HASHI_VAULT_SECRET_ID` is currently in the shell env (i.e. whatever 1Password holds) into the local secret-zero file.** Re-running it after a "the SecretID is stale" symptom just re-stamps the file's *mtime*, not the underlying *value* — if 1P's stored copy is itself the stale one (e.g. it drifted from Vault's live SecretID without anyone rotating through `rotate-approle`), the login keeps failing with `invalid role or secret ID` no matter how many times you re-seed. The actual fix path is `rotate-approle <role>` (mints via Vault, updates 1P) **then** `homelab-env --refresh && seed-vault-approle` (pulls the now-correct value down locally) — re-seeding alone never touches Vault. Diagnostic to tell these apart: `vault read -field=role_id auth/approle/role/<role>/role-id` vs. the role_id in the local file — if they match, the problem is the secret_id specifically, and only a real `rotate-approle` fixes it. Surfaced 2026-09-03 during Immich shape work — a `homelab-env && seed-vault-approle` re-seed produced a freshly-timestamped file that still failed login identically.
- **`ansible-frigg` has no entry in `__homelab_approle_items` (`homelab.sh`) and no matching 1Password item — `rotate-approle ansible-frigg` fails "unknown role".** Only `ansible-local` is wired (plus a commented placeholder for `ansible-awx`, which actually uses the separate `rotate-semaphore-approle` helper per the "two rotation helpers" gotcha above). Frigg's SecretID was seeded once at provision time directly into `/etc/frigg/vault-approle.env` and was never brought into the `rotate-approle` pattern — there's no 1P item shaped like `ansible-local`'s (`secret_id`/`secret_id_accessor` fields) to update. **Not yet fixed** — when Frigg's SecretID next goes stale, the fast path is a direct root-token mint (`vault write -f auth/approle/role/ansible-frigg/secret-id`) + manual write to `/etc/frigg/vault-approle.env` over SSH (no 1P mirror); the proper fix is creating the missing 1P item + adding an `__homelab_approle_items` entry so it joins the standard rotation path. Surfaced 2026-09-03.
- **Which token to use for a MacBook `terraform apply` depends on the module — the `ansible-local` AppRole's policy is scoped to `secret/data/ansible/*` reads only, NOT `secret/data/k8s/*` or any write capability.** `terraform/vault` (manages Vault's own auth methods/policies — always root, by design, see CLAUDE.md) and any module writing/reading `k8s/<app>/*` paths (`terraform/authentik`, `terraform/cloudflare` if it ever touches Vault, most app-provisioning modules) need the **root** token from `~/.cache/homelab/env.sh`, not `vault-homelab-env`'s AppRole token — the AppRole 403s with `failed to create limited child token: permission denied` on the very first `secret/data/k8s/*`-touching resource. Only ansible-adjacent modules reading exclusively from `ansible/*` paths work with the narrower AppRole token. Surfaced 2026-09-03 applying `terraform/authentik` for Immich — `vault-homelab-env`'s token got a wall of 403s across every pre-existing `k8s/*` OIDC secret in state, not just the new one, because the token simply can't read that subtree at all.
- **A HelmRelease install that fails and exhausts `install.remediation.retries` does NOT self-heal on a later `flux reconcile` — it needs `--force`.** Once Helm's own retry budget is spent (3 retries + 1 initial = "Failed to install after 4 attempt(s)"), Flux reports the same terminal failure on every subsequent plain reconcile even after the underlying blocker (e.g. a CrashLoopBackOff cleared) is long gone and the Deployment is genuinely healthy (`kubectl rollout status` succeeds). `flux reconcile helmrelease <name> -n <ns> --force` forces a fresh install/upgrade attempt regardless of the exhausted counter. Surfaced 2026-09-03 — Immich's HelmRelease sat `Ready: False` reporting a stale timeout error for several minutes after the actual pod had been `1/1 Running` the whole time; a plain reconcile still said "Failed to install after 4 attempt(s)", `--force` cleared it in one shot.
- **`vault kv patch <field>=-` stdin pattern can silently produce wrong values.** Length matches expected (e.g. 36 chars for a UUID stored via 36-char input from stdin), but a hash-compare against the canonical source fails. Suspected cause: vault CLI version-dependent handling of trailing whitespace or stdin buffering. Reliable alternative: `vault kv patch <field>="$var"` with the value in a shell var (argv exposure is <100ms on single-user machines — acceptable). **Defense-in-depth**: any rotation flow that writes through `vault kv patch` should hash-compare the resulting `vault kv get -field=...` output against the source value before proceeding. Pattern in `rotate-semaphore-approle`. Surfaced 2026-05-27 during AppRole rotation; produced a 4-hour debug detour assuming Semaphore was misconfigured before realising Vault KV had the wrong bytes.
