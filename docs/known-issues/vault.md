# Known gotchas — Vault

*Migrated from `CLAUDE.md`. Recovery commands + rules. Incident retros in [`../incidents/`](../incidents/).*

## Vault

- **Vault TLS disabled is deliberate.** `tls_disable = 1` on listener (cluster traffic too). Conscious homelab tradeoff. `vault-ui` LB on `10.0.20.11` serves plaintext HTTP — internal/VLAN-only.
- **`vault-ui` is dual-pathed (Phase 6 Stage 1): a pinned MetalLB LB at `10.0.20.11` + a Traefik HTTPRoute at `vault.niflheim.xiiisins.com`.** Both reach the same `vault-ui` Service (selects all 3 server pods; Vault standby request-forwarding routes to the active node, so either entry behaves identically). The FQDN is the OIDC/primary path (Authentik login via `terraform/vault/oidc.tf` + `terraform/authentik/vault.tf`); the `.11` LB is **kept deliberately** as a Traefik-independent direct path (break-glass when the Gateway/Traefik is itself being debugged). **`VAULT_ADDR` was cut over `.11` → the FQDN on 2026-05-31** — it's sourced from the 1P item `[Asgard] - Ansible - Vault - AppRole (ansible-local)` (`url` field, read by the `homelab-env` shim into `VAULT_ADDR`, which `community.hashi_vault` also falls back to — so Terraform + Vault CLI + Ansible AppRole all follow that one field). To move it again: edit the 1P `url` field + `homelab-env --refresh` (HTTPS needs no `VAULT_SKIP_VERIFY` — the `*.niflheim` wildcard is a public LE cert). `.11` is pinned via `ui.loadBalancerIP` (NOT dynamic — stable across Service recreate, closes the static/dynamic collision gotcha). The earlier "flip to ClusterIP to reclaim `.11`" plan was **abandoned** — `.11` is kept. Don't remove the `.11` LB without re-confirming nothing points at it.
- **Vault Raft follower auto-join can fail** on fresh init. If vault-1/2 missed the join window, they log "stored unseal keys are supported, but none were found." Fix: `kubectl exec -n vault vault-<N> -- vault operator raft join http://vault-0.vault-internal:8200`. Auto-unseal via KMS after.
- **Vault init can leave stuck partial state.** Recovery: `kubectl delete statefulset vault -n vault --cascade=orphan`, `kubectl delete pvc -n vault data-vault-{0,1,2}`, `kubectl delete pod -n vault vault-{0,1,2} --force --grace-period=0`, then `flux reconcile helmrelease vault -n vault --force`. Clean up old iSCSI LUNs on DSM after.
- **Vault root token is in 1Password item `7g4grolyien2yqkm7me2jficmy`.** Retrieve: `op item get 7g4grolyien2yqkm7me2jficmy --reveal --fields password`. Use with container pin: `kubectl exec -n vault vault-0 -c vault -- env VAULT_TOKEN=(op item get 7g4grolyien2yqkm7me2jficmy --reveal --fields password) vault operator raft list-peers`.
- **`VAULT_TOKEN` in `~/.cache/homelab/env.sh` is per-session and can expire mid-deploy.** Symptom during a long apply chain: `terraform plan/apply` errors with `* permission denied / * invalid token` against any `vault_*` resource. Re-mint: `fish -c 'homelab-env; set-vault-token root; homelab-env --refresh'` (the shim's `set-vault-token root` mode reads the root token from 1P and writes it into the cache files; `--refresh` is needed to actually persist; `homelab-env` first because `set-vault-token` depends on `VAULT_ADDR` from the cache). Verify with `vault token lookup`. **Long-deploy rule**: any chain that spans more than ~2h should re-verify VAULT_TOKEN before each TF module's apply — token-expiry mid-flight is a quiet failure that costs a full plan-and-retry cycle. Tracked as a follow-up in open-questions (`homelab-preflight` shim idea).
- **Two AppRoles, two storage conventions, two rotation helpers — don't conflate.** `ansible-local` (MacBook control node) stores RoleID + SecretID in 1P item `Ansible - Vault - k3s` and rotates via `rotate-approle ansible-local`. `ansible-awx` (Semaphore — inherited the role when Semaphore replaced the planned AWX deployment) stores its credentials at Vault KV `secret/k8s/semaphore/vault-approle` and rotates via `rotate-semaphore-approle` (separate helper). Running `rotate-approle ansible-awx` errors out at "unknown role" because the helper is 1P-canonical and ansible-awx has no 1P entry. Worse failure mode: assuming Semaphore uses ansible-local and manually writing ansible-local's new SecretID into Semaphore's Vault KV slot → role_id (ansible-awx's `c43a483d-…` from Vault KV) + secret_id (ansible-local's freshly minted UUID) is a mismatched pair → Semaphore drift-checks fail with `permission denied` on `/v1/auth/approle/login`. Diagnostic: `vault read -field=role_id auth/approle/role/ansible-{local,awx}/role-id` shows both authoritative RoleIDs; compare against the leaked / consumer-stored value to identify which AppRole each consumer actually uses. Surfaced 2026-05-27 leak-driven rotation. Recovery: mint a fresh ansible-awx SecretID, write to Vault KV with hash-verify, `terraform apply` in `terraform/semaphore/`, drift-check validate, revoke orphan.
- **The `approle` auth mount's `max_lease_ttl` caps every role's `secret_id_ttl` — Vault's 768h (32d) default silently clamps a 90d role.** A SecretID minted under the default mount expires 32d out despite `secret_id_ttl = 7776000` (90d) on the role — a surprise monthly re-mint treadmill. **Diagnostic:** `vault read sys/auth/approle/tune` shows the mount ceiling (`max_lease_ttl`); compare to the role's `secret_id_ttl`. **Fix:** `tune { max_lease_ttl = "2160h" }` on `vault_auth_backend.approle` in `terraform/vault/` (plan is in-place, 0 destroy). Verify a fresh mint gets the full window: `vault write auth/approle/role/<r>/secret-id-accessor/lookup secret_id_accessor=<new>` → `.expiration_time` should be ~90d out. Surfaced 2026-05-31 Wave S7.
- **`rotate-approle` is human-in-the-loop by design (it PRINTS the new SecretID), and the paste step is a footgun — NEVER touch the `username` field.** The helper mints, prints `password` + `secret_id_accessor` + `expires_at` (so it's operator-run, never scripted into a transcript), and the human pastes those three into the 1P item. `username` holds the **RoleID**, which is STABLE across SecretID rotations and must not be changed. A 2026-05-31 rotation pasted the new *accessor* into `username` (and left `secret_id_accessor` at the now-revoked old value) → `set-vault-token approle` sent an accessor as the role_id → Vault `400 invalid role or secret ID`. **Diagnostic** (never echo the secret — use sha256 + accessor membership): triangulate authoritative Vault (`vault read -field=role_id auth/approle/role/<r>/role-id` + `vault list .../secret-id`) against the 1P fields — the 1P `username` must equal Vault's role_id, and the 1P `secret_id_accessor` must be in Vault's live accessor list. **Recovery:** `op item edit <uuid> "username=$RID" "secret_id_accessor=<live-accessor>"` (values via shell var, not literal) → `homelab-env --refresh`. Correcting `secret_id_accessor` is load-bearing, not cosmetic: a later `rotate-approle --fix` treats the 1P accessor as canonical and **destroys every other SecretID** — a stale value there would nuke the live one. Surfaced 2026-05-31 Wave S7.
- **Machine-accessed 1P items are referenced by UUID, not title — `vault-root-token` was the last offender.** The shim helper behind `set-vault-token root` read the literal title `"Asgard - Vault - Root Token"`, which the Wave-S1 1P reorg renamed → `op read` failed (`isn't an item`) and `set-vault-token root` broke (masked while a cached root token stayed valid). Now `__op_vault_root = 7g4grolyien2yqkm7me2jficmy` in both shims (`.config/fish/conf.d/homelab.fish` + `.config/scripts/homelab.sh`). Reaffirms the convention — every `op://` reference in the shim/TF uses a UUID so 1P renames never break automation. Surfaced 2026-05-31 Wave S7.
- **Replacing a Vault Raft node's storage (e.g. a StorageClass migration) is a per-node remove→wipe→join→WAIT-for-voter dance.** The chart's raft config has **no `retry_join`** stanza, so a node whose `/vault/data` is wiped comes up **uninitialized + sealed** and will NOT auto-rejoin — it must be manually `vault operator raft join http://<leader>.vault-internal:8200`'d, after which KMS auto-unseals it and it resyncs (validated 2026-05-30: uninitialized→joined→unsealed→standby in ~10s). Clean per-node sequence, leader last: `raft remove-peer vault-N` (from a healthy node; drops to 2 voters, quorum still 2) → `kubectl delete pvc data-vault-N --wait=false` + `delete pod vault-N` (STS provisions the fresh empty PVC on the new SC) → `raft join` → KMS unseal. **The load-bearing gate: after join, a freshly-joined node is a NON-VOTER until autopilot promotes it (~`server_stabilization_time` window), during which `raft autopilot state` shows `Failure Tolerance: 0`.** Moving to the next node before promotion (Voter:true + tolerance back to 1) means the next wipe drops you below quorum. Always poll `list-peers` (target node `Voter: true`) **and** `autopilot state` (`Failure Tolerance: 1`) between nodes. Step the leader down (`vault operator step-down`) before wiping it so leadership lands on an already-migrated node. Surfaced 2026-05-30 Class-L (iSCSI→local-path); full runbook in [`docs/procedures/synology-storage-redesign.md`](../procedures/synology-storage-redesign.md) "Class L".
- **`vault operator raft snapshot save` is the right Vault backup, NOT a recursive `kv get` dump.** The snapshot is the entire Vault (all KV + policies + auth methods + mounts) captured consistently and **sealed-encrypted** (4 tar members: `meta.json` + `state.bin` BoltDB + `SHA256SUMS` + `SHA256SUMS.sealed`); restore via `vault operator raft snapshot restore`. A `kv get` dump is plaintext-on-disk and only covers KV. Take one before any storage-touching maintenance: `kubectl exec -n vault vault-0 -c vault -- env VAULT_TOKEN=$ROOT vault operator raft snapshot save /tmp/snap` → `kubectl cp` off-cluster → `rm` the in-pod copy. Kept at `~/homelab-backups/vault/`.
- **`vault kv patch <field>=-` stdin pattern can silently produce wrong values.** Length matches expected (e.g. 36 chars for a UUID stored via 36-char input from stdin), but a hash-compare against the canonical source fails. Suspected cause: vault CLI version-dependent handling of trailing whitespace or stdin buffering. Reliable alternative: `vault kv patch <field>="$var"` with the value in a shell var (argv exposure is <100ms on single-user machines — acceptable). **Defense-in-depth**: any rotation flow that writes through `vault kv patch` should hash-compare the resulting `vault kv get -field=...` output against the source value before proceeding. Pattern in `rotate-semaphore-approle`. Surfaced 2026-05-27 during AppRole rotation; produced a 4-hour debug detour assuming Semaphore was misconfigured before realising Vault KV had the wrong bytes.
