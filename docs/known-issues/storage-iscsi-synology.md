# Known gotchas — Storage — iSCSI / Synology CSI / local-path / migration

*Migrated from `CLAUDE.md`. Recovery commands + rules. Incident retros in [`../incidents/`](../incidents/).*

## Storage / iSCSI / Synology CSI

- **iSCSI LUNs are single-session.** After ungraceful restarts, stale sessions or discovery node records can pin a LUN to the wrong node (`non-retryable iSCSI login failure` / `iscsi_limit_max_session_count`). Cleanup: `iscsiadm -m session` / `-m node -o delete` on affected nodes; clear NAS-side if needed.
- **iSCSI node records persist across pod migrations and outlive sessions.** Sessions die with the pod; `/var/lib/iscsi/nodes/` records do not. After worker-to-worker iSCSI PV migration, source worker is left with stale node records. Latent risk: next iscsid restart/reboot logs in to stale targets → Multi-Attach errors elsewhere. Diagnosis: `iscsiadm -m node` vs `iscsiadm -m session`; entries in `node` but not `session` AND the PV is bound to a *different* node = orphan. Cleanup: `iscsiadm -m node -T <iqn> -p <portal> -o delete` on source. **Recurs after every iSCSI PV migration.**
- **iSCSI session timeout → ext4 journal abort → FS RO.** Network blip during maintenance lets the session time out; ext4 remounts RO. Recovery: scale workload to 0, attach LUN to debug pod, `fsck.ext4 -y /dev/sdX` (from Alpine — see RHEL 9 e2fsprogs gotcha below), detach, scale back up.
- **Released PVs with retain policy leave orphan iSCSI sessions** on the worker that last consumed them. Consumes Synology's `iscsi_limit_max_session_count`. Cleanup: `iscsiadm -m node -T <iqn> -p 10.0.254.20 --logout` then `-o delete`, plus NAS-side LUN cleanup via DSM. asgard-health script cross-references live sessions against `kubectl get pv` to flag orphans.
- **Synology DSM-side stale state can block iSCSI re-attach.** If a VolumeAttachment is deleted but DSM still considers a previous initiator connected, re-attach times out. Check DSM SAN Manager → Target → Connected Initiators; manually disconnect stale entries.
- **CSI controller down → all VolumeAttachment ops stall cluster-wide.** Single-replica StatefulSet, no redundancy. First diagnostic for multi-pod `Init:0/1` hangs: `kubectl get pods -n synology-csi -o wide` and check controller status.
- **Synology CSI iSCSI volumes need a chown initContainer for non-root pods.** Synology CSI doesn't honor `securityContext.fsGroup` reliably. Pattern: busybox initContainer as UID 0 running `chown -R <uid>:<gid> /mountpath` before the main container. Currently shipped in Vault (`vault-data-chown`) + Authentik Redis (`redis-data-chown`) + VictoriaLogs (`vl-data-chown`) + Teamspeak (`data-chown`). **Sub-gotcha**: the init container must keep default capabilities — `capabilities.drop: ["ALL"]` strips `CAP_CHOWN` + `CAP_FOWNER` even when `runAsUser: 0`, so recursive chown of root-owned files (e.g. fresh ext4's `lost+found`) fails with `Operation not permitted`. Mirror the Vault pattern: minimal securityContext (`runAsUser: 0`, `runAsNonRoot: false`, `allowPrivilegeEscalation: true`), no `drop`. Short-lived container; hardening surface gain isn't worth the breakage. Surfaced 2026-05-25 Phase 5g (Teamspeak first-deploy).
- **Vault SKIP_CHOWN + iSCSI fsGroup quirk.** Chart sets `SKIP_CHOWN=true` when non-root; fsGroup doesn't apply on iSCSI. Pod-level `securityContext { runAsUser: 100, runAsGroup: 1000, fsGroup: 1000, runAsNonRoot: false }` + `extraInitContainer vault-data-chown` (busybox UID 0) running `chown -R 100:1000 /vault/data && chmod 750 /vault/data`.
- **VictoriaLogs (`victoria-logs-single`) chart's init-container values key is `server.initContainers`, NOT `extraInitContainers`.** Setting `extraInitContainers` is silently ignored (no error, no warning) and the pod crashes at startup on permission-denied writing to `/storage`. Same fsGroup-on-iSCSI quirk as Vault + Authentik Redis — busybox UID 0 chown init does the job. Surfaced 2026-05-24 Phase 8a deploy.
- **RHEL 9 e2fsprogs 1.46.5 cannot fsck Synology-CSI-formatted iSCSI LUNs.** CSI uses newer ext4 features (`orphan_file`, ro-compat bit 16) → `unsupported feature(s): FEATURE_C12 FEATURE_R16`. Workaround: fsck from Alpine 3.20 debug pod. `kubectl debug node/<worker> -it --image=alpine:3.20 --profile=sysadmin -- sh` then `apk add --no-cache e2fsprogs && fsck.ext4 -y /dev/sdX`. Revisit at RHEL 10.
- **CSI eviction from tainted CPs is a footgun**, not a free side effect. CP NoSchedule taint evicts the CSI node-plugin DaemonSet; stateful pod still on the CP can't unmount (kubelet retries forever — `csi.san.synology.com not found`). `VolumeAttachment` stays `ATTACHED=true NODE=<dead-CP>` → Multi-Attach errors elsewhere. **Mitigation:** drain stateful workloads BEFORE applying CP taint, OR add CP-taint toleration to CSI DaemonSet. Recovery: iscsiadm logout from affected CP via debug pod, force-delete pod, manually delete stale VolumeAttachment.
- **Synology DS223J iSCSI LUN cap is DSM-WIDE (~10 total), NOT per-volume, and it's a hard, non-raisable model limit.** Originally (2026-05-26) misdiagnosed as per-volume; **corrected 2026-05-30** by smoke-test: creating an 11th LUN on a brand-new *empty* Volume2 still failed with `Failed to create LUN, err: Number of LUN reach limit`, and DSM's UI refuses to create more LUNs anywhere. The published spec is even lower (Max LUN 4 / Target 2) yet we run 10/10 — the enforced runtime ceiling (~10) is fixed in DSM for this 1 GB-RAM ARM model. **More volumes do NOT add LUN slots.** Not raisable via SAN Manager; the only would-be lever is editing `synoinfo.conf` (unverified it's even the right key, reverts on reboot/DSM-update, unsupported, RAM-risky on the storage SPOF) — don't. **Diagnostic**: `kubectl get pv | grep -c synology` — at 10 = at the wall. **Structural fix (the real answer): storage tiering** — NFS (`csi-driver-nfs`, no LUN limit) for file-class, local-path for app-replicated (Vault Raft), iSCSI only for block-critical single-instance (LMDB/BoltDB — mmap hates NFS), emptyDir for caches. Full plan + per-workload assignment: [`docs/procedures/synology-storage-redesign.md`](../procedures/synology-storage-redesign.md). **Block storage is RWO/single-mount by nature** — you can't pack multiple pods onto one LUN without an FS layer (= NFS), so the cap is escaped by *not using iSCSI for everything*, not by clever LUN reuse.
- **First-deploy mkfs.ext4 on Synology iSCSI LUNs is TRIM-bound at ~10GB/min over 1GbE.** 200Gi data LUN takes ~20 min, 50Gi ~5 min, 10Gi <1 min. mkfs sits in D-state issuing discard (TRIM) commands to the LUN before laying down filesystem metadata. Symptom from the kubelet side: `MountVolume.MountDevice failed ... rpc error: code = DeadlineExceeded` retries during the formatting window. Synology's TRIM is the bottleneck — kernel is just waiting. **Diagnostic**: on the elected worker, `cat /sys/block/sdX/stat` field 14 (sectors discarded) grows ~20M sectors per minute. **Implication**: any bootstrap Job that depends on a fresh PVC must size its timeouts (`backoffLimit`, per-attempt wait loops) to the LUN size — Garage's `layout-init-job.yaml` uses `backoffLimit: 30` with 5-min waits for ~2.5h total budget against the 200Gi data PVC.
- **mke2fs "apparently in use by the system; will not make a filesystem here!" during CSI format can be transient.** Surfaced during Outline+Garage deploy: meta-garage-0 first format failed with that exact message, second retry succeeded. Likely a race between Synology LUN-init finalisation + kernel block-layer device probing. If a single retry doesn't resolve, check `lsblk -f /dev/sdX` for any lingering FS signature + `blkid /dev/sdX` for a stale UUID — wipe with `wipefs -a /dev/sdX` from a debug pod if so. Don't reach for force-format prematurely; first retry handles most cases.
- **Deleting a Synology volume (esp. the first/system volume) fails `Device or resource busy` through a chain of *invisible* holders — and DSM ships neither `lsof` nor `fuser`.** The 2026-05-30 Volume1 recreate hit **five** successive, different holders, each invisible to the tool that found the last. Work the chain in this order:
  1. **iSCSI LUN on the volume** — a LUN (even with zero active sessions) blocks removal. Delete the LUN **and** its target in SAN Manager first. (`kubectl delete pv` does NOT delete the LUN under `Retain`; it's a DSM-side delete.)
  2. **A DSM package install dir** on the volume (Tailscale was on Volume1) — uninstall or move it (Package Center → Settings → default volume to relocate the framework).
  3. **`s2s_daemon` (Shared Folder Sync) holding `@S2S`** — `systemctl stop` is NOT enough: DSM's volume-removal flow *restarts* it (new PID) mid-delete and it re-grabs the volume. **`systemctl mask --now s2s_daemon.service`** keeps it down. (Unmask + start after.)
  4. **`nfsd` holding a stale datastore `.lock`** for an NFS *client* (a stale PBS mount). nfsd is a kernel thread — its open files appear ONLY in the kernel log `VFS: opened file in mnt_point: (/volume1), file: (…), comm: (nfsd)`, never in a `/proc/*/fd` scan. Clear by killing the client's hold (reboot the PBS LXC) + letting the NFSv4 lease (~90s) expire.
  5. **An invisible `Synotify`/fanotify mount-mark** (Universal Search / `SynoFinder`). Symptom: `umount … busy` with **NO `VFS: opened file` line at all** — a fanotify `FAN_MARK_MOUNT` pins the mount but is not a file/fd. `synopkg stop SynoFinder` drops it (but DSM re-invokes the `fileindex` tool during the delete, re-arming it).
  **Diagnostic toolkit (no lsof/fuser):** `/proc` holder scan — `readlink /proc/[0-9]*/{cwd,root,exe}` + `/proc/[0-9]*/fd/*` (userspace fds), `grep -l /volume1 /proc/[0-9]*/maps` (mmaps); `dmesg | grep 'opened file'` (**nfsd** holders, invisible to the fd scan); `grep volumeN /proc/mounts` for real sub-mounts (the volume's own `subvol=/@syno` line is normal; `grep -l volumeN /proc/*/mountinfo` matches *every* process = useless false positive). **When all visible scans are clean but it's STILL busy with no `VFS` line → it's a fanotify mark or other kernel-level hold → reboot the NAS.** A reboot drops every fanotify mark + kernel hold at once and is the community-consistent fix for the "everything's clear but still busy" tail (the headless DS223J has no console, so it's the power button). The first/system volume's `@`-dirs (`@appstore`/`@database`/`@iSCSI`/`@S2S`/…) are mostly empty stubs (<1 MB; packages live on the system partition `/usr/local/packages`), so they don't *themselves* block removal — the live *services* holding them do. Full hunt: [`docs/incidents/2026-05-30-storage-redesign-nas-rework.md`](../incidents/2026-05-30-storage-redesign-nas-rework.md).
- **Moving a Synology shared folder between volumes changes its NFS export path (`/volume1/share` → `/volumeN/share`) — stale NFS clients break + can pin the old volume.** DSM's "move shared folder" copies the data then re-exports under the new volume path and removes the old export. Any client still mounting the old path gets a **stale file handle** (and, if a process holds an fd, pins the old volume so it won't delete — see above). For the PBS datastore move: after the folder move, `showmount -e <nas>` confirms the new export path; re-point the client's fstab to match, `systemctl daemon-reload && umount -f -l <mnt>; mount <mnt>`, then `df` must show NFS (not stale). **Always restore-verify** (PBS: a real backup + file restore, or a Verify job) before relying on a moved datastore. PBS services can show `active` against an *unmounted* datastore dir (boot-mount failed) — mount it, then `systemctl restart proxmox-backup proxmox-backup-proxy` to re-scan.

## local-path-provisioner (node-local tier)

Rancher `local-path-provisioner` v0.0.36 (Flux, **GitRepository** source — Rancher publishes no Helm index) provides SC `local-path` (non-default, `WaitForFirstConsumer`, `reclaimPolicy: Retain` — a released PVC must NOT wipe its node-local host dir, since the tier backs single-replica VL/VM with no app replication; the original `Delete` was a Vault-only-era choice. Tradeoff: orphan `/data` dirs after a PVC delete → occasional manual sweep per worker. Changing reclaim on a live SC = delete+recreate, it's immutable). Backs a dedicated **50G `scsi1` data disk per worker, xfs, mounted at `/data`** (separate from the OS disk → survives a VM rebuild). Provisioned by `ansible/roles/local-path-disk` + the `scsi1` disk in `terraform/proxmox/asgard-k3s`. Deployed + rolled out to all three workers 2026-05-30; now backs single-replica VL/VM **and the 3-node Vault Raft cluster** (Class-L migration off iSCSI done 2026-05-30 — vault-{0,1,2} on `/data` of urd/skuld/verd respectively).

- **SELinux: the helper pod's `mkdir` is denied on default-labeled host paths even as root.** Workers run `Enforcing`; `/opt` etc. are `usr_t`, which `container_t` can't write → PVCs hang Pending with `mkdir: ... Permission denied` then `create process timeout after 120 seconds`. **Fix: mount the data disk with a blanket `context="system_u:object_r:container_file_t:s0"` mount option** (whole-FS label — valid because the worker VMs are K3s-only; no per-dir `semanage`/`restorecon`). `s0` (no MCS categories) is reachable by every pod's `container_t:s0:cN`. Same class as the privileged-DaemonSet SELinux gotcha, solved via mount option for a single-purpose disk.
- **NEVER identify the data disk by `/dev/sdX`.** iSCSI LUNs (Vault's PVC, post-migration others) claim `sd*` letters too, and **the ordering swaps across reboots** — validated 2026-05-30: the 50G data disk was `sdc`→`sdb` on urd, `sdg`→`sdb` on verd, `sdf`→`sdb` on skuld, and pre-reboot `/dev/sdb` on urd was a *live Vault iSCSI LUN*. Identify by **stable SCSI address `/dev/disk/by-path/*-scsi-0:0:0:1`** (virtio-scsi LUN 1 = TF `interface=scsi1`; OS disk is `0:0:0:0`); iSCSI is `ip-...-iscsi-...` and can't collide. Mount by **UUID** in fstab. The `local-path-disk` role resolves by-path, skips gracefully when absent (incremental rollout / drift-check safe), and has a 40–60 GiB size-guard as defence-in-depth.
- **`ssd=true` on an existing `scsi0` disk is an in-place update in bpg/proxmox, NOT ForceNew** — verified via `terraform plan` (`0 to destroy`); gate any such change on the plan showing in-place before applying. It only takes effect on a **Proxmox-level power-cycle** (`qm reboot` = fresh QEMU process), NOT a guest `reboot` (QEMU re-reads disk config only on a new process). Canaried on urd before rolling to verd/skuld. `discard = "on"` (TRIM passthrough to LVM-thin) + periodic `fstrim.timer` (not the latency-adding online `discard` mount option) handle thin reclaim. **CP `scsi0` ssd flip still pending** (see open-questions).
- **local-path single-instance does NOT self-heal across node loss** — the PV is node-pinned (`nodeAffinity` to the worker the data lives on), so if that worker dies the pod can't reschedule elsewhere; it's down until the VM/node is restored. Availability for non-app-replicated workloads must be solved at the **app layer** (replication/clustering — Vault Raft is the model), NOT by local-path-single and NOT by storage-replication (Longhorn). **Recovery** is separate + covered: PBS daily backs up the worker VMs incl. the `scsi1` `/data` disk (`backup=1`, verified). Rule: only place app-replicated (Vault) or downtime-tolerant/refillable (VL/VM observability) data on local-path; availability-critical single-instance data needs app-level replication. Surface any iSCSI(NAS-RAID1)→local-path(single-NVMe) move as an explicit redundancy downgrade, never a footnote. See [[feedback_app_level_redundancy]].

## Storage migration (rsync static-rebind across tiers)

Cross-StorageClass data moves (the storage-redesign Class N / local-path migrations) use a quiesce → migrator-pod → rsync → static-rebind → STS-recreate pattern. Gotchas surfaced 2026-05-30 doing teamspeak/VL/VM/garage-data:

- **Migrator pod needs `privileged: true` + `runAsUser: 0` to read a source iSCSI/ext4 PVC from a *different* pod.** RHEL workers are SELinux `Enforcing`; the CRI relabels an RWO block volume to the owning pod's MCS category, so a second pod (different category) gets `change_dir "/src" failed: Permission denied` even as root. Privileged → `spc_t` (unconfined) → can read. Same class as the privileged log-collector DaemonSet.
- **`rsync -aHAX` fails on NFS/local-path dst with `lsetxattr("security.selinux") Not supported (95)` → exit 23.** NFS (and the `context=`-mounted local-path xfs) don't store per-file SELinux xattrs — the volume's context comes from the mount, not xattrs. Use `rsync -aH --numeric-ids` (drop `-A`/`-X`); add `--delete` to clean any `.fuXXXX` temp files a prior `-X` run left. Verify integrity with a **content checksum diff** (`find -type f -exec sha256sum | sort`, prune `lost+found`), NOT `du` — `du` differs by filesystem dir-block accounting (ext4 4K blocks + `lost+found` vs NFS/xfs) and looks alarming while the file data is identical.
- **Migrator pods targeting a `WaitForFirstConsumer` local-path PVC must pin with `nodeSelector`, NOT `nodeName`.** `nodeName` bypasses the scheduler, so the PVC never gets its `volume.kubernetes.io/selected-node` annotation → local-path-provisioner doesn't know where to provision → PVC hangs `Pending` → pod stuck `ContainerCreating` (`PVC is not bound`). `nodeSelector: {kubernetes.io/hostname: <worker>}` goes through the scheduler, which sets the annotation. The migrator (first consumer) provisions the local-path PV on that node, which then becomes the workload's pinned home (the PV's `nodeAffinity` forces the recreated STS pod there).
- **Static-rebind under `Retain` (NFS + the now-Retain local-path):** rsync into a temp PVC → `kubectl delete pvc <temp>` (PV → `Released`, data intact under Retain) → `kubectl patch pv <pv> --type=json -p '[{"op":"remove","path":"/spec/claimRef"}]'` → recreate the PVC under the **STS-expected name** with `spec.volumeName: <pv>`. Delete the **old** source PVC first to free the name (its iSCSI PV → `Released`/`Retain` = rollback net). A `volumeName`-pinned local-path PVC may sit `Pending` a few seconds before binding — not stuck.
- **Reconcile the Flux *source* (and the owning Kustomization / HR object) to the new manifest BEFORE the orphan-delete+recreate** — else a values/manifest race recreates the STS on the *old* VCT. For HelmReleases this manifests as an immutable-STS-VCT Helm-upgrade failure → automatic **rollback loop** (helm history shows `failed`/`Rollback to N` ping-pong). Sequence that works: push → `flux reconcile source git flux-system` → (for HR) `flux reconcile kustomization <ks>` so the HR *object* carries the new values → `kubectl delete sts --cascade=orphan` (keeps the running pod for zero-downtime adopt) → `flux reconcile hr/ks --force`. Verify the live STS VCT matches git after (`kubectl get sts -o jsonpath=...volumeClaimTemplates`).
- **VictoriaMetrics / VictoriaLogs (`victoria-metrics-single` / `victoria-logs-single`) PV storage-class value key is `server.persistentVolume.storageClassName`, NOT `storageClass`.** `storageClass` is silently ignored — a pre-existing iSCSI binding came from the **cluster-DEFAULT SC** (`synology-csi-iscsi-retain` is default), not the value. Wrong key → the rendered VCT has *no* `storageClassName` → a future PVC defaults back to iSCSI. Always set `storageClassName` explicitly + verify the rendered VCT (`helm show values <chart>` to confirm the key when in doubt).
