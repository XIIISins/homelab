# Known gotchas — Tailscale

*Migrated from `CLAUDE.md`. Recovery commands + rules. Incident retros in [`../incidents/`](../incidents/).*

## Tailscale

- **Tailscale auth keys cap at 90 days** — API hard-clamps `expiry` to 7776000s. Closest to "indefinite": `reusable = true` + `recreate_if_invalid = "always"` + `expiry = 7776000`. Set `lifecycle { ignore_changes = [expiry] }` on provider <0.29.0 (we're on 0.28.0) to avoid plan-flap. **Rebuilding a Tailscale-joined LXC 90+ days after initial mint requires `terraform apply` on the tailscale module BEFORE re-running Ansible** — otherwise Vault holds an expired key and `tailscale up` fails.
- **Tailscale `tailnet_key.description` is alphanumeric + spaces + identifier-internal hyphens only.** Rejects parens, em-dashes, slashes — generic error, bisect-the-description to debug. Safe template: `"<hostname> <tag> managed by terraform"`.
- **Tailscale subnet routers + exit nodes need `net.ipv4.ip_forward=1` AND `net.ipv6.conf.all.forwarding=1`.** `tailscale up` succeeds without; control plane's per-route-family relay check flags "cannot relay traffic." `--advertise-exit-node` implicitly advertises both `0.0.0.0/0` AND `::/0` → triggers v6 check regardless of LAN v6. v6 sysctl is kernel-state-declarative — flag set is sufficient even with link-local-only v6. Persisted via `/etc/sysctl.d/99-tailscale.conf` in the tailscale role.
- **Tailscale provider 0.28.0 DNS resource names differ from later versions.** Split-DNS resource is `tailscale_dns_split_nameservers` (one resource per `domain`), NOT `tailscale_dns_split_dns` (map-form, added in later provider versions). The provider also exposes `tailscale_dns_configuration` / `tailscale_dns_nameservers` / `tailscale_dns_preferences` / `tailscale_dns_search_paths`. **First-line diagnostic for "Invalid resource type" errors on any provider:** `terraform providers schema -json | jq '.provider_schemas | to_entries[] | .value.resource_schemas | keys[]'` lists every resource the installed provider actually supports — beats guessing from docs that drift across versions.
- **Tailscale OAuth client scopes are editable in-place via admin UI** (Settings → OAuth clients → edit). Adding a new scope to an existing client does NOT rotate the client_id/client_secret — no Vault rewrite needed. Surfaced 2026-05-24 adding `dns:write` to the existing TF OAuth client for 5e.4.
- **Tailscale DSM 7 package upgrades wipe `configure-host` TUN-permissions state.** Boot-up Task Scheduler task re-applies on next reboot — but package auto-update without reboot silently breaks subnet-router/exit-node. Diagnostic: tailnet admin shows "cannot relay traffic"; `tailscale netcheck` no relay. **Recovery:** `/var/packages/Tailscale/target/bin/tailscale configure-host; synosystemctl restart pkgctl-Tailscale.service` as root. Consider disabling auto-update in DSM Package Center.
- **Tailscale subnet-router on Synology can cut the NAS's own LAN — `--accept-routes=false` is mandatory, and auth via CLI authkey NOT the web UI.** Munin advertises the `10.0.0.0/16` supernet, which *contains* its own `10.0.254.0/24`. If the node **accepts routes** (or consumes an exit node — which blocks LAN access by default), Tailscale's policy-routing rules (`ip rule` → table 52) divert Munin's own `10.0.254.x` traffic into the tailnet *before* the local connected route is consulted → the NAS loses its LAN IP entirely while still showing **online in the tailnet** (its WAN/internet path stays up). On a Synology that cuts iSCSI+NFS to the cluster (garage crashlooped within ~1 min). **Cause is usually deviating from the documented bring-up:** the DSM package **web-UI login applies default flags** instead of the explicit advertiser-only set — Appendix D says "don't log in via the UI, authenticate with the CLI authkey." **Correct bring-up:** `tailscale up --advertise-routes=10.0.0.0/16 --accept-routes=false --accept-dns=false --hostname=munin --reset` (the `--reset` is the actual cure — wipes any stray exit-node/accept-routes flag the reinstall/UI left; `--accept-routes=false` pins the safe resting state). **Break-glass recovery (headless ARM NAS = no console):** reach it over its *Tailscale IP* (online in tailnet, dead on LAN) and `tailscale down` — restores LAN immediately; do NOT power-cycle (boot re-applies the bad saved state). After any package reinstall, also re-create the `tailscale-tun-permissions` boot-task (Appendix D Step 4) — it lives in the install dir and gets wiped. Surfaced 2026-05-30 (storage-redesign Volume1 rework forced a Tailscale reinstall). See [`docs/incidents/2026-05-30-storage-redesign-nas-rework.md`](../incidents/2026-05-30-storage-redesign-nas-rework.md).

- **Tagging an existing device / disabling its key expiry via the API (no node access needed).** With the Terraform OAuth client (`secret/k8s/tailscale/oauth-client`, scope `devices:core`): `POST /api/v2/device/<id>/tags` `{"tags":["tag:x"]}` and `POST /api/v2/device/<id>/key` `{"keyExpiryDisabled":true}` (mint a short-lived token via `/api/v2/oauth/token` inside the shell — never print it). The tag must exist in `tagOwners` and the client must be allowed to assign it. Converting a user-owned node to tagged is effectively **one-way** (back to user-owned needs re-auth on the node); peers then show owner `tagged-devices`. The device's `expires` timestamp stays **stale** in the API/`tailscale status --json` after `keyExpiryDisabled=true` — trust the flag. 2026-10-01: the DO droplet's key was due to expire 2026-11-19 until this was done.

- **`tag:burst` (10b2) is deliberately a dead end.** It is a `tagOwners` entry and the destination of one `tag:server -> tag:burst` grant, and **not a src of any grant** — burst nodes can reach nothing (not prod, not each other; cluster traffic rides the DO VPC). Frigg's reach to it also comes from the existing wide `tag:server -> *` rule; the explicit grant just survives a future narrowing. Nodes use an **ephemeral reusable** key (`tailscale_tailnet_key.burst`, Vault `secret/ansible/tailscale/authkeys/burst`) so reaped/destroyed droplets vanish from the tailnet by themselves; same 90-day cap as the LXC keys — `terraform apply` in `terraform/tailscale` before a `burst-up` after 90 idle days. Burst nodes do not `--accept-routes`, so the subnet routers' `10.0.0.0/16` never lands on them. Procedure: [`../procedures/burst-substrate.md`](../procedures/burst-substrate.md).
- **A subnet-router-fronted address is unreachable from a node that does not accept routes, even with an ACL grant for it.** `tailscale debug prefs` -> `RouteAll: false` (the default on Linux) means no route to e.g. `10.0.11.22`; `tailscale status` health shows "Some peers are advertising routes but --accept-routes is false". Fix per host with the role's opt-in `tailscale_accept_routes: true` (only emitted when true, so no diff elsewhere). Never on Synology (see the item above). Surfaced 2026-10-01 wiring the 10b3 Gatus Hermod probe on `do1`; the grant `tag:offsite -> 10.0.11.22 tcp:80` existed but timed out.
