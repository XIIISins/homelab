# Known gotchas — LXC / Proxmox (+ PVE host patching)

*Migrated from `CLAUDE.md`. Recovery commands + rules. Incident retros in [`../incidents/`](../incidents/).*

## LXC / Proxmox

- **bpg/proxmox API token can change `nesting`, NOT other LXC features.** `keyctl`, `fuse`, `device_passthrough` require `root@pam` — `device_passthrough` also at *create*-time. Workaround: aliased provider pattern (`provider "proxmox" { alias = "root", username = "root@pam" }` with `PROXMOX_VE_PASSWORD`; declare `configuration_aliases = [proxmox.root]` in `versions.tf`; resources needing these features use `provider = proxmox.root`). Don't put `keyctl: false`/`fuse: false` in resource block — they're defaults, omitting avoids future 403s.
- **`terraform import` of an existing LXC always proposes destroy-recreate** unless `lifecycle.ignore_changes` is set. The bpg/proxmox provider doesn't return `operating_system.template_file_id` (Proxmox forgets the source template after creation) or `initialization.user_account` (create-only seed) from the API on read, so post-import plan shows both as null-on-read vs the HCL spec's set value — both flagged "forces replacement", which would destroy the running container. Fix: `lifecycle { ignore_changes = [operating_system[0].template_file_id, initialization[0].user_account] }`. Works for fresh creates too — ignore_changes only suppresses diffs, values are still written at creation. Add to any resource being imported. Also include `features[0].keyctl` if the existing container has keyctl=true (community-scripts installer enables it) — switching to the root-aliased provider just to flip keyctl is heavier than the value; ignore the diff. Surfaced 2026-05-25 5b.2.b.
- **Systemd 257 in unprivileged LXC requires `nesting=true`.** Debian 13 systemd uses namespace ops needing CAP_SYS_ADMIN in user-ns. Flag name is misleading: does NOT enable nested containerization — that's preserved by `unprivileged=true`, not `nesting=false`.
- **bpg/proxmox may reboot VMs on apply — `reboot_after_update` defaults to `true`.** The provider power-cycles a VM whenever an updated attribute (disk, cpu, memory, IP state) is one it deems reboot-requiring; that is the "sometimes it reboots, sometimes not" behaviour. The CP resource sets it `true` explicitly (rolling, one `-target` at a time); the **worker resource sets `reboot_after_update = false`** (2026-10-02) so an apply can never power-cycle a node carrying Vault Raft / Victoria state — a flag that genuinely needs a power-cycle is then pending until a deliberate cordon/drain + `qm reboot`. Per-disk `backup = false` is a config-only flag (no reboot): used on worker `scsi0` to keep the OS/containerd disk (~27 GiB unique per worker) out of PBS; `scsi1` (`/data`) stays backed up. Existing snapshots age out via retention + GC (24h5m grace).
- **An LXC's `memory.dedicated` is a cap, not a reservation, and `memory.current`/`pct`/Proxmox "used" include page cache — size by anonymous + shmem, not by the headline number.** Measured 2026-10-06 on Urd: Factorio 8 GB cap / ~45 MB anon / ~1 GB peak (cache), Hugin 4 GB / ~170 MB / ~850 MB, the HAProxy+etcd trio 2 GB / 55-140 MB; every small LXC peaks at its cap because the cgroup fills it with cache and reclaims at the limit. So an over-large cap frees no host RAM when you lower it; what it buys is containment (a runaway LXC OOMs inside its own cgroup instead of the host OOM killer picking a qemu worker) and an honest committed total. **Diagnostic** (on the PVE host): `awk '/^(anon|shmem|file) /{print $1, int($2/1048576)"MB"}' /sys/fs/cgroup/lxc/<ctid>/memory.stat` next to `memory.peak`. **Exception:** database LXCs (the Patroni trio) use the cache as the working set for a ~21 GB Zabbix-dominated dataset on 4 GB; do not cut their caps on the anon number alone. VMs are different: guest cache is held by the host until ballooned/shrunk.
- **Growing an LXC's `disk.size` (bpg/proxmox) is a live, in-place `pct resize` — no container restart, no reboot.** Confirmed 2026-09-17 growing Fulla/Vör/Idunn (PG cluster, `terraform/proxmox/asgard-lxcs/lxcs.tf`) 36G→46G one node at a time: `terraform plan` shows `~ update in-place` (not a replace), applies in ~1-2s, and `systemctl show <svc> -p ActiveEnterTimestamp` on the running workload was untouched by the apply — filesystem online-grows under the running container. Contrast with VM disk grows, which can still need a guest-side rescan/fs-grow. Don't default to a maintenance window for LXC-only disk grows; do still check cluster health before/after if the LXC hosts a clustered service (Patroni, etcd).
- **Proxmox orphan LVs from a host that died mid-clone.** `qm clone` allocates destination LVs *before* writing VM config. Crash between → stranded LVs, no config to own them. Symptom on next clone at same VM ID: `lvcreate ... already exists`. Diagnosis: `qm list | grep NNNN` (no config) + `lvs | grep vm-NNNN`. Recovery: `lvremove -f /dev/pve/vm-NNNN-cloudinit /dev/pve/vm-NNNN-disk-0` (and matching LVs). If phantom config exists, prefer `qm destroy NNNN --purge`. Class: state surviving outside orchestrator view.

## Proxmox / PVE host patching (`proxmox-host-patching.yml`)

*Rolling PVE-host OS patching. Runbook: [`docs/procedures/proxmox-host-patching.md`](../procedures/proxmox-host-patching.md); decision row in [`docs/operations/decisions.md`](../operations/decisions.md) "PVE host patching".*

- **Patroni REST mutating endpoints (`/switchover`, `/failover`, `/restart`) need `restapi.authentication` — GET endpoints (`/cluster`, `/master`) are open.** A raw `uri` POST to `/switchover` from the control node fails with `Connection reset by peer` (not a clean 401) because the cluster's `restapi.authentication.username: patroni_admin` is set. **Don't POST the REST API for switchover — run `patronictl -c /etc/patroni/patroni.yml switchover --leader <name> --candidate <name> --force`** delegated to a PG node (it reads the local config incl. the restapi creds). patronictl 4.x accepts `--leader`/`--primary` aliases + `--candidate` + `--force`. GET `/cluster` polling from the control node is fine (used to confirm the leader moved). Surfaced 2026-06-18 (first PVE-patch canary halted here — safely, before any reboot).
- **An orchestrator playbook cannot live on a host it reboots.** `proxmox-host-patching.yml` is **run from the MacBook**, never Semaphore (its pod reschedules when its worker's host reboots → kills the job) or Frigg (HA cold-restarts when Verd reboots → kills the job). The playbook needs no `community.hashi_vault` lookup, so the MacBook's Python-3.14 hvac-fork crash doesn't apply. Hands-off Frigg/Semaphore scheduling is deferred (phase 2) pending a resumable per-host checkpoint.
- **A `hosts: localhost` play is silently skipped under `--limit <otherhost>`** ("skipping: no hosts matched") — `--limit` filters localhost out too. A canary `--limit urd` therefore bypassed the whole-cluster pre-flight health gate. **Fix: make controller-side gate plays `hosts: <the-targeted-group>` + `run_once: true` with the probes `delegate_to: localhost`** — then the gate is scoped to the same `--limit` as the work and always runs. (`run_once: true` is accepted at play level.) Surfaced 2026-06-18.
- **Jinja `dict.items` resolves to the dict's `items()` METHOD, not an `items` key** → `map(attribute=...)` over it errors `'method' object is not iterable`. `kubectl get … -o json | from_json` returns a dict whose node list is under the `items` key — use the **`['items']` subscript**, never `.items`. (pvesh `/cluster/resources` returns a JSON *array*, so it's unaffected — only dict-shaped `from_json` results hit this.) General Jinja footgun, not k8s-specific. Surfaced 2026-06-18.
- **Node-readiness from `kubectl … -o json` is fragile to express in Jinja** (`map('selectattr',…)|map('first')` over per-node `status.conditions` trips `'method' object is not iterable`). Cleaner: `kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}={range .status.conditions[?(@.type=="Ready")]}{.status}{end};{end}'` → emits `name=True;` pairs → parse with `.split(';') | reject('search','=True$')`. Pass the space-containing jsonpath via the `command` module's **`argv:` list form** (whitespace-splitting breaks it otherwise).
- **`--check` makes the `reboot` module report `changed` without actually rebooting**, so a `_rebooted` fact derived from `reboot.changed` goes true under `--check` → the post-reboot gates (whose `pvesh`/`kubectl` reads are check-skipped → empty stdout → `from_json` errors) wrongly fire. Gate `_rebooted` with `and (not ansible_check_mode)` so a dry-run skips the inherently-post-reboot gates. Read-only *discovery* tasks instead get `check_mode: false` so `--check` still gathers + prints the plan. Surfaced 2026-06-18.
- **`pvecm status` prints `Quorate:` with variable whitespace before `Yes`** — match with a regex (`_pvecm.stdout is search('Quorate:\s+Yes')`), not a literal `'Quorate: Yes'` substring (which never matches → always-false-fails).

## LXC reboot persistence — config that doesn't survive a container restart

*A fleet-wide reboot (PVE-host patching, 2026-06-18) re-initialises each LXC's netns/veth and re-runs container-startup file management, resetting provision-time config that VMs keep. Surfaced as 48 drift items, LXC-only — VMs + bare-metal came back clean. Retro: [`../incidents/2026-06-18-lxc-reboot-persistence-drift.md`](../incidents/2026-06-18-lxc-reboot-persistence-drift.md). Diagnostic for "drift is LXC-only after a reboot": the config was applied live at provision time but isn't re-asserted (or is overwritten) at container start.*

- **Hardened `net.ipv4.conf.*` sysctls are reset by interface bring-up, AFTER `systemd-sysctl` applies them.** In an LXC the netns is created fresh at each start (kernel defaults), `systemd-sysctl` applies `/etc/sysctl.conf` early, then the veth/eth0 coming up re-defaults `conf.{all,default}.accept_redirects`→1 and `conf.all.log_martians`→0. Only keys whose container-default differs from the hardened value drift (e.g. `accept_source_route` already defaults 0 → no drift). Symptom: `sysctl net.ipv4.conf.all.accept_redirects` = 1 despite the on-disk value being 0; `systemd-sysctl` shows active(exited) success. **Fix (hardening role):** write the keys to a dedicated drop-in `/etc/sysctl.d/60-niflheim-hardening.conf` (var `hardening_sysctl_file`) + a `niflheim-sysctl-reapply.service` oneshot `After=network-online.target` running `sysctl -p <that file>` (LXC-gated). Re-apply ONLY the drop-in — `sysctl --system` would fail on read-only `kernel.*`/`vm.*` keys in an unprivileged LXC and turn the unit into a failed-service drift signal of its own.
- **A `Type=oneshot` `ip route` unit `After=network-online.target` can still lose the boot race in an LXC.** `network-online.target` is reached before the interface has its address/route, so `ip route replace default via <gw> dev <iface>` exits status 2 ("Network is unreachable") and — with no `Restart=` — stays `failed` until the next apply (it's restarted by the keepalived role's handler). Symptom: `vlan10-policy-routing.service` failed after reboot, `ip rule` missing the source-routing rule. **Fix:** an `ExecStartPre` that polls `ip route get <gateway>` until it succeeds before touching the routing table (`roles/keepalived/templates/policy-routing.service.j2`). Note: running `ip route show table <name>` as a non-root user errors "table id value is invalid" because it can't read `/etc/iproute2/rt_tables` — a red herring; the named table is valid for root.
- **`/etc/default/locale` is a `systemd-tmpfiles` symlink, recreated every boot.** `/usr/lib/tmpfiles.d/debian.conf` ships `L+ /etc/default/locale - - - - ../locale.conf`, which force-deletes whatever's there and re-links it to `/etc/locale.conf` at each boot. A regular file written by ansible (`copy: dest=/etc/default/locale`) loses every reboot and shows perpetual drift (the symlink reads as mode 777, no content diff). **Fix:** manage `/etc/locale.conf` (the symlink target + canonical systemd locale file, also native on RHEL) — `roles/baseline/tasks/debian.yml`.
- **PVE rewrites a container's `/etc/resolv.conf` from its config at every start** — so ansible-managed resolv.conf is clobbered on reboot (perpetual drift). Without a `dns {}` block the container inherits the *Proxmox host's* `/etc/resolv.conf`. **Fix: own resolv.conf at the provision layer, not ansible.** Add `initialization { dns { servers, domain } }` to each `proxmox_virtual_environment_container` (`terraform/proxmox/asgard-lxcs/lxcs.tf`) and set `baseline_manage_resolv_conf: false` (drop the adguard role's resolv copy task for AGH). bpg applies the dns block **in-place** via `pct set` (0 replacements — confirmed by plan) but it only takes effect on the **next container start**, so reboot to validate. AGH trio gets `127.0.0.1` + a Quad9 bootstrap fallback (local resolver survives an all-AGH-down window); everyone else gets the AdGuard VIP + UCG fallback (mirrors the old `baseline_nameservers`, no redundancy downgrade). Decision row: [`../operations/decisions.md`](../operations/decisions.md) "LXC resolv.conf ownership".

## PVE HA watchdog (softdog vs hardware)

- **PVE's `watchdog-mux` defaults to `softdog` — a kernel-timer watchdog that cannot fire if the kernel itself freezes.** On a full-system hard freeze (no panic, no log) a `softdog`-backed node neither resets itself nor fences: HA can restart its guests elsewhere while the frozen node is still running. Fleet state until 2026-09-30: all three hosts on `softdog` (`/sys/class/watchdog/watchdog0/identity` = `Software Watchdog`).
- **Hardware watchdog exists but is hidden: Proxmox blacklists `iTCO_wdt` from autoload.** `/lib/modprobe.d/blacklist_proxmox-kernel-*.conf` lists every `*_wdt`, so it never loads even though `i2c_i801` already creates the `iTCO_wdt` platform device (MSI Cubi / Alder Lake PCH-P, TCO v6, 30 s heartbeat, BIOS does not set `NO_REBOOT`). Blacklist only blocks alias autoload — selecting the module by name works. **Fix:** `WATCHDOG_MODULE=iTCO_wdt` in `/etc/default/pve-ha-manager`, managed by the `proxmox-host` role (`proxmox_host_watchdog_module`, set per-host in `inventory/host_vars/<host>.yml`). No `lpc_ich` needed on this platform.
- **Never restart `watchdog-mux` to apply it.** Bouncing it while HA clients (CRM/LRM) are attached trips the watchdog and resets the node. The role deliberately has no handler; the change activates on the next reboot (use `proxmox-host-patching.yml --limit <host>`). Verify after boot: `cat /sys/class/watchdog/watchdog0/identity` → `iTCO_wdt`, `state=active`; `journalctl -u watchdog-mux -b` → `Watchdog driver 'iTCO_wdt'`.
- **`watchdog-mux` arms the device on idle nodes too** (`ha-manager status` shows `lrm <node> (idle, watchdog standby)` but `watchdog0` is `state=active`), so a hardware watchdog covers nodes with no HA resources (Skuld, Urd), not just the Frigg host.
- **Limits.** A chipset reset, not a power cut — a wedged PCH may not fire. Fallback: smart plug on local control + BIOS "power on after AC loss" (guard against false positives, maintenance windows, boot-loops). Rollout: canary on Skuld 2026-09-30 (full freezes, kernel can't catch them); promote to Urd/Verd once a real freeze is auto-recovered ([`open-questions.md`](../operations/open-questions.md)). Incident: [`2026-09-30-skuld-freeze-chart-bump.md`](../incidents/2026-09-30-skuld-freeze-chart-bump.md).

## VM disk changes via bpg/proxmox (CP OS disks, 2026-09-30)

- **`reboot_after_update = true` does NOT reboot the VM for a pending `ssd=`/disk-flag change** — `terraform apply` hot-resizes the virtual disk (2 s, VM stays up, guest sees the new size immediately) and queues `ssd=1` as Proxmox *pending* config (`qm pending <vmid>` shows `cur ssd=0` / `new ssd=1`); the guest keeps `rotational 1` until a Proxmox-level **`qm reboot <vmid>`** on the PVE host (a guest `reboot` does not apply it). So Terraform alone never completes this kind of change: plan → apply → `qm reboot`.
- **Growing a VM disk is only half the job:** after the apply, grow inside the guest — `growpart /dev/sda 4 && xfs_growfs /` (RHEL cloud image: `sda4` is the XFS root, done online, no reboot). Verify `lsblk`/`df -h /`.
- **Quorum-critical VMs (K3s CPs): apply and reboot one at a time.** An untargeted apply with pending changes on all three CPs would touch all of them at once. Per CP: gate (6/6 nodes Ready + `kubectl get --raw /readyz/etcd` = ok) → `terraform apply -target='proxmox_virtual_environment_vm.control_plane["<name>"]'` (from the main checkout) → grow fs → `qm reboot` → wait for the node to cycle NotReady → Ready and etcd ok → next CP (gondul, hlokk, sigrun last — Skuld is the flaky host). Each CP was back in ~20 s.
- Use a stable numeric compare in gate scripts: macOS `wc -l` pads with spaces, so `[ "$n" = 6 ]` silently fails — use `tr -d ' '` and `-eq`.

- **`pool_id` on an LXC is not read back and forces replacement (found 2026-10-03, 10g).** Adding `pool_id = "aiops-canary"` to the canary containers made the first plan want to destroy and recreate all three, because bpg/proxmox neither returns `pool_id` on read nor allows changing it in place. Why: the provider treats it as create-only. How to apply: put existing guests into a pool through the PVE API (`pvesh set /pools/<pool> --vms <vmids>`) and list `pool_id` in the resource's `lifecycle.ignore_changes`; a new or `-replace`d guest is still created in the pool because ignore_changes never applies to creation. Symptom: a plan that says "must be replaced ... `+ pool_id` # forces replacement" on guests that were not meant to change; stop and use this instead of applying.

- **A destroyed LXC returns 403, not 404, to a pool-scoped token (found 2026-10-03, 10g).** When a canary container is deleted it leaves its pool, so the rebuild runner's pool ACL stops covering its VMID and the refresh of `/vms/<vmid>` fails with `Permission check failed (/vms/<vmid>, VM.Audit)`; the runner then cannot plan the re-creation. Why: Proxmox checks the ACL path before it checks the guest exists. How to apply: the token user has read-only `VM.Audit` on exactly the canary VMIDs (`terraform/proxmox/asgard-pools`, `rebuild_vm_audit`); a new canary needs its VMID added to `canary_vmids`. Symptom: `terraform-failed ... Permission check failed (/vms/<vmid>, VM.Audit)` in the runner journal and "was NOT proposed: the runner did not produce a plan" in the thread.

- **Declaring ACLs as separate resources makes the user resource want to delete them (found 2026-10-03, 10g).** After the first apply the bpg provider reads the ACLs back onto `proxmox_virtual_environment_user.acl`, and the next plan shows an in-place user update that REMOVES every ACL entry not declared inline (here the runner's pool, storage and SDN grants). Why: the inline attribute is authoritative for the user resource. How to apply: when ACLs are separate `proxmox_virtual_environment_acl` resources, put `lifecycle { ignore_changes = [acl] }` on the user; read any plan that touches a user before applying it. Symptom: `~ proxmox_virtual_environment_user ... - path = "/pool/..." -> null`.

  - **Follow-up (same day): the per-VMID ACL needs the full guest role, not only VM.Audit.** Creating a container with a fresh VMID checks `VM.Config.Options` (and the other config privileges) on `/vms/<vmid>` itself, which the pool ACL does not cover until the guest exists: `terraform-failed ... Permission check failed (/vms/<vmid>, VM.Config.Options)` at apply. The runner user now has the guest role on exactly `/vms/1190`..`/vms/1192` (`canary_vmids`).

- **Destroying an LXC removes its per-VMID ACL, so the rebuild runner's next plan 403s (found 2026-10-04).** PVE deletes the ACLs on `/vms/<vmid>` with the guest. `terraform/proxmox/asgard-pools` declares `rebuild_vm` ACLs for the canary VMIDs but a `-refresh=false` plan still believes they exist (plan shows no changes). Symptom: runner `terraform-failed` with `Permission check failed (/vms/1192, VM.Audit)`. Recovery: a refreshing `terraform plan` in that module from the main checkout shows `rebuild_vm["<vmid>"] will be created`; apply it. A real dead guest is not destroyed, so only deliberate test destroys hit this.
