## Zabbix

- **Zabbix apt-repo deb URL has NO `/release/` segment.** Path is `https://repo.zabbix.com/zabbix/<major>/debian/pool/main/z/zabbix-release/zabbix-release_latest_<major>+debian<N>_all.deb` — the `/release/debian/...` variant 404s (verified against the directory listing 2026-05-25). Same pattern for RHEL/AlmaLinux subtrees: `/zabbix/<major>/<distro>/...`, no `/release/` middleware. Common source of the mistake: confusion with the upstream docs "Stable releases" section header — that's a doc heading, not a URL segment.
- **`no_log: true` on shell tasks blanks BOTH stdout AND stderr from playbook output even on failure.** Correct for tasks that interpolate secrets (PGPASSWORD env, `--password` flags), but turns failures into "task failed with no information." Don't drop `no_log` to debug — **stream the failing operation from the operator workstation instead**, bypassing ansible entirely. Pattern for DB schema loads / migrations against a Patroni-VIP-fronted backend:
  ```fish
  set -lx PGPASSWORD (vault kv get -field=value secret/ansible/<path>)
  ssh ansible@<target-host> "cat /path/to/file.sql.gz" | gunzip | \
    psql -v ON_ERROR_STOP=1 \
         "host=<vip> port=5432 dbname=<db> user=<user> sslmode=require" \
         2>&1 | tail -50
  ```
  Streams the input file from the target host through `gunzip` to the local psql client (which talks to the same VIP the role does). Stderr lands in the operator's terminal where it can be read. Pattern is reusable for ANY `no_log` task involving a file-input → command pipeline against a network-reachable service. Surfaced 2026-05-25 8c.2 deploy.
- **Zabbix factory default admin is `Admin` / `zabbix` — NOT auto-rotated from Vault.** The `server.sql.gz` schema seeds the `users` table with `Admin` + bcrypt(`zabbix`). The `zabbix-server` role's `zabbix_admin_password_vault_path` is the POST-rotation value the operator MUST set via the UI after first login — it's not pushed to the DB by any task today (8c.7 plan: Ansible+API rotation post-deploy). Workflow: log in once as `Admin`/`zabbix`, change password via UI to the Vault-stored value, IaC truth converges. Don't try to log in with the Vault value before the manual rotation — Zabbix will reject + lock the account after 5 attempts.
- **Zabbix 5-attempt lockout → SQL unlock.** Zabbix locks any user after 5 consecutive failed login attempts. Stored in the `users` table; clear via psql against the Patroni VIP:
  ```sql
  UPDATE users SET attempt_failed=0, attempt_clock=0, attempt_ip=''
  WHERE username='Admin';
  ```
  Generic across users + Zabbix 6.0/7.0 LTS as of writing. Pair with the `secret/ansible/postgres/zabbix-password` Vault value for psql auth.
- **Default "Zabbix server" host needs renaming to match the agent's `Hostname=`.** `server.sql.gz` ships a default monitored host literally named `Zabbix server` with `Agent interface: 127.0.0.1:10050`. The `zabbix-agent` role configures local agent2 with `Hostname={{ inventory_hostname }}` (e.g. `hugin`). Hostname mismatch → agent's data is dropped → UI shows "no data" / red. **Fix:** Data collection → Hosts → click `Zabbix server` → set *Host name* to match the agent → Update. The 8c.7 auto-registration action will supersede this for OTHER hosts; the local agent on the Zabbix server itself still needs the manual rename on first deploy unless the role also creates an auto-registration action.
- **Debian's nginx default-site shadows app server blocks for unmatched Host headers.** `nginx` package on Debian ships `/etc/nginx/sites-enabled/default` listening on `*:80 default_server`. Any app's server block that doesn't have `default_server` set will lose Host-header-mismatch traffic to the welcome page. App packages (zabbix-nginx-conf included) install their server blocks via `/etc/nginx/conf.d/` but don't touch `sites-enabled/default` — that's an operator step. **Fix:** remove `/etc/nginx/sites-enabled/default` via Ansible `file: state=absent` + notify `restart nginx`. `sites-available/` left intact so re-enabling is a one-symlink revert. Now applied in `roles/zabbix-server/tasks/web-config.yml` — same fix applies to any nginx-fronted app role.

- **"Linux: Load average is too high" is meaningless inside an LXC and is muted fleet-wide for LXCs (2026-10-06).** `system.cpu.load` in a container is the Proxmox HOST's load average while `system.cpu.num` is the container's own (1-2) CPU count, so any busy neighbour on the shared host pushes every LXC over the stock `{$LOAD_AVG_PER_CPU.MAX.WARN}` (1.5) and the Average-severity trigger routes straight to Hermod. Fix: `group_vars/asgard_lxcs.yml` sets `{$LOAD_AVG_PER_CPU.MAX.WARN}=1000` through the role's `zabbix_agent_class_macros` (merged into the host record by `register-host.yml`), so VMs (K3s nodes, Frigg) keep 1.5. **The `asgard_lxcs` group must exist in the NetBox inventory, not just in `hosts.yml`** (see the next entry); `netbox.yml` builds it from the VMID custom field (1101-1199). Do NOT put it in `zabbix_agent_host_macros` on a parent group: child groups that define that var (postgres, haproxy_etcd, proxmox) replace the list wholesale and would drop it. The trigger is muted by macro, not deleted, so existing hosts pick it up on the next `zabbix-agent.yml` run (`--tags zabbix-agent:register` is enough); a still-open problem clears on the next evaluation. Host-level load stays covered on urd/verd/skuld by the same template, and per-container pressure by "High CPU utilization".
- **SMART NVMe temperature thresholds are raised to 75 (warn) / 85 (crit) on the Proxmox hosts (2026-10-07).** The trigger exists only on urd/verd/skuld (the SMART template is linked to nothing else), so it is a real sensor, not the LXC shared-host problem. Stock 50/65 left every node in a permanent "too high" warning and the Average-severity "critical" flapped on urd's short spikes (30 Hermod pages in 7 days; hourly max 74 C, hourly average 59 C). Set in `group_vars/proxmox.yml` `zabbix_agent_host_macros`, NOT a global macro: Zabbix resolves host, then template, then global macros, and the SMART template defines these two itself, so a global value never wins (this also means the S4 `zabbix_global_macros` only restate the template defaults for any macro a linked template defines). 85 equals verd's own critical composite threshold (urd 95, skuld 90), so a page there means the drive is about to throttle. Drive lifetime counters worth watching: urd's Lexar NM790 reports 194 min above its 95 C critical threshold, verd's Samsung 970 EVO 46 min at 85 C.
- **A `group_vars/<group>.yml` only applies under Semaphore if NetBox PRODUCES that group (2026-10-07).** Semaphore passes `-i ansible/inventory/netbox.yml` explicitly, which bypasses `hosts.yml`; NetBox builds groups only from `ansible:<group>` tags (plus the `groups:` expressions in `netbox.yml`). A group that exists only in `hosts.yml` (e.g. `asgard_lxcs`, a parent of the LXC groups) is silently empty there: the first LXC load-average fix passed on the Mac (its static snapshot merges `hosts.yml`) and then did nothing in `asgard-apply` / `asgard-fleet-agents`, whose register step reported `ok`, not `changed`, for every LXC. Worse, `zabbix_host` converges the host's macros to the declared list, so a Semaphore run with the group missing strips a macro an operator run added. **Test group_vars against the NetBox-only chain** (`ansible-inventory -i netbox.yml --graph <group>` / `--host`, in a scratch copy without `vault.yml`), never the merged `inventory/` dir, and expect `changed` for the new macro on the first Semaphore run after merge. `asgard_lxcs` is now a `groups:` expression in `netbox.yml` keyed on the VMID custom field, because the NetBox `lxc` tag exists but is applied to no VM.

- **The stock "PostgreSQL by Zabbix agent 2" template collects replication lag and streaming status but ships NO trigger on either (found 2026-10-09).** Replica loss was therefore silent in the 2026-10-06 Fulla incident. The `Patroni replication` template (`playbooks/files/zabbix/patroni-replication.yml`, linked in `group_vars/postgres.yml`, imported by `zabbix-host-groups.yml`) adds two Average triggers (so they reach Hermod `alert`, not the diagnosis agent): replay lag at or above `{$PATRONI.REPL.LAG.MAX.SEC}` (900 s = 15 min) for 3 samples, and a replica not streaming for `{$PATRONI.REPL.DOWN.TIME}` (15m). Change a threshold with a host macro in `group_vars/postgres.yml`, not by editing the template. Why two triggers: `pgsql.replication.lag.sec` reports 0 when the receive and replay LSNs are equal (as understood from the agent2 plugin; confirm with `zabbix_agent2 -t` on a replica), which is what a replica that lost its slot looks like, so lag alone cannot see a dead stream. The template's items use the stock keys minus the optional 4th (database) parameter, because two linked templates cannot define the same key on one host. Deploy: `ansible-playbook playbooks/zabbix-agent.yml --limit postgres` (the imported bootstrap play creates the template before register-host links it); a template-only change is `--tags zabbix-agent:patroni-template,zabbix-agent:register`. Verify after deploy: the template shows `Patroni replication` on all three PG hosts, both items are supported (lag 0 / status 2 on the leader, 0 / 1 on replicas), and the leader's status item reads 2 so neither trigger can fire there.
- **A Zabbix template added in git must exist in Zabbix BEFORE the first play that registers a host linking it (2026-10-10, task 2591).** `register-host` links templates by name, and the template is created by the `zabbix-host-groups.yml` bootstrap. That import used to run only inside `asgard-zabbix.yml` (late in `site.yml`) and the standalone `zabbix-agent.yml`, so the first `asgard-apply` after adding `Patroni replication` failed "Register host in Zabbix" on fulla/vor/idunn (censored by `no_log`), with the `asgard-postgres` play ahead of `asgard-zabbix`. Self-healed by the 04:30 `asgard-fleet-agents` run (it goes through `zabbix-agent.yml`, so the bootstrap runs first). Fix: `site.yml` now imports `zabbix-host-groups.yml` before `asgard-k3s.yml`. Diagnostic when it recurs: `template.get` for the template name returns empty, and every host that links it fails at the register task while hosts without it are `ok`. A Zabbix outage now fails `site.yml` at the first play instead of at the first register, which was already fatal for any host it touched.

## AIOps canary smoke-test template (10f)

- **A fault that is only Average never reaches Gná.** The agent path receives High and Disaster only, and the stock "Zabbix agent is not available" trigger is Average, so stopping an agent or a unit on a canary produced no diagnosis (found 2026-10-03 on the first soak fault). Why: the 10d filter is deliberate (Average is Hermod-only). How to apply: soak faults come from the `Canary smoke test` template ([`canary-pool.md`](../procedures/canary-pool.md)); do not weaken the filter for real hosts. Symptom: Zabbix logs "interface unavailable" for the canary but the Toolbelt journal shows no `leader` event.
- **Do not name a trigger "temporary" or "safe to ignore".** The agent reads the trigger name and description as evidence: a hand-made soak trigger with that wording made it conclude the alert was ignorable and propose nothing. Why: trigger text is untrusted input to the model but still steers it. How to apply: smoke triggers are named `Canary smoke: <what is wrong>`, and routing maps the service-fault ones to `RB-UNIT-STOPPED-T1`.
- **Two linked templates cannot define the same item key on one host.** The smoke template therefore uses keys the stock template lacks (`vfs.file.exists[...]` on its own paths, `systemd.unit.info[vlagent.service,ActiveState]`) and a `nodata()` heartbeat instead of re-declaring `zabbix[host,agent,available]`. Symptom of getting it wrong: the host record update fails with "item already exists" when linking.

- **A dead guest needs a trigger that does not depend on the guest.** Every agent-based item (heartbeat, `systemd.unit.info`) stops with a stopped container, so only `nodata` fires, and as the Average-class lesson above shows, the stock trigger does not reach Gná. The smoke template adds `icmpping[,3]` (a SIMPLE check executed by the Zabbix server via `fping`) with `Canary smoke: guest unreachable (ICMP ping loss)` (High). Known limit: the heartbeat trigger fires as well, so one dead guest is two High problems (the Toolbelt correlates them per host). Routing: the guest trigger must stay ahead of `zbx-host-unavailable` in `aiops/alert-routing.yml`, whose `unreachable` pattern would otherwise name `RB-HOST-HARD-FREEZE`. Symptom if `fping` is absent on Hugin: the item is unsupported and the trigger never fires. See [`canary-pool.md`](../procedures/canary-pool.md).

## Zabbix agent + API automation (8c.8 + Round 2)

- **`community.zabbix` 4.x requires the httpapi connection plugin — env vars are 1.x/2.x legacy and rejected.** Symptom: `Module failed: socket_path must be a value` (httpapi connection wasn't initialized → no socket). Pattern: delegate the module call to an inventory host representing the Zabbix server, override connection at task scope. Example shape:
  ```yaml
  - community.zabbix.zabbix_host: { ... }
    delegate_to: "{{ zabbix_agent_api_delegate }}"
    vars:
      ansible_connection: httpapi
      ansible_network_os: community.zabbix.zabbix
      ansible_httpapi_port: 80
      ansible_httpapi_use_ssl: false
      ansible_user: ansible
      ansible_zabbix_auth_key: "{{ lookup('community.hashi_vault.vault_kv2_get', '...').secret.value }}"
      ansible_zabbix_url_path: ""
  ```
- **`delegate_to: localhost` inherits the play-level `become: true` and triggers sudo on the workstation.** Operator's user has no passwordless sudo → task hangs with `sudo: a password is required`. Combined with `no_log: true` (correct for token-bearing tasks), every host fails with zero diagnostic info. **Fix:** explicit `become: false` on delegated tasks. The control-node-side API call has no need for root. **Debug recipe when no_log is masking errors:** `ANSIBLE_NO_LOG=False ansible-playbook ... --limit <one-host>` shows the real error.
- **Zabbix host.create / hostgroup.create APIs don't handle the default 5 parallel ansible forks cleanly.** Roughly 1/5 succeed, the rest fail with the underlying error masked by `no_log: true`. **Fix:** `throttle: 1` on the offending task scopes to one concurrent execution across the play while leaving the rest of the playbook at full parallelism.
- **Zabbix "Admin role" doesn't grant global host visibility — system automation needs "Super admin role".** Admin grants admin-level perms only WITHIN host groups the user has been explicitly granted access to (via user-group → host-group mappings). With no usrgrps assigned and Admin role, the user can authenticate but `host.get` returns empty + `host.create` fails with permission denied. Assign **Super admin role** for any user owning an API token used by system automation.
- **Module is `community.zabbix.zabbix_group`, NOT `zabbix_hostgroup`** despite the parameter being `host_groups`. ansible-doc disambiguates; the bare guess from the Zabbix UI term gets "couldn't resolve module/action."
- **`set_fact` with `run_once + delegate_to: localhost` scopes the fact to localhost only.** Target hosts don't see it; subsequent task interpolation of `{{ <fact> }}` errors with "is undefined." **Fix:** inline the lookup directly in the task's `vars:` block. `lookup()` always runs on the controller regardless of delegation; no per-host fact pre-population needed.
- **Pre-tasks (e.g. host-groups bootstrap) need `group_vars/all/`, not role defaults.** Pre-tasks run BEFORE the role is loaded, so role-default vars aren't in hostvars yet. Symptom: `'zabbix_agent_api_delegate' is undefined` on the bootstrap play. **Fix:** API connection vars (delegate host, port, ssl, user, token vault path) live in `group_vars/all/zabbix.yml`; the role still declares the same keys as documentation + standalone-use fallback. group_vars/all wins per Ansible's variable precedence.
- **`include_tasks` doesn't propagate `--tags` to inner tasks** without `apply: tags:` — already documented above (this session reinforced it). Caught during the zbx_monitor provisioning re-run: include statement ran (loaded users.yml) but inner postgresql_user task silently no-op'd because it didn't inherit the tag. **Fix:** `apply: tags: [...]` on the include. Applied to `postgres-common/tasks/main.yml`.
- **agent2 plugin packages ship separately on Debian** (and similarly named on RHEL). Base `zabbix-agent2` package doesn't bundle the PG/Redis/MySQL/Oracle/etc. plugin binaries. Without `zabbix-agent2-plugin-postgresql`, PG items return `Unknown metric pgsql.<…>` in unsupported state. Override `zabbix_agent_packages` in per-group group_vars (e.g. `postgres_hosts.yml` adds the plugin package). Same applies to Redis/MySQL/Memcached/Oracle templates — each needs its own plugin package.
- **`community.postgresql.postgresql_user` has NO `groups` arg** despite the parameter name suggesting it. To grant predefined-role membership (e.g. `pg_monitor` for the Zabbix monitoring user), follow with a separate `community.postgresql.postgresql_membership` task. `subelements('groups', skip_missing=True)` lets the membership loop iterate (user, group) pairs while users that don't declare `groups` pass through unchanged.
- **`bpg/proxmox_virtual_environment_user_token.value` returns the FULL `USER@REALM!TOKENNAME=UUID` string** (designed for direct use as `Authorization: PVEAPIToken=<value>`). Passing the full string into the Zabbix `{$PVE.TOKEN.SECRET}` macro produces `Authorization: PVEAPIToken=USER@REALM!TOKENNAME=USER@REALM!TOKENNAME=UUID` → 401 on every scrape. **Fix:** `element(reverse(split("=", value)), 0)` extracts just the UUID (safe because the token_id portion contains no `=` and the UUID is hex+dashes).
- **PG 17 split `pg_stat_bgwriter` into `pg_stat_bgwriter` + `pg_stat_checkpointer`** views. The `PostgreSQL by Zabbix agent 2` template targets the older single-view shape; `pgsql.bgwriter` master item returns `Unknown metric` on PG 17. Upstream issue, not actionable in IaC. 6 items unsupported per PG cluster (master + dependents × 3 hosts). Cosmetic; the rest of the template still works.
- **Shell-variable interpolation through `ansible -a` is a secret leak vector.** `PW=$(vault kv get ...); ansible host -a "cmd --secret \"$PW\""` looks safe (inline fetch into local shell var) but ansible's adhoc module echoes the command back in its output with the substituted value, leaking the secret to the transcript. Verified twice in 8c.8 work — zbx_monitor PG password leaked via `zabbix_agent2 -t pgsql.ping[...]`. Rotated via TF `-replace=random_password.<name>`. **Rule:** avoid local shell variable interpolation when the value is sensitive. Use `community.hashi_vault.vault_kv2_get` lookups in a real task with `no_log: true`, or stream a Vault lookup into the remote command server-side.
- **Zabbix unsupported items retry at a 10-minute cadence by default.** Items that recover (e.g. after a missing plugin gets installed) don't immediately flip to OK — they wait for the next retry. To force immediate recheck via API:
  ```json
  {"jsonrpc":"2.0","method":"task.create",
   "params":[{"type":6,"request":{"itemid":"..."}}],"id":1}
  ```
  Type 6 = "Check now." Use this when iterating; otherwise just wait.
- **`Etcd by HTTP` template is server-side (item type 19), NOT agent-side.** Zabbix server (hugin) fetches `{$ETCD.SCHEME}://{$ETCD.HOST}:{$ETCD.PORT}/metrics` directly. With our HTTP-only etcd config on VLAN 11 (no client TLS), server-side scrape Just Works. `{$ETCD.HOST}` resolves to `{{ ansible_host }}` per host so the server hits the right node each scrape. If etcd were TLS-only, this template would need cert handling that gets complex; the homelab's HTTP-only etcd makes it trivial.

- **The official `Proxmox Backup Server by HTTP` Zabbix template requires Zabbix 7.2+ — it does NOT ship in 7.0 LTS.** (The `Proxmox VE by HTTP` template ships much earlier and IS on 7.0 — don't conflate the two.) We run 7.0 LTS deliberately, so PBS backup-failure monitoring rides the Wave-S4 `infra-health-check.yml` prober (`GET /api2/json/nodes/localhost/tasks?errors=1` with a `PBSAPIToken=<id>:<secret>` header) rather than the stock template. PBS also has its OWN API/token system (`proxmox-backup-manager user generate-token`), separate from the PVE API — `bpg/proxmox` cannot mint a PBS token, and `terraform/proxmox/zabbix-access/` (which mints the PVE monitoring token) doesn't cover it. Surfaced 2026-05-31 Wave S4.
- **Disk-usage trigger thresholds are set via global macros, not stock-template defaults.** `group_vars/all/zabbix.yml` `zabbix_global_macros` pins `{$VFS.FS.PUSED.MAX.WARN/CRIT}` + inode equivalents fleet-wide (applied by `playbooks/zabbix-host-groups.yml` via `zabbix_globalmacro` in the run_once global-bootstrap play); per-host-class overrides go in each group's `zabbix_agent_host_macros` (e.g. postgres is tighter — full PG disk = WAL-write failure = outage). The stock "critically low" trigger (fires at `PUSED.MAX.CRIT`) is **Average** severity → routes to Hermod via the bitmask-56 media-type; the "low" trigger (`WARN`) is **Warning** → below the Hermod cutoff, stays in the UI. Surfaced 2026-05-31 Wave S4.
- **`community.zabbix.zabbix_globalmacro` `macro_type` wants the STRING `text`/`secret`/`vault`, NOT the integer `0`** — despite the ansible-doc EXAMPLE showing `macro_type: 0`. Passing `0` fails with `value of macro_type must be one of: text, secret, vault, got: 0`. Another entry in the community.zabbix module-shape-surprise class; trust the error's allowed-values list over the doc example. Surfaced 2026-05-31 Wave S4.

## Wave-S4 active prober (`infra-health-check.yml`)

<!-- runbook: RB-S4-PROBER-ERRORED -->
- **The S4 observability gaps are closed by an active Semaphore prober, NOT Zabbix triggers.** `ansible/playbooks/infra-health-check.yml` runs `hosts: localhost` in the Semaphore pod (every 12h, `45 6,18 * * *`) and actively checks: Cloudflare token validity (`/user/tokens/verify`), served-cert expiry per wildcard zone (`community.crypto.get_certificate` against FQDNs with a CoreDNS rewrite so the pod reaches Traefik, not the unreachable MetalLB VIP), Patroni REST `/cluster` health (defence-in-depth for the `on_role_change` callback — which can't fire if the node holding it died), etcd `/health`, and PBS failed-tasks. It POSTs findings to `HERMOD_URL` (`critical`→Hrist, `alert`→Mist), is **silent on a clean run**, and a play-level `rescue` POSTs `critical` if the prober itself errors (a silent prober is worse than a noisy one). The `hermod_summary` callback no-ops for non-drift/apply wrappers, so it does NOT double-post. Deploy + non-destructive synthetic-failure validation matrix: [`docs/procedures/s4-observability-validation.md`](../procedures/s4-observability-validation.md).
- **Jinja `|` binds tighter than `+` — list concatenation feeding `| join` needs parens.** `['a',''] + (x | map | list) | join('\n')` parses as `['a',''] + ((x|map|list)|join)` → list+string TypeError. Write `(['a',''] + (x | map | list)) | join('\n')`. Bit the prober's Hermod-body construction; generic Jinja gotcha.
- **A `hosts: localhost` HTTP/Vault prober needs explicit `become: false`.** The control-node `ansible.cfg` (and the Semaphore pod) default `become: true`, so every task — including a localhost `uri` call — tries to sudo and dies with `sudo: a password is required`. Set `become: false` at play level for any pure-API/localhost playbook. Surfaced 2026-05-31 Wave S4 deploy.
- **Ansible `uri` only populates `.json` when the response `Content-Type` is `application/json`.** etcd's `/health` returns `Content-Type: text/plain` (the body IS JSON), so `.json` is undefined and a `selectattr('json', 'defined')` filter silently drops every node → false-positive "etcd quorum LOST" against a healthy 3/3 cluster. Parse `.content | from_json` instead when the endpoint mislabels its content-type. (Patroni `/cluster` + the PBS API both send `application/json`, so `.json` is fine there.) Surfaced 2026-05-31 Wave S4.
- **Hermod's Caddy IP-allowlist 403s any POST from a non-producer source** (e.g. the operator's control node). Hermod delivery can therefore only be validated from an allowlisted source — the Semaphore pod, Zabbix (hugin), or the Patroni nodes. To validate the prober's delivery, trigger the Semaphore template (allowlisted) rather than running the playbook from the control node (which 403s at the POST). Surfaced 2026-05-31 Wave S4.
- **The Semaphore task-start API honours an `environment` extra-vars override even when `allow_override_args_in_task = false`** (that flag gates CLI args, not the environment/extra-vars JSON). `POST /api/project/<id>/tasks` with `{"template_id": N, "environment": "{\"var\":\"val\"}"}` injects `-e` vars — used to drive a synthetic failure (bogus token Vault path + `cert_warn_days=9999`) through the real scheduled path without touching production secrets. Surfaced 2026-05-31 Wave S4.

## Zabbix SAML SSO (8c.3–8c.6)

- **`community.zabbix.zabbix_user_directory` (v4.x) flattens SAML fields onto the module itself — NOT nested under a `saml:` block.** Error against a nested-shape draft: `Unsupported parameters for ... module: saml. Supported parameters include: ... idp_entityid, sso_url, slo_url, sp_entityid, username_attribute, nameid_format, sign_messages, ...`. The supported-parameters list in the error itself is authoritative; quick first-line check before drafting any new module call: `ansible-doc community.zabbix.zabbix_user_directory` shows the actual shape. Same advice applies to any community-collection module whose docs may lag the installed version. Surfaced 2026-05-26 5h.2/8c.4 deploy.
- **`provision_groups` entry key is `role`, NOT `role_name`.** `community.zabbix.zabbix_user_directory` errors with `missing required arguments: role found in provision_groups` if the key is `role_name`. The Zabbix UI surfaces the field as "User role", which makes `role_name` the intuitive Ansible-side guess — but the module's parameter name is the bare `role`. Same first-line check: `ansible-doc`.
- **`disabled_usrgroup` is required whenever `ldap_jit_status` OR `saml_jit_status` is enabled** on `community.zabbix.zabbix_authentication`. Error: `'disabled_usrgroup' must be provided if 'ldap_jit_status' or 'saml_jit_status' enabled`. Pin to Zabbix's built-in `Disabled` usergroup (ships with the schema, no permissions) unless you have a real reason for a different parking spot. JIT'd users whose IdP-side group membership stops matching the `provision_groups` mapping land here.
- **`authentik_provider_saml.sign_response` defaults to `false`** — Authentik signs only the inner Assertion, not the outer Response. Zabbix's `userdirectory_saml.sign_messages: true` requires the Response signed too, and the login error is the unambiguous `Response is not signed and SP requires signed response.` Set `sign_response = true` explicitly on every `authentik_provider_saml` resource (TF default is the Authentik default = false). Generalisation: any SP that asks for "signed messages" needs `sign_response = true` on the IdP side.
- **`authentik_provider_saml` URL attributes return literal `"-"` until `terraform apply -refresh-only` after the initial apply.** Zabbix DB ends up with `sso_url = "-"` / `slo_url = "-"` → login errors with `idp_sso_url_invalid, idp_slo_url_invalid`. Workaround: after the first apply of any new SAML provider, run `terraform apply -refresh-only -auto-approve` to re-read the provider's `url_sso_redirect` / `url_slo_redirect` (which populate once the Application bind is fully realised IdP-side), then a regular apply propagates real URLs into Vault/downstream. Pattern carries for every new SAML provider; couldn't reproduce as a fresh-apply quirk for OIDC providers in the same module, only SAML.
- **`authentik_provider_saml` computed URLs use the default-brand apex hostname, NOT the resource's `issuer` value.** Even with `issuer = "https://authentik.midgard.xiiisins.com/"` hardcoded, `url_sso_redirect` returns `https://authentik.xiiisins.com/...`. Both hostnames reach the same Authentik backend (CF tunnel + AGH rewrite), and the SAML Response's `Issuer` claim still uses the TF-hardcoded `issuer` (which Zabbix's `idp_entityid` matches), so the cross-hostname shape works end-to-end. Cosmetic, but worth knowing when the URL-vs-issuer hostnames don't match in the resulting Vault entry.
- **`authentik_provider_saml.acs_url` is a single string, NOT a list.** Service Providers like Zabbix whose frontend bakes the request's Host header into the AuthnRequest's `AssertionConsumerServiceURL` can only succeed from one canonical hostname. Picking the apex (`hugin.xiiisins.com`) makes WAN clients via cloudflared work directly; LAN clients can reach the same hostname via public Cloudflare → tunnel → Traefik backchannel without any extra config. The midgard alias remains live for non-SAML browsing (backdoor scenario where someone's logged in via Internal auth on `hugin-direct.niflheim`) but SAML login from `hugin.midgard.xiiisins.com` fails by design with `ACS URL ... doesn't match Provider ACS URL`. Workarounds if it becomes friction: (a) drop the midgard alias entirely for the affected app, (b) Traefik redirect midgard→apex on the affected HTTPRoute. Neither is needed for Hugin currently.
- **Reverse-proxy SAML SP: nginx must reflect `X-Forwarded-Proto` into PHP's `HTTPS`** or the SP builds `http://...` ACS URLs that the IdP rejects. Pattern in `roles/zabbix-server/templates/nginx.conf.j2`: `set $forwarded_https "off"; if ($http_x_forwarded_proto = "https") { set $forwarded_https "on"; }` at server-block scope + `fastcgi_param HTTPS $forwarded_https;` in the PHP location. Backdoor (no XFF header) stays `off`, which is correct for the plaintext path. Generalisable to any reverse-proxied PHP app that generates absolute URLs from `$_SERVER['HTTPS']` — Zabbix, NetBox-pre-4.6, older WordPress, etc.
- **`username_attribute` must match an actually-attached property mapping's `saml_name` — NOT an arbitrary URN that looks plausible.** Draft default `http://schemas.goauthentik.io/2021/02/saml/uid` referred to a `uid` property mapping that the TF provider never attached (we only attached email/name/upn/groups). Error: `parameter "https://schemas.goauthentik.io/2021/02/saml/uid" is missing from user attrs` (Zabbix's frontend rewrites the scheme to https in the error rendering). Diagnostic: `curl https://authentik.midgard.xiiisins.com/api/v3/propertymappings/provider/saml/?managed=goauthentik.io%2Fproviders%2Fsaml%2F<slug> -H "Authorization: Bearer $AUTHENTIK_TOKEN" | jq '.results[].saml_name'` gives the actual emitted attribute name for each mapping slug. Default property-mapping saml_names as of Authentik 2026.2.x:
  - `email` → `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress`
  - `name` → `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/name`
  - `upn` → `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/upn` (expression falls back to user.email when no UPN attribute set)
  - `groups` → `http://schemas.xmlsoap.org/claims/Group`
  Pick the one whose semantic matches the SP's `username_attribute`. For email-rooted usernames, UPN is the right choice (falls back to email, stable).
- **Ansible role template-render tasks need explicit tags for `--tags <feature>` to re-render them.** Class-of-issue: a feature pass (`--tags zabbix:saml`) writes new files (cert PEMs) but the config file that references them (`zabbix.conf.php`, `nginx.conf`) lives behind a `web-config.yml` whose tasks have no tags → `--tags zabbix:saml` skips the re-render entirely + the certs sit there inert. **Rule**: any config-file render whose content varies by feature toggle must be tagged with every feature toggle that flips its output. Pattern: `tags: [zabbix, zabbix:web-config, zabbix:saml, zabbix:saml-conf]` on the conf.php render + same with `zabbix:saml-nginx` on the nginx.conf render. Surfaced twice this deploy — once for conf.php (commit 71abdbd), once for nginx.conf (commit 2ab39d0).
- **First-deploy debugging hostility from `no_log: true` on declarative API tasks is severe.** All 4 community.zabbix module-shape findings (5ef72f1, 4d70db4, 62ea3e8, 2e0bcce) hit the same blank-failure pattern — task fails with zero context because `no_log: true` masks both stdout AND stderr. For first-deploy passes against documented schemas, run with `ANSIBLE_NO_LOG=False` to surface module-level errors. The role's `no_log: true` is correct steady-state (auth tokens in `vars:` block), but flip it via env var during validation iterations. Existing Zabbix gotcha "`no_log: true` blanks both stdout AND stderr from playbook output even on failure" already documents the rule; this deploy reinforced it × 4.

- **Apprise YAML schema — URL is the dict KEY, not a `url:` field.** Load-bearing rule that silently fails when wrong: every URL in the `urls:` list is a dict KEY, with options (incl. `tag`) nested under it as a list of single-key dicts. URL-as-string-with-sibling-fields is rejected with the cryptic chain `Ignored entry url found under urls, entry #N` → `Unsupported URL, entry #N` → `Failed to load Apprise configuration from memory://` → `There are no service(s) to notify`. AppriseAPI returns HTTP 424 to the producer. **Two valid shapes**:
  ```yaml
  # Tagged routing — URL is dict key, tag-options nested as list-of-single-key-dicts
  urls:
    - discord://id/token/?format=markdown&username=Hrist:
        - tag: critical
    # Untagged fallback — bare URL string, no nested options. Matches notifications
    # with no `tag` field. POSTs tagged critical/alert/media don't also land here.
    - discord://id/token/?format=markdown&username=Hel
  ```
  **Wrong shape that silently breaks**:
  ```yaml
  urls:
    - url: discord://...    # ← rejected ("Ignored entry url found under urls")
      tag: critical         # ← rejected ("Ignored entry tag found under urls")
  ```
  Surfaced 2026-05-25 5h.2 first-deploy after initial Vault values were correct; cost one playbook iteration before the cause was visible in `journalctl -u apprise-api`. Design doc + role template both updated.
- **AppriseAPI config-key in `/notify/<key>` URI leaks via access logs.** Both Caddy's JSON access log and gunicorn's access log echo the full request URI verbatim. Both ship to VictoriaLogs via vlagent → the soft-auth config-key is queryable in VL. **The Caddy IP allowlist is the *only* real access gate**; the config-key buys nothing additional once logs reach a queryable system. For homelab posture (VL is Authentik-gated), this is acceptable — anyone with VL access is already inside the trust boundary. Mitigations exist (Caddy log redaction filter, gunicorn `--access-logformat` override stripping the path) but aren't justified by the current threat model. **Revisit if** Hermod ever gets fronted publicly (Cloudflared) or VL access scope changes; proper fix at that point is HTTP Basic via Caddy's `basicauth` matcher or HMAC-signed payloads, not the URI key.

## Proxmox VE template — guest memory false-positives (QEMU discovery disabled)

- **The "Proxmox VE by HTTP" per-VM/LXC memory triggers are cache-inclusive → false-fire on healthy Linux guests.** `proxmox.qemu.mem` (and `proxmox.lxc.mem`) are computed host-side as `total − MemFree`, so the guest's reclaimable page cache counts as "used." An idle Linux VM fills free RAM with cache and pegs ~90–97%, tripping the stock `high memory usage (over 90%)` trigger (`{$PVE.VM.MEMORY.PUSE.MAX.WARN}` / `{$PVE.LXC.MEMORY.PUSE.MAX.WARN}`, both default 90) even though real headroom is fine. **Proven**: warming a VM's page cache drove Proxmox `mem` 74%→86% while the guest's `MemAvailable` (real headroom) didn't move. The *accurate* signal is the in-guest agent's `vm.memory.utilization` (MemAvailable-based). **No VM setting fixes the host-side number** — virtio-balloon (`memory.floating`) only makes it *live*; Proxmox still reads `total − MemFree`, so it re-creeps to ~90% as cache refills (balloon was tested and rejected). **Decision (2026-06-27):** monitor VMs only via their own Zabbix agent — **QEMU (VM) discovery is disabled** on the template, LXC memory trigger neutralised (`{$PVE.LXC.MEMORY.PUSE.MAX.WARN}=100`). Node/LXC/Storage/Cluster discovery kept (genuine PVE-only signals). Reproducible in `playbooks/zabbix-proxmox-template-tuning.yml` (imported by `asgard-zabbix.yml`); see [decisions.md](../operations/decisions.md).
- **PVE memory triggers have `manual_close=0` → a stuck false problem can ONLY be cleared by removing the discovered entity.** You can't acknowledge-close them via API, and a *disabled* LLD rule stops feeding data so the trigger never re-evaluates to OK — the PROBLEM stays stuck ON forever. Removal path is the LLD lost-resource lifecycle, NOT a simple rule-disable.
- **`discoveryrule` `lifetime_type` enum (Zabbix 7.0) is `0=after period, 1=NEVER, 2=immediately`.** Setting `1` to "remove now" is the inverted-enum trap — `1` means *never delete*, so discovered items are kept. Use **`2`** for immediate lost-resource removal. (Original stock value was `lifetime="7d", lifetime_type="0"` = delete-after-7d, which is how you confirm `0`=after.)
- **The Proxmox LLD rules are DEPENDENT (`type=18`), fed by the master HTTP item `proxmox.cluster.resources` (`type=19`, 5m poll).** "Execute now" on the *LLD rule itself* does NOT re-run discovery — you must force-run the **master `proxmox.cluster.resources` item** (one per PVE host), which re-polls the PVE API and cascades to the dependent LLDs. Teardown recipe for qemu items: neuter the LLD filter to match nothing (a `{#RESOURCE.TYPE}` regex that never matches) + `lifetime_type=2`, **reload the server config cache** (`zabbix_server -R config_cache_reload`) so host-instance rules inherit the new filter, then force-run each master. A host whose master item has `lastclock=0` (never polled) leaves disabled stragglers the lifecycle can't reap — sweep those with a direct `item.delete` (works on already-disabled discovered items). All codified in the tuning playbook. Note: each PVE Zabbix host (urd/verd/skuld) independently discovers the *whole cluster*, so every guest is monitored ×3 (latent redundancy beyond memory — separate cleanup). Surfaced 2026-06-27 (CP "90% memory" investigation — the CPs were at ~56% real utilisation; the alert was this false-positive class).
- **`uri`-based Zabbix API playbooks MUST be check-mode-safe — the Semaphore drift-check runs `--check`.** `ansible.builtin.uri` is *skipped* under check mode, so a `register`ed result becomes `{"skipped": true, "changed": false}` with **no `.json` key**. A skipped task does NOT evaluate its own `failed_when`, so a read like `template.get` "passes" silently; the next `set_fact`/conditional then dereferences `result.json.*` and dies with `'dict object' has no attribute 'json'` (Ansible's "offending line" heuristic misattributes it to the `set_fact`, not the skipped read). **Fix pattern:** put `check_mode: false` on the read-only API tasks (template.get / discoveryrule.get / item.get countOutput — safe to execute during a drift-check) so `.json` is populated, and gate every mutating task/block with `when: not ansible_check_mode` (converging state is out of drift-check scope — same posture as `zabbix-host-groups.yml`). Surfaced 2026-07-02 when `zabbix-proxmox-template-tuning.yml` broke the drift-check on its first check-mode run (it had only ever run un-checked via `asgard-zabbix.yml`).

- **`community.zabbix.zabbix_user` REPLACES the user's whole media list, so every media for `Admin` must be written in ONE task (2026-10-02, 10d2).** Adding the n8n media type with its own attach task would silently drop Hermod's on the next run (and vice versa). Both entries live in `roles/zabbix-server/defaults/main.yml` (`zabbix_hermod_user_media`, `zabbix_n8n_user_media`, joined into `zabbix_admin_user_medias`) and are written by the single attach task in `hermod-mediatype.yml`; the n8n *media type* (`n8n-mediatype.yml`) is imported first because the attach resolves it by name. Disabling n8n means dropping its entry from that list, not deleting the type.
- **Zabbix renders `{EVENT.DATE}` / `{EVENT.TIME}` in the server's LOCAL timezone, with no offset (Hugin: `Europe/Amsterdam`, CEST +0200 / CET +0100).** Treating them as UTC puts every timestamp 1-2 h in the future (the 10c normalizer did until 2026-10-02). The webhook script runs inside the server process, so it builds a `Date` from the components in that same local zone and emits exact UTC (`n8n-webhook.js`, tested under `TZ=Europe/Amsterdam`); the Hermod-path normalizer converts from `Europe/Amsterdam`. Ambiguous local times in the autumn DST overlap resolve to the first occurrence.
- **Unresolved webhook macros arrive as the literal string `*UNKNOWN*` (or the raw `{MACRO}`), not as empty.** `{ITEM.NAME2}` on a trigger with one item, `{EVENT.RECOVERY.*}` on a problem, `{TRIGGER.URL}` when unset. The sender's `clean()` maps both forms to `''`; any new script must do the same or the agent will read "*UNKNOWN*" as data. `{EVENT.TAGSJSON}` is the structured tag list (a JSON array); a trigger tag named `runbook_id` stamps the runbook at the source.
- **A webhook media type with no message template for an operation type never sends that operation.** The n8n script builds its own JSON from the params, but `message_templates` for `operations` AND `recovery_operations` must still exist or recoveries are silently not sent.
- **An Ansible bool passed as `-e flag=false` on the command line is the STRING `"false"`, which is truthy in a Jinja `if`.** The media-list expression uses `(zabbix_n8n_enabled | bool)`; do the same for any flag that an operator might override with `-e`. (`when:` conditionals coerce it, a bare `if` inside `{{ }}` does not.)
- **The AIOps read-only identity (`aiops-ro`) needs THREE things to be read-only, and a visible host needs a fourth (2026-10-02, 10d2).** User role `AIOps read-only` (type User, `api.mode: 1` allow-list `*.get`, UI off), user group with `read-only` on every HOST group, and `read-only` on every TEMPLATE group too: without template-group rights `host.get` silently returns `parentTemplates: []` for every host (it looks like "no templates", not a permission error). A new role also starts with the UI actions (acknowledge, execute_scripts, manage_api_tokens, ...) enabled; the task switches each off explicitly. Proof it holds: `host.update`, `event.acknowledge`, `user.create`, `script.execute`, `token.generate`, `configuration.import` all answer `No permissions to call`.
- **`community.zabbix.zabbix_usergroup` takes `gui_access: disable` (not `disabled`), and `hostgroup_rights` need `permission: read-only` (not `read`).** The failure message names the allowed values; both are enums.
- **`community.hashi_vault` MODULES (unlike lookups) run on the target.** `vault_kv2_write` delegated to Hugin failed with `Failed to import the required Python library (hvac)`. Delegate them to `localhost` with `become: false`; the lookups already run on the controller.
- **A `never`-tagged task still runs under any broad tag it inherits.** Putting the token-minting tasks behind `tags: [never, zabbix:aiops-token]` in a file imported with `tags: [zabbix, ...]` would run them on `--tags zabbix`. The minting file is imported with ONLY `[never, zabbix:aiops-token]`.
- **A Zabbix API token is shown once, at generation.** `tasks/aiops-token.yml` therefore writes it to Vault in the same run and preflights the Vault write first (a placeholder), so a Vault identity that cannot write fails BEFORE a token is generated. It does nothing while `secret/ansible/aiops/zabbix-token` holds a value; to rotate, delete that secret and the Zabbix token `toolbelt`, then re-run `--tags zabbix:aiops-token`. Debug a hidden failure with `-e zabbix_aiops_no_log=false` (the tasks' `no_log` is a variable, default true).
- **`min(item,T)=0` fires on ANY zero in the window; "failing for the whole window" is `max(item,T)=0` (found 2026-10-10).** The Jellyfin QSV smoke trigger used `min(...,70m)=0 and count(...)>=10` to mean "failed for two consecutive hourly runs" and opened 18 seconds after the first failed run (J5 failure-path test); with `min` it would also have stayed open for 70 minutes after a fix. Rule for a 0/1 health item: sustained failure is `max(...)=0`, sustained success is `min(...)=1`, and recovery follows when the opposite value appears. Fixed in `playbooks/files/zabbix/jellyfin.yml`; the other custom templates already use `max()=0`. Roll a template fix out with `zabbix-agent.yml --tags zabbix-agent:jellyfin-template`.
- **Scratch CTs from `pbs-restore-test.yml` raise Information-level "LXC [...] has been restarted (uptime < 10m)" problems** on the Proxmox template (seen for `CT1199` and `restore-test-<name>`). They are not routed anywhere and clear on their own; the stock template has no LXC name filter macro to exclude them.
