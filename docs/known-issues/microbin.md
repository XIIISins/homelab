# Known gotchas — MicroBin (pastebin / file-share)

*Migrated from `CLAUDE.md`. Recovery commands + rules. Incident retros in [`../incidents/`](../incidents/).*

## MicroBin (pastebin/file-share, Services)

- **JSON-DB + auto-expiry/burn panics and poisons the paste mutex → every POST 502s (run the patched image).** `remove_expired` (`src/util/misc.rs`) calls `delete(None, Some(p.id))` from INSIDE a `pastas.retain(..)` closure. Under `--json-db` (our backend), `db::delete` does `pastas.expect("Called delete() without passing Pasta vector")` — it needs the WHOLE Pasta vector to rewrite the JSON file, but the vector is mutably borrowed by `retain`, so `None` is passed → `.expect()` panics WHILE HOLDING the pastas mutex. Rust then poisons that `std::sync::Mutex` permanently, so every later write (`create.rs` `data.pastas.lock().unwrap()`) panics → the worker returns no response → Traefik/cloudflared surface a **502**. **GET keeps returning 200** (the read path tolerates the poison), so the pod looks healthy — `kubectl get pods` shows Running 1/1. **Trigger:** any paste crossing its expiry/burn/GC threshold, surfaced on the next `/list` or paste view (`list.rs:26`, `pasta.rs:40/211/293/366`). With the 24h default expiry, this re-fires ~daily. **Symptom in logs:** `panicked at src/util/db.rs:63: Called delete() without passing Pasta vector` (the first panic) then forever after `panicked at src/endpoints/create.rs:377: PoisonError { .. }`. **Genuine upstream bug, NOT a JSON-DB limitation NOR a config error** — present unchanged v2.0.4 → v2.1.4 → master; v1.x predates the json/sqlite split. There is no fixed release to upgrade to, and JSON deletion itself works fine when the vector is passed (the manual `/list → Remove` path, `remove.rs:53`, is unaffected). **Fix = custom patched image** (`docker/microbin/`, built to `ghcr.io/xiiisins/microbin-homelab` by `.github/workflows/build-microbin-image.yml`): the one-site patch prunes via `retain` then calls the existing public `db::update_all(pastas)` ONCE after the borrow ends (correct for both JSON + SQLite). **Stopgap if it re-fires on stock:** `kubectl rollout restart deployment/microbin -n microbin` clears the in-memory poison — but only until the next paste expires. **GHCR pull:** GitHub has NO API to make a package public (UI-only), so `microbin-homelab` is kept PRIVATE and pulled via a read-only token — `externalsecret-ghcr.yaml` renders a dockerconfigjson from the OPERATOR-WRITTEN Vault path `secret/k8s/microbin/ghcr` (fields `username` + `token`, `read:packages` scope), referenced by the deployment's `imagePullSecrets`. This DIVERGES from `semaphore-homelab` (public, no pull secret) — chosen to keep the rollout fully automatable. The Vault secret must exist before the deployment reconciles or the pod `ImagePullBackOff`s. **Workflow-file push gotcha:** frigg pushes via a repo deploy key, which GitHub forbids from creating/updating `.github/workflows/` — pushing `build-microbin-image.yml` needs a `workflow`-scoped credential (push from a user account / PAT, not frigg's deploy key). Surfaced 2026-06-25.
- **MicroBin's JSON-DB path is HARDCODED to `pasta_data/database.json` and IGNORES `MICROBIN_DATA_DIR`.** `src/util/db_json.rs`: `static DATABASE_PATH: &str = "pasta_data/database.json"` (relative to `WORKDIR /app`). `MICROBIN_DATA_DIR` only relocates *attachments*, NOT the JSON DB. Symptom: first deploy crashloops with `panicked at db_json.rs … failed to create temporary database file … pasta_data/database.json.tmp: No such file or directory` because the persistent volume was mounted at the DATA_DIR path (e.g. `/data`) while the DB wants `/app/pasta_data`. **Fix:** mount the PV at **`/app/pasta_data`** (the hardcoded dir) and set `MICROBIN_DATA_DIR=/app/pasta_data` too, so DB + attachments co-locate on the one volume. (SQLite mode DOES honor `data_dir`, but SQLite-on-NFS is the mmap/locking footgun — JSON's tmp-write-then-atomic-rename is NFS-safe, so JSON-on-NFS at the hardcoded path is the right combination.) Surfaced 2026-05-31.
- **MicroBin docs (microbin.eu) + WebFetch summaries are unreliable on defaults/var names AND route paths — verify against the binary/source, not the docs.** Three separate misses on one deploy: (1) the config page claimed `MICROBIN_DATA_DIR` default `microbin_data`; the running binary used `pasta_data`. (2) The docs called the paste-list route **`/pastalist`** and said `MICROBIN_NO_LISTING` "disables the /pastalist endpoint" — but the REAL route is **`/list`** (`endpoints/list.rs #[get("/list")]`). Gating `/pastalist` left the actual `/list` index world-readable (a real auth hole — caught post-deploy). The true gated set is `/list`, `/admin`, `/auth_admin` (the form `/admin` 302-redirects to — gate it too or it's a backdoor), `/remove/{id}`. (3) admin is `/admin` exact (actix 404s on `/admin/` trailing slash). **Diagnostics that ARE authoritative:** (a) a throwaway probe pod overriding the entrypoint — `kubectl run mb-probe --image=danielszabo99/microbin:<v> --restart=Never --command -- sh -c 'pwd; microbin --help | grep -i data; microbin --version'` (the image has `sh`); (b) grep the raw source at the matching tag for route macros + path constants (`raw.githubusercontent.com/szabodanika/microbin/v<ver>/src/...`, e.g. `grep '#\[get(' src/endpoints/*.rs`). The official image is `danielszabo99/microbin` (per the repo README badges), `WORKDIR /app`, `ENTRYPOINT ["microbin"]`, no `.env` bundled. **General lesson: when you gate specific routes, enumerate the real routes from source before trusting doc path names.**
- **Partial-auth gating pattern (open app, gated admin routes) = Gateway API longest-prefix + per-rule Traefik Middleware `extensionRef`.** Most-specific path rules (`/list`, `/admin`) carry the `authentik-forward-auth` Middleware filter; the `/` catchall has none → open. This is the inverse of the VictoriaLogs route (which *exempts* `/insert` from an otherwise-gated app) and the general tool for "anonymous-public app with a trusted admin surface." The Middleware must be a **same-namespace copy** (extensionRef resolves in the route's namespace) — copy `monitoring/authentik-forward-auth` into the app ns. Gating is at Traefik, so curling the Service directly bypasses it (returns 200) — test gating through the Gateway/tunnel (302 → Authentik) instead.
  - **CRITICAL for partially-gated apps: the `/outpost.goauthentik.io` path MUST be routed through the ForwardAuth rule too.** After login, Authentik redirects the browser to `https://<host>/outpost.goauthentik.io/callback?code=…`, and the embedded outpost only processes that callback when the request goes THROUGH the ForwardAuth middleware (its `/auth/traefik` endpoint inspects `X-Forwarded-Uri`, exchanges the code, sets the session cookie, 302s back). For a **fully-gated** app (VL/VM) the callback rides the gated `/` catchall automatically — which is why VL/VM need no special handling. For a **partially-gated** app whose `/` catchall is OPEN, the callback falls through to the app backend and 404s ("`<app> doesn't know what to do with /outpost.goauthentik.io/callback`"). **Fix: add `PathPrefix: /outpost.goauthentik.io` as another match in the gated rule** (same backend, same Middleware) — no cross-namespace route to `authentik-server` needed. Surfaced 2026-05-31 (MicroBin first login). Symptom: the pre-login 302 → Authentik works, but the post-login callback dead-ends on the app.
- **A new Authentik `forward_single` proxy provider needs a one-time embedded-outpost attach or ForwardAuth 404s.** Same as the observability providers (`terraform/authentik/observability.tf` note). TF doesn't manage the embedded outpost; after `terraform apply`, append the new provider's pk to the outpost: `curl -X PATCH .../api/v3/outposts/instances/<embedded-pk>/ -d '{"providers":[<existing…>,<new-pk>]}'` (or via the UI: Applications → Outposts → edit embedded → add provider). Symptom of forgetting: gated routes loop on login / 500 from the outpost endpoint.
